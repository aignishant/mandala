# 4.2 — The tracker you never hand-edit

## One-line answer

`docs/TRACKER.md` is **generated** from the curriculum index plus what is actually on disk, never
edited by hand — because a progress file that a human updates is a progress file that eventually
disagrees with the project, and a status you cannot trust is worse than no status at all.

---

## The story

A team keeps a migration checklist in a shared document. Forty services need moving to a new
authentication scheme. Each row has a service name, an owner, and a status: not started, in
progress, done.

For the first few weeks it is accurate. Then one engineer finishes two services in an afternoon and
updates one row, meaning to do the other later. Someone else marks a service done when the pull
request is open rather than merged. A service is renamed and appears twice. Two rows are marked done
by different people who each believed the other had done the work.

At the cutover meeting the document says thirty-eight of forty are complete. The engineering
manager, sensibly, asks someone to verify. It takes a day, and the real number is thirty-one.

The document was not maintained badly. It was maintained *by hand*, which means it recorded what
people **remembered to write down**, not what was **true**. Those two things track each other
closely at first and diverge steadily, and the divergence is invisible — a stale row looks exactly
like a fresh one.

The fix is not more discipline. It is to stop storing the status separately from the thing it
describes.

---

## The idea in plain language

**Two ways to know the state of something:**

- **Store it.** Write the status somewhere and update it when things change. Fast to read, and wrong
  the moment someone forgets.
- **Derive it.** Compute the status from the artifacts themselves, every time you ask. Slower to
  read, and it cannot be stale, because there is nothing to forget.

`docs/TRACKER.md` is derived. Nothing records "Day 7 is done". The generator looks at the filesystem
and works it out:

| Question | Answered by looking at |
|---|---|
| Does this day exist at all? | is there a `days/day-07/` folder |
| Is it written? | does it have `LESSON.md` **and** a non-empty `parts/` |
| How deeply? | how many files in `parts/*/` |
| Is it complete? | does `CHECKLIST.md` have zero `- [ ]` lines and at least one `- [x]` |
| Is it still on the old format? | is there a `legacy/days/day-07/LESSON.md` and nothing new |

Every one of those is a fact about files, and files are what `./m done`
([3.3](../03/3.3-the-done-gate.md)) actually produces. So the tracker cannot claim a day is finished
when the checklist has open boxes — **not because someone would notice, but because there is no
field in which to write the lie.**

**The two inputs, and why they are different kinds of thing.** The generator reads:

1. **`docs/CURRICULUM_INDEX.md`** — the *plan*: which days exist, their titles, their IDs, their
   kind. Hand-maintained, because it changes only when the curriculum changes, and then
   deliberately.
2. **The filesystem** — the *reality*: what has actually been written.

Plan on one side, reality on the other, and the tracker is the join. That separation is the design.
The index has no status column at all, so there is no second place where progress could be recorded
and no way for two records to disagree.

**Why the output is committed even though it is generated.** It is a fair question — generated files
are usually ignored. Two reasons here. It is the file a person reads to answer "where am I?", so it
should be visible on a repository page without running anything. And because `./m done` regenerates
it *before* committing, the tracker in commit *N* describes the project as of commit *N* — the
history of the file is a real record of progress over time, which a `.gitignore`d file could not
give you.

**And the guard against the obvious hazard.** Any generated file invites someone to improve it by
hand, reasonably, since it is Markdown. The file opens with *"Do not edit this file by hand"* and
names the command that regenerates it, because the alternative is an edit that survives until the
next regeneration and then silently vanishes.

---

## Why Mandala needs it

- **Ninety days is long enough to lose track**, and the tracker is what a future session — yours or
  an AI pair-programmer's — reads first to answer "what is next?". If it could be stale, the answer
  would need verifying every time, which is the cutover meeting from the story.
- **The part count per day is the thin-day detector.** Part 11.9 says a thin day should be visible
  from the progress table alone. A day covering three frameworks with four parts stands out in a
  column of numbers, without anyone reading the documents.
- **The 🗃️ legacy marker is the migration ledger.** All 91 v1.1.0 lessons live under `legacy/days/`
  and are being rewritten one at a time. The tracker distinguishes *legacy* (an old lesson exists to
  mine) from *pending* (nothing exists), which is exactly the distinction you need to plan the next
  day's work.
- **Principle 1 is measured here.** "No commit = day not done" produces a number, and the number is
  computed rather than claimed.

## The mechanism

Run it:

```bash
uv run python scripts/tracker.py
```

**Line by line:**

- Reads `docs/CURRICULUM_INDEX.md`, walks `days/` and `legacy/days/`, and rewrites
  `docs/TRACKER.md`. It writes exactly one file and touches nothing else.
- It has no arguments for choosing a day, on purpose: the tracker is always regenerated whole. A
  partial regeneration would let one row be current while another is stale, reintroducing the exact
  problem the design removes.

The summary form, which is what `./m status` calls:

```bash
uv run python scripts/tracker.py --summary
```

**Line by line:**

- `--summary` — print one line and **write no file**. That distinction matters: reading progress
  should never modify the repository, or `./m status` would leave you with changes to commit.

Now the two functions that carry the design. First, how a day's status is derived:

```python
def inspect(day: Day) -> Day:
    legacy_folder = find_folder(day.number, LEGACY_DAYS)
    day.legacy = legacy_folder is not None and (legacy_folder / "LESSON.md").is_file()

    folder = find_folder(day.number)
    if folder is None:
        return day
    parts_dir = folder / "parts"
    day.parts = len(list(parts_dir.glob("*/*.md"))) if parts_dir.is_dir() else 0
    day.written = (folder / "LESSON.md").is_file() and day.parts > 0
    checklist = folder / "CHECKLIST.md"
    day.has_checklist = checklist.is_file()
    if day.has_checklist:
        text = checklist.read_text(encoding="utf-8")
        day.open_boxes = len(re.findall(r"^- \[ \]", text, flags=re.M))
        ticked = len(re.findall(r"^- \[x\]", text, flags=re.M | re.I))
        day.complete = day.open_boxes == 0 and ticked > 0
    return day
```

**Line by line:**

- `find_folder(day.number, LEGACY_DAYS)` — the same lookup against the archive, so a day can be
  reported as 🗃️ legacy. Reusing one function for both trees means the Day-0 folder-naming
  irregularity (`day-00-setup`) is handled in one place.
- `if folder is None: return day` — an unwritten day returns with every flag false. **No exception,
  no error** — "not written" is a normal state for most of ninety days, not a failure.
- `parts_dir.glob("*/*.md")` — every Markdown file exactly one directory deep: `parts/01/1.1-x.md`
  matches, a stray `parts/notes.md` does not. The glob encodes the contract's folder shape rather
  than restating it.
- `day.written = (folder / "LESSON.md").is_file() and day.parts > 0` — **the v2.0.0 definition of
  written, in one line.** A hub with no parts is not a written day (Principle 15), so a half-migrated
  day is reported honestly instead of counting toward progress.
- `re.findall(r"^- \[ \]", text, flags=re.M)` — count open boxes, the same pattern the `done` gate
  greps for ([3.3](../03/3.3-the-done-gate.md)). The gate and the tracker agree because they are
  asking the identical question of the identical file.
- `day.complete = day.open_boxes == 0 and ticked > 0` — **both halves are needed.** Zero open boxes
  alone would mark an empty checklist complete, which is the fail-open bug from
  [3.3](../03/3.3-the-done-gate.md) wearing different clothes. Requiring at least one tick means a
  file with no boxes cannot masquerade as finished.
- `encoding="utf-8"` — stated explicitly, because Python on Windows otherwise picks the system code
  page and mangles the emoji and en dashes these documents are full of.

And how the plan side is read:

```python
PHASE_RE = re.compile(r"^##\s+Phase\s+(\d+)\s+·\s+(.+?)\s+·\s+Days?\s+([\d–—-]+)\s*$")
ROW_RE = re.compile(r"^\|\s*(\d+)\s*\|\s*(.+?)\s*\|\s*(.*?)\s*\|\s*([\w ]+?)\s*\|\s*$")
```

**Line by line:**

- `PHASE_RE` matches a heading like `## Phase 7 · LangGraph 1.x · Days 43–52`, capturing the number,
  the name and the span. The `·` separators are literal, which means the index has a *format*, not
  just a layout — and formatting it differently would silently produce a tracker with missing
  phases.
- `(.+?)` — **non-greedy**: match as few characters as possible. With a greedy `(.+)` the name would
  swallow the ` · Days 43–52` too. This is the single most common regex bug when parsing delimited
  text.
- `[\d–—-]+` — the day span, allowing an en dash, an em dash or a hyphen, because all three occur in
  hand-written Markdown and rejecting two of them would be a checker failing on punctuation.
- `ROW_RE` matches a table row `| 43 | Graph thinking | LG-01, LG-02 | lab |`, capturing day number,
  title, IDs and kind. `\s*` around each `|` absorbs the spacing people use to align columns.
- `([\w ]+?)` for the kind — word characters and spaces only, which is why the index's Kind column
  says `gate` rather than `gate 🎯`. **A parser and its input are a contract**, and this one is
  documented at the top of the index.

Look at what it produced:

```bash
head -30 docs/TRACKER.md
```

**Line by line:**

- The frontmatter names the generator, so anyone opening the file learns where it came from.
- The progress table and the bar are computed from the counts. `bar()` renders `█` and `░` blocks —
  a progress bar in plain text, which works on a repository page with no tooling.
- Below it, one row per day with its status badge, part count and open-box count. **That part-count
  column is Part 11.9's thin-day detector**, published without anyone reading a document.

## When it breaks

**The index format drifting away from the parser:**

```text
$ uv run python scripts/tracker.py
wrote docs\TRACKER.md - 0/1 written
```

...on a project with ninety days. **What it means.** `PHASE_RE` matched nothing, so no phases were
found and only the hard-coded Day 0 appears. Almost always a heading was edited — an `-` where a `·`
belongs, or "Days" spelled differently. The failure is quiet, which is this design's real weakness:
a parser that finds nothing reports success with an empty result. **The tell is always the count**,
so read it every time rather than trusting the exit status.

**The missing input, which does fail loudly:**

```text
$ uv run python scripts/tracker.py
missing C:\Users\me\...\mandala\docs\CURRICULUM_INDEX.md - the tracker has nothing to track
```

**What it means.** `sys.exit(str)` prints the message and exits non-zero. Fail closed
([3.3](../03/3.3-the-done-gate.md)): with no plan to compare against, the honest output is no output.

**The hand-edit, discovered the way hand-edits are always discovered:**

```text
$ git diff docs/TRACKER.md
-| 7 | Memory that survives the turn | AG-09, AG-12 | lab | ✅ done | 12 | 0 |
+| 7 | Memory that survives the turn | AG-09, AG-12 | lab | 📄 written | 12 | 3 |
```

**What it means.** Someone marked Day 7 done in the tracker; regeneration reverted it, because the
checklist still has three open boxes. The generated file won, correctly. **The lesson is not "do not
edit the tracker" so much as "the tracker was never the place that decision lives"** — tick the
boxes and the tracker follows.

**The one that looks like lost progress:**

```text
$ ./m status
Mandala: 0/91 days in the v2.0.0 shape (0 sub-topic docs), 0 completed, 91 legacy to regenerate, 0 never written.
```

...after you have written a day. **What it means.** Read the definition rather than doubting the
count: *written* requires `LESSON.md` **and** a non-empty `parts/`. A day with parts but no hub, or
a hub whose parts live loose in `parts/` instead of in `parts/01/`, is not written by this
definition. `./m depth N` will tell you which ([4.1](4.1-the-depth-check.md)). The number is not
wrong; the day is not finished.

## In production

**"Single source of truth" is the whole idea, and the discipline is in the negative form:** the
truth lives in exactly one place, and everything else is a *view* of it. When a status appears in
two places, they will diverge, and you will spend the divergence discovering which was right. The
practical test to apply to any dashboard: *if I change the underlying thing and change nothing else,
does this update?* If not, it is a copy, and copies rot.

**This is the same pattern as infrastructure-as-code and observability.** A server's state is
derived from a declaration rather than recorded in a wiki; a service's health is derived from
telemetry rather than from a status page someone updates. In each case the alternative — a
human-maintained record of what is true — fails identically, and always at the meeting where it
matters. **You meet this again on Day 75**, when traces become the record of what an agent actually
did, rather than logs someone remembered to add. Principle 8 states it directly: *the trace is the
truth. If it is not in a trace, it did not happen.*

**Generated files need three things to be good citizens**, and this one has all three: a header
saying they are generated and naming the command, deterministic output so regeneration produces no
spurious diff, and regeneration wired into the workflow rather than left to memory (`./m done` calls
it). Miss the second and every commit contains noise; miss the third and you are back to hand
maintenance with extra steps.

**Deriving state has a real cost, and it is worth naming.** It is slower — this script walks the
filesystem on every run — and it constrains the artifacts, since the checklist format is now a
parsing contract that cannot be freely restyled. At small scale the trade is obviously right. At
large scale teams add caching and incremental computation to keep it, because the alternative — going
back to stored status — reintroduces the story. **The pattern to recognise: when derivation gets too
slow, you cache the derivation; you do not go back to storing the answer.**

**The review comment a senior engineer leaves.** On a pull request that edits a generated file:
*"This is generated by `scripts/tracker.py` — the change will disappear on the next run. What is the
underlying state you are trying to reflect?"* And on a new dashboard field that a human updates:
*"Can we derive this instead? A field that requires someone to remember is a field that will be
wrong within a month, and wrong silently."*

**The interview question.** *"How do you keep a status dashboard accurate?"* The weak answer is
process and reminders. The one that lands: do not store status — derive it from the artifacts that
already exist, so there is no separate record to go stale; commit the generated view for
readability; and make regeneration part of the workflow that changes the underlying state, not a
separate step someone must remember. The sentence worth volunteering is the diagnostic one: *"if
changing the thing does not change the dashboard, the dashboard is a copy, and copies rot."*
