# 4.1 — The depth check, and turning a writing standard into an exit code

## One-line answer

`scripts/depth_check.py` reads every day folder and refuses any day that violates the parts of the
plan's Part 11 contract a machine can see — a missing section, an unexplained code block, a
numbering gap, a time estimate — which converts a documentation standard from something you intend
into something the build enforces.

---

## The story

A curriculum was written across many days. Each day was one long document, and every day was
genuinely good work.

Around the fortieth day something began to shift, and nobody noticed because it happened gradually.
A day would cover four subjects, and the fourth would get three paragraphs where the first got
fifteen — not because it was simpler, but because the page was already long. A failure mode would be
described as "you may see an error here" instead of quoting the error. A section that had always
ended with "and here is what changes in production" would end at the working example instead.

Every individual decision was defensible. The page *was* long. The reader *would* probably manage.
The subject *could* be covered again later.

Reviewing the whole set afterwards, the pattern was unmistakable: the last topic of a day was
reliably the thinnest, and thinness correlated with position on the page rather than with the
difficulty of the subject. The material had been trimmed to fit a shape, and nobody had decided to
do that. It had simply happened, one reasonable edit at a time.

You cannot fix that by resolving to try harder. Trying harder is exactly what produced it. You fix
it by making the standard *checkable*, so that a shortfall is a failing build rather than a
judgement call at the end of a long evening.

---

## The idea in plain language

Part 11 of the plan states how a day must be written: one document per subtopic, ten required
sections in a fixed order, a real error message in "When it breaks", an "In production" section that
is never optional, no clocks anywhere, and a hub that orients without teaching.

That is a standard. Standards decay unless something applies them.

**Split the standard into what a machine can verify and what only a reader can.** This is the
central move, and being honest about the boundary is what makes the machine half worth having.

| A machine can check | Only a reader can judge |
|---|---|
| Is there an `## In production` section? | Is it any good, or three vague sentences? |
| Does every code block have a walkthrough after it? | Does the walkthrough explain *why that line*? |
| Are the sections in the contract's order? | Does the argument actually flow? |
| Is there a time estimate anywhere? | Was an explanation quietly trimmed? |
| Do the part numbers run 1, 2, 3 with no gap? | Is each part genuinely one idea? |

The left column is mechanical: **presence, order, shape, absence**. None of it proves quality. All of
it catches the specific failures from the story — because a section that was cut to save space is
*absent*, and absence is exactly what a machine sees best.

**What "unexplained code block" means, since it is the subtlest check.** The contract says every code
block is followed by a `**Line by line:**` walkthrough. The script walks each document, finds each
fenced block, and looks ahead for that marker before the next block or the next heading. Blocks that
are *evidence* rather than teaching are exempt — error output, a diagram, a bare verification
command — which the script recognises by the fence's language tag and by the heading it sits under.
That exemption list is a judgement encoded in code, and it is worth knowing it exists: a checker
with no exemptions produces false failures, and a checker with too many produces false confidence.

**Why banning clocks is a *content* rule enforced by a *text* check.** Principle 16 says a day is a
unit of subject, not of time. The reason is causal, not aesthetic: the moment a document claims to
take ninety minutes, every edit is measured against that claim, and the way to keep the claim true
is to cut the explanation. **Removing the clock removes the pressure**, and a regular expression
that fails the build on a pace claim, a duration field, or a number followed by a unit of time is
how the removal stays permanent.

**And the fail-closed principle from [3.3](../03/3.3-the-done-gate.md) applies again**: a day folder
with no `parts/` directory is not "unchecked", it is a *failure*. A checker that skips what it does
not understand is a checker that reports success on the worst input.

---

## Why Mandala needs it

- **This day exists because of the story.** The v1.1.0 lessons for all ninety days are archived in
  `legacy/` precisely because the single-file format produced that drift. The depth check is the
  mechanism that stops v2.0.0 going the same way — see `docs/CHANGELOG_PLAN.md` for the amendment.
- **`./m check` runs it on every day, every time** ([3.2](../03/3.2-the-case-dispatcher.md)), and
  `./m done N` cannot commit while it fails ([3.3](../03/3.3-the-done-gate.md)). A day that does not
  satisfy the contract cannot be marked complete, whatever the code does.
- **The days get harder and the temptation grows.** Day 50's interrupts and Day 53's MCP stateless
  core are large subjects. Those are exactly the days where "the page is getting long" would have
  won, and exactly the days where a reader most needs the failure text and the production section.
- **`docs/TRACKER.md` publishes the part count per day**
  ([4.2](4.2-the-tracker-you-never-hand-edit.md)). A day with three parts covering three frameworks
  is visible as thin from the progress table alone, without anyone reading it.

## The mechanism

Run it. With no day folders yet in the new shape it has nothing to check, which is itself worth
seeing:

```bash
uv run python scripts/depth_check.py
```

**Line by line:**

- `uv run` — the locked environment, as always ([2.5](../02/2.5-the-venv-you-never-activate.md)).
  The script uses only the standard library, so this is about consistency rather than dependencies.
- With no `parts/` directory anywhere it prints `no day has a parts/ directory yet` and exits **0**.
  That is a deliberate choice: an *unwritten* day is not a *failed* day, or the check would be red
  for the entire project until Day 90.

Now the shape of the checker itself. The section list is a table, in contract order:

```python
PART_SECTIONS = [
    ("one-line answer", re.compile(r"^#{2,3}\s.*one[- ]line answer", re.I | re.M)),
    ("the story", re.compile(r"^#{2,3}\s.*the story", re.I | re.M)),
    ("the idea in plain language", re.compile(r"^#{2,3}\s.*idea in plain language", re.I | re.M)),
    ("why Mandala needs it", re.compile(r"^#{2,3}\s.*why mandala needs it", re.I | re.M)),
    ("the mechanism", re.compile(r"^#{2,3}\s.*mechanism", re.I | re.M)),
    ("line by line", re.compile(r"^#{2,3}\s.*line by line|^\*\*Line by line:?\*\*", re.I | re.M)),
    ("when it breaks", re.compile(r"^#{2,3}\s.*when it breaks", re.I | re.M)),
    ("in production", re.compile(r"^#{2,3}\s.*in production", re.I | re.M)),
    ("check yourself", re.compile(r"^#{2,3}\s.*check yourself", re.I | re.M)),
]
```

**Line by line:**

- A **list of tuples**, not a dictionary, because **order is part of the contract** and a list
  preserves it. The checker verifies not just that all nine are present but that their positions in
  the file are ascending.
- `re.compile(...)` — build the regular expression once at import rather than on every file. With
  ninety days times a dozen parts times nine patterns, that is a real saving, and it is the idiom
  you will see in any Python that matches patterns in a loop.
- `^#{2,3}\s` — a line starting with two or three `#` followed by whitespace: a Markdown heading at
  level 2 or 3. Level 1 is excluded because that is the document title.
- `.*one[- ]answer` style patterns — match the *phrase* anywhere in the heading, so
  `## The story` and `## The story — a Tuesday afternoon` both count. **The contract is about the
  section existing, not about exact wording**, and a checker that demanded exact strings would be
  rejecting good documents for punctuation.
- `re.I` — case-insensitive. `re.M` — multi-line, which is what makes `^` mean "start of any line"
  rather than "start of the string". Forgetting `re.M` is the single most common bug in this kind of
  code, and it fails in the confusing direction: everything appears to be missing.
- `"line by line"` matches **either** a heading or the `**Line by line:**` bold marker, because in
  practice the walkthroughs live inline after each code block rather than under one heading. The
  contract cares that the explanation is adjacent to the code, not that it has its own section.

The clock ban, which is the check with the most opinion in it:

```python
TIME_BANS = [
    (
        re.compile(r"\b\d+\s*[-–]?\s*\d*\s*(minutes?|mins?|hours?|hrs?)\b(?!\s*(of |the ))", re.I),
        "a time estimate in the prose",
    ),
    (re.compile(r"should take (about |around |roughly )?\w+", re.I), "a 'should take ...' pace"),
    (re.compile(r"\b(half|full) a? ?day\b", re.I), "a day-length estimate"),
]
```

**Line by line:**

- `\b\d+` — a word boundary then one or more digits, so a bare number followed by a time
  unit matches, while a number glued into a longer word does not.
- `[-–]?\s*\d*` — an optional hyphen or en dash and a second number, so a written range is caught as
  one match rather than slipping through its second half.
- `(?!\s*(of |the ))` — a **negative lookahead**: do *not* match if the next words are "of" or "the".
  This is the false-positive guard: it exempts phrasings where the number is describing something
  other than how long you should spend. **Every text-matching check needs one of these**, and finding
  out which exemptions you need is what the first few runs are for.
- Each entry is `(pattern, description)`, so the failure message says *what kind* of clock was found
  rather than dumping a regex at you. A checker whose error message is its own source code is a
  checker people learn to ignore.
- The prose is scanned with fenced code blocks stripped out first, because a real command may
  legitimately mention a timeout.

Now look at what the checker is matching against, on a document you have already read:

```bash
grep -n '^## ' days/day-00-setup/parts/04/4.2-the-tracker-you-never-hand-edit.md
```

**Line by line:**

- `grep -n '^## '` — every level-2 heading in that part, with line numbers. What comes back is the
  nine required sections, in contract order, and nothing else.
- **Compare the line numbers to `PART_SECTIONS` above.** The checker does exactly this: find each
  pattern, record where it matched, and assert the positions are ascending. A document that reorders
  two sections has descending positions, and a document that dropped one has no position at all.
- The single quotes around `'^## '` stop the shell touching the `#`, which it would otherwise treat
  as the start of a comment.

Delete a section from a copy and watch the refusal, which is the only way to trust a checker:

```bash
cp -r days/day-00-setup /tmp/day-demo && sed -i '/^## In production$/,/^## Check yourself$/{/^## Check yourself$/!d}' /tmp/day-demo/parts/04/4.2-the-tracker-you-never-hand-edit.md && grep -c '^## ' /tmp/day-demo/parts/04/4.2-the-tracker-you-never-hand-edit.md
```

**Line by line:**

- `cp -r` — copy the day folder somewhere disposable, because you are about to damage it on purpose
  and you do not want to damage the real one.
- `sed -i '/START/,/END/{/END/!d}'` — a **range delete**: from the line matching the first pattern up
  to the line matching the second, delete everything *except* the end line. `-i` edits in place.
  The effect is to remove one whole section and leave the next heading intact — precisely the shape
  of the failure from the story, where a section was cut and its neighbours closed over the gap.
- `grep -c '^## '` — count the headings that remain: **eight**, where the contract requires nine.
- Run `uv run python scripts/depth_check.py` against that copy and it reports
  `missing required section: in production`. The file still looks like a finished document. That is
  the entire reason the check exists.

## When it breaks

**A day that has been split but not deepened:**

```text
$ ./m depth 12
FAIL day  12  3 problems
       - parts/01/1.1-what-a-crew-is.md: missing required section: in production
       - parts/01/1.2-roles-and-goals.md: missing required section: when it breaks
       - parts/02/2.1-the-sequential-process.md: code block at line 88 has no 'Line by line' walkthrough

depth contract: 0/1 days pass
```

**What it means.** Exactly the story, caught. Three subtopic documents exist — the day *looks*
written — and three of them stop before the part that makes them professional. The failure names the
file, the section and, for the code block, the line number. Nothing here requires judgement to act
on.

**The clock that slipped in:**

```text
$ ./m depth 23
FAIL day  23  1 problems
       - LESSON.md: a time estimate in the prose ('90 minutes') - a day has no clock (Principle 16)

depth contract: 0/1 days pass
```

**What it means.** Somewhere in the hub a sentence promises ninety minutes. Delete the claim rather
than adjusting it: the point is not that the estimate is wrong, it is that having one creates the
pressure to trim ([Principle 16](../../../../docs/00_MASTER_PLAN_AGENT_STACKS.md)).

**The numbering gap, which is a symptom rather than a formatting nit:**

```text
$ ./m depth 47
FAIL day  47  2 problems
       - parts/: section 2 subtopics are [1, 3], expected 1..2
       - LESSON.md: frontmatter says parts: 8, parts/ holds 7

depth contract: 0/1 days pass
```

**What it means.** A part was deleted or never written, and the hub still counts it. The gap matters
because the hub's map is the reading order — a reader following `2.1 → 2.3` has no way to know
whether `2.2` was removed deliberately or is simply missing. The two failures together tell you
which: the frontmatter still expects it.

**The false positive, which you will eventually hit:**

```text
$ ./m depth 76
FAIL day  76  1 problems
       - parts/01/1.2-rate-limits-are-the-budget.md: a time estimate in the prose ('60 minutes') - a day has no clock (Principle 16)
```

...on a day whose subject is *literally* rate limits, where a provider's quota window is the
material. **What it means.** The checker cannot tell a promise about your evening from a fact about
someone else's API. The fix is to rephrase the sentence in units the ban does not cover — requests
per hour, rather than a number and a time word — and **not** to add an exemption. This is worth stating as a rule: **when a checker produces a false
positive, weaken the document before you weaken the checker.** Every exemption you add is a hole
that stays open for the remaining days, and holes are how the story started.

## In production

**This is linting applied to prose, and the argument is identical.** Nobody argues about tab width
any more because a formatter settled it; nobody should argue about whether a lesson needs a failure
section because a checker settles that too. What both do is move a class of decision out of review
entirely, so review time goes to the things only a human can assess. **Documentation checkers are
standard in serious repositories** — link checkers, required-frontmatter validators, style linters
like `vale` — and they exist for the same reason code linters do.

**The honest limit, and why stating it matters.** This script cannot tell a good explanation from a
bad one. It can only tell an *absent* one from a present one. A day could pass every check and still
be poor. That is not a defect in the design — it is the design: **automate the floor, review the
ceiling.** The danger is a team that mistakes a green checker for a quality guarantee and stops
reading, which is how coverage metrics become theatre. Part 11.8 exists precisely as the
human-reviewed half, and it is written in the plan so the boundary is explicit.

**"Executable specification" is the general pattern.** A rule written only in a document is a rule
that is followed as long as everyone remembers it. The same rule expressed as a program that exits
non-zero is enforced. You will meet this repeatedly: **Day 4's structured output** makes "the model
must return this shape" executable instead of hoped-for; **Day 12's guardrails** make "do not answer
off-topic questions" a check rather than an instruction; **Day 71's eval suite** makes "the agent
behaves correctly" a test that can go red. Part 11 is a specification, `depth_check.py` is its
executable form, and the relationship between the two is the thing to notice.

**What degrades at scale.** A checker that runs over every file on every invocation gets slow, and a
slow check gets skipped. At ninety days times a dozen parts this script finishes instantly; a
repository with ten thousand documents needs incremental checking — only what changed — and caching.
The second pressure is **rule creep**: every incident suggests a new rule, rules accumulate, and
eventually the checker rejects reasonable documents and people start adding exemptions. Mature teams
periodically *delete* rules that no longer earn their false-positive rate, which is a discipline
almost nobody practises.

**The review comment a senior engineer leaves.** On a pull request that adds an exemption to a
linter to make a specific file pass: *"Why is this file special? If the rule is wrong, let's change
the rule for everyone; if the file is wrong, let's fix the file. A one-off exemption is a rule
nobody will remember the reason for."* And on a checker that skips malformed input: *"This passes
when it cannot parse the file — please fail closed, or a corrupt file will read as compliant."*

**The interview question.** *"How do you keep documentation from rotting?"* The weak answer is code
review and good intentions. The one that lands: make as much of the standard executable as you can —
required sections, link validity, frontmatter schema, freshness dates — run it in CI so a violation
blocks the merge, and be explicit that the machine checks presence and shape while humans review
substance. Volunteering the failure mode — *"and you have to watch for rule creep, because a checker
with too many exemptions is worse than none since it looks like coverage"* — is what marks someone
who has actually maintained one.
