# 4.3 — The first commit, and the habit it installs

## One-line answer

The first commit is where the workshop stops being a folder and becomes a project with a history —
and the reason Principle 1 makes a commit the definition of a finished day is that a commit is the
only artifact that is simultaneously a checkpoint you can return to, a record you can search, and
evidence a stranger can read.

---

## The story

Two people spend a weekend learning the same subject.

The first works in a folder. They read, they try things, they overwrite the file when an approach
does not work. By Sunday evening they have one script that does something impressive and a real
understanding of how it works.

The second works in a repository and commits at the end of each session. Same reading, same
experiments, same understanding. Slightly less time on the subject, because committing costs a few
seconds each time.

Six weeks later both are asked, in different interviews, to talk about what they built.

The first describes it. It is a good description — they understood it, and they explain it clearly.
The interviewer nods and moves on, because a description is all there is.

The second opens a repository. There are eleven commits. The messages show the order things were
built. One says *"revert to sequential — the parallel version double-filed tickets on retry"*. The
interviewer stops on that one and asks what happened. The candidate explains the idempotency bug,
what they tried, why they backed it out, and what they would do differently. That conversation lasts
fifteen minutes and is the reason they get the job.

The second person did not do better work. They did the same work, in a form that could be *shown* —
and, more importantly, in a form that let them go back and read what they had actually done rather
than what they remembered doing.

---

## The idea in plain language

**A commit does three separate jobs**, and it is worth naming them individually because people
usually only think of the first:

1. **A checkpoint.** A known-good state you can return to. This is what makes experimenting cheap:
   you can try the risky refactor because getting back costs one command.
2. **A record.** *What changed, when, and why.* The diff answers the first two on its own; the
   message is the only place the third can live. This is the `git blame` archaeology from
   [2.3](../02/2.3-git-init-and-what-a-repo-is.md).
3. **Evidence.** A commit is dated, attributed, and immutable in practice — a claim about what
   existed and when, which is what makes the history the story's fifteen-minute conversation.

**Why a *day* is the unit.** Principle 1 says every day produces runnable, committed code. A day is
neither a keystroke nor a month: it is a chunk small enough to describe in one sentence and large
enough to be worth returning to. That granularity is what makes `git bisect` useful — a regression
that appears on Day 50 can be narrowed to the day that introduced it in about six steps rather than
six hundred.

**What goes in the message.** The subject line says *what*, in the imperative mood, as if completing
the sentence "if applied, this commit will…". The body — separated by a blank line — says *why*,
which is the part the diff cannot show. This project's automated message is `day-NN: complete`,
deliberately plain because the day's own documents carry the detail; a commit you write by hand
should say more.

**Why the ordering inside `./m done` matters.** It regenerates the tracker *before* committing
([4.2](4.2-the-tracker-you-never-hand-edit.md)), so the commit contains a progress file describing
the project as of that commit. Reverse the order and every commit would carry the *previous* day's
progress — off by one, forever, and the history of `docs/TRACKER.md` would be quietly useless.

**And the reason `git add -A` is safe here.** It stages everything, including deletions. That is the
right behaviour for a day's work, and it is only safe because
[`.gitignore` was written first](../02/2.2-gitignore-before-the-secret-exists.md). Without it,
`-A` is precisely the command that commits `.env`.

## Why Mandala needs it

- **Principle 1 is the plan's first rule and the whole enforcement mechanism.** No commit, no day.
  `./m done` is the gate ([3.3](../03/3.3-the-done-gate.md)) and the commit is what it withholds.
- **`docs/TRACKER.md` derives progress from disk** ([4.2](4.2-the-tracker-you-never-hand-edit.md)),
  and what is on disk is what git restored. History and progress are the same artifact, so they
  cannot disagree.
- **Day 64's ADR-003 is a decision you must be able to defend cold.** The bake-off produces a
  scorecard, and the ADR records which architecture you chose and why — committed next to the four
  implementations it compares. That is the story's *"revert to sequential"* commit, written
  deliberately.
- **Day 89 is README-as-portfolio.** Ninety commits with meaningful messages, ninety days of gated
  work, and a set of decision records is the artifact you show. It cannot be assembled at the end;
  it is either accumulated or it does not exist.

## The mechanism

Look at what you are about to commit — always, before every commit:

```bash
git status --short
```

**Line by line:**

- `--short` — one line per file in a compact format. `??` is untracked, `A` staged for addition, `M`
  modified. Compact enough to actually read, which the long form is not once a day's work has piled
  up.
- **Read the list.** This is the last cheap moment to notice a file that should not be there.
  `.env` must not appear ([2.2](../02/2.2-gitignore-before-the-secret-exists.md)); neither should
  `.venv/` or a stray notebook checkpoint.

Then stage and inspect what is staged:

```bash
git add -A
git diff --cached --stat
```

**Line by line:**

- `git add -A` — stage everything: new files, modifications, **and deletions**. The last is the
  reason for `-A` over `git add .`, which in older versions ignored deletions and produced commits
  claiming files still existed.
- `git diff --cached` — show the difference between the **index** and the last commit — that is,
  exactly what a commit would contain right now. `--cached` is the flag that means "staged"; without
  it you are looking at unstaged changes instead, which is a genuinely easy mistake to make.
- `--stat` — a summary: file names and how many lines changed in each, instead of the full text.
  What you are checking here is *shape* — twenty-one files is plausible for Day 0; two hundred means
  something is being committed that should not be.

Now make the commit. For Day 0 you do it through the gate, which is the whole point of having built
one:

```bash
./m done 0
```

**Line by line:**

- Reads `days/day-00-setup/CHECKLIST.md` and refuses if any box is `- [ ]`
  ([3.3](../03/3.3-the-done-gate.md)).
- Runs `./m check` — ruff, formatting, offline pytest, and the depth contract
  ([4.1](4.1-the-depth-check.md)).
- Regenerates `docs/TRACKER.md` ([4.2](4.2-the-tracker-you-never-hand-edit.md)).
- Then, and only then, `git add -A && git commit -m "day-00: complete"`.
- **You do not type `git commit` for a day in this project.** The gate is the path, and a path you
  can step around is not a path.

Read back what you made:

```bash
git log --oneline --stat -1
```

**Line by line:**

- `--oneline` — one line per commit: short hash and subject.
- `--stat` — the file summary for that commit, so you can see what actually landed rather than
  trusting that it did.
- `-1` — just the most recent commit.
- **Read it.** This is the same check as `git diff --cached --stat`, one moment later, and it is the
  cheapest possible confirmation that the commit contains what you meant.

And the check that matters most on a first commit:

```bash
git ls-files | grep -c . && git ls-files | grep -E "^\.env$|^\.venv/" || echo "no secrets tracked"
```

**Line by line:**

- `git ls-files` — every file git is **tracking**, which is a different and more useful question
  than "what is in the folder".
- `grep -c .` — count them. A number in the low tens is right for Day 0.
- `grep -E "^\.env$|^\.venv/"` — search that list for the two things that must never be in it.
  `^\.env$` anchors both ends so it matches `.env` exactly and not `.env.example`; `^\.venv/`
  matches anything under the environment folder.
- `|| echo "no secrets tracked"` — `grep` exits non-zero when it finds nothing, so the `||` branch
  runs on success-by-absence. **This is a check whose passing condition is a failed search**, the
  same inversion as the `done` gate ([3.3](../03/3.3-the-done-gate.md)).

## When it breaks

**The identity refusal, if you skipped [1.2](../01/1.2-git-bash-and-the-carriage-return.md):**

```text
$ ./m done 0
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"
```

**What it means.** Git will not invent an author. Unusually, the error contains the exact fix.

**The empty commit, which is a symptom rather than an error:**

```text
$ ./m done 0
On branch main
nothing to commit, working tree clean
FAIL git commit failed
```

**What it means.** Everything was already committed — you ran `./m done 0` twice, or committed by
hand first. Not damage, but worth noticing: the second run had nothing to record, which means the
tracker regeneration produced no change either, which means the state was already correct.

**The one that is genuinely bad, and the reason for the check above:**

```text
$ git ls-files | grep -E "^\.env$"
.env
```

**What it means.** `.env` is tracked. If it contains a real key and this commit has been pushed
anywhere, **rotate the key now, before anything else** — the fix ordering from
[2.2](../02/2.2-gitignore-before-the-secret-exists.md). Then `git rm --cached .env`, fix
`.gitignore`, and commit. On Day 0 you are almost certainly lucky, because the keys do not exist
until Day 1 — which is exactly why `.gitignore` was written before `git init`.

**The pre-commit hook refusing, which people mistake for a broken commit:**

```text
$ ./m done 0
ruff.....................................................................Failed
- hook id: ruff
- files were modified by this hook

FAIL git commit failed
```

**What it means.** The hook from `.pre-commit-config.yaml` ran, found a lint issue, **fixed it**, and
aborted the commit so you can review the fix. Nothing is broken. Look at the change, then run
`./m done 0` again — the second run commits the corrected files. A hook that modifies files always
fails the first time by design; a hook that silently amended your commit would be far worse.

## In production

**Commit hygiene is a professional signal, and it is read.** Small commits with informative
messages, each one individually runnable, are what make `git bisect`, `git revert` and code review
work at all. The specific failure of a large commit is that it cannot be partially undone: when a
refactor and a bug fix land together and the refactor turns out to be wrong, reverting takes the fix
with it. **"Can I revert this alone?" is the practical test for whether a commit is the right size**,
and it is a better guide than any line-count rule.

**Trunk-based development is the common shape**, and it follows from the same reasoning: short-lived
branches merged into `main` frequently, rather than long branches that diverge for weeks. Long
branches accumulate conflicts and hide work from CI, so problems are found late and all at once.
This project's rhythm — one day, one commit, straight to `main` — is that idea at the smallest
possible scale.

**The commit is where automation attaches.** In a real repository, pushing triggers CI; a merge to
`main` may trigger a deploy; the message may be parsed to generate a changelog or infer a version
bump. This is why teams standardise on conventional prefixes (`feat:`, `fix:`, `docs:`) — not for
tidiness, but because the history becomes machine-readable. **Day 2 wires the CI trigger**, and from
there every commit is checked by something other than you.

**History is evidence, with the properties evidence needs.** Dated, attributed, and tamper-evident:
changing a past commit changes every hash after it
([2.3](../02/2.3-git-init-and-what-a-repo-is.md)). During an incident review, the history answers
"when did this change and who knew about it". In regulated environments, signed commits and
protected branches make that answer admissible rather than merely convenient. And in an interview it
is the story's fifteen-minute conversation.

**What degrades at scale.** A repository with a long history and large files gets slow to clone,
which is why binaries belong in an object store rather than in git
([2.3](../02/2.3-git-init-and-what-a-repo-is.md)). Large teams add shallow clones, partial clones
and monorepo tooling. The one thing that does *not* scale is a convention nobody enforces: commit
message standards survive only when a hook or a CI check verifies them, which is the lesson of
[3.3](../03/3.3-the-done-gate.md) applied to prose.

**The review comment a senior engineer leaves.** On a pull request with one 4,000-line commit:
*"Please split this — the refactor and the bug fix should be separate so we can revert one without
the other."* On a message reading *"fixes"*: *"What was broken and why did this fix it? In six months
this line is the only explanation anyone will have."* And on any commit touching a config file:
*"Confirm no credentials in here — `git ls-files` after the change, please."*

**The interview question.** *"Walk me through a project you built."* The answer is not a description;
it is a repository. What separates candidates is the ability to open the history and say *"this
commit is where I got it wrong, and here is what I learned"* — because that demonstrates judgement,
which is the thing being assessed, in a way that a working demo cannot. **Day 89 exists to make that
possible**, and it is only possible if the commits were made along the way.
