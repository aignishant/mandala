# 1.6 — Docker and Ollama, the two tools you meet before you need them

## One-line answer

Two programs are not needed today and are needed badly later — **Docker**, which gives agent-written
code somewhere to run that is not your laptop, and **Ollama**, which gives you a model that answers
when every free tier has said no — and both are large downloads that you want to have already done
before the day you need them.

---

## The story

Someone is on Day 67 of a ninety-day plan. The subject is sandboxing: the day's whole point is that
code an agent wrote must run somewhere disposable, with no credentials and no network, because you
cannot review every line a model produces before it executes.

They read the lesson. It makes sense. They reach the setup block, which begins by pulling a
container image.

The download is several gigabytes. Their connection is ordinary. The download will not finish
tonight.

So they do what anyone does at that point: they skip the isolation and run the generated code
directly, "just to see it work". It works. The demo passes. They tick the box.

What they have actually learned is the opposite of the day's lesson. They now have a working memory
of agent-written code executing with their own credentials, on their own filesystem, and nothing bad
happening — which is precisely the intuition the day was built to destroy. The blast radius they
were supposed to feel was replaced by a green checkmark.

Nothing in that story is a knowledge failure. It is a *logistics* failure. The tool needed to be
there before the day that needed it, and downloading it was never going to be the interesting part.

---

## The idea in plain language

**Docker, in one paragraph.** A **container** is a process running on your machine with a lie told
to it about what the world looks like: it sees its own filesystem, its own process list, and only
the network you grant it. It is not a virtual machine — there is no second operating system, and
starting one takes a moment rather than a minute — because it shares your kernel and only isolates
what a process can *see*. An **image** is the frozen filesystem a container starts from: a base
operating system, an interpreter, your dependencies, your code. Images are built from a text file
called a **Dockerfile**, which means the environment becomes something you version, review and
reproduce — the same argument as the lockfile in
[1.3](1.3-uv-the-one-binary-that-owns-the-environment.md), one layer further out.

Two properties matter for this project, and they are the two the story lost:

- **Disposable.** A container that is deleted takes everything inside it with it. Code that damages
  a container has damaged something you were going to throw away anyway.
- **Constrained.** You choose what it can reach. No credentials in its environment, no network
  route, one mounted folder and no more. That list is what "blast radius" (Principle 6) means
  concretely rather than as a slogan.

**Ollama, in one paragraph.** Ollama runs a language model on your own machine. You pull a model
once, it lives on your disk, and a local server answers requests with no key, no rate limit and no
network. In exchange, the models small enough to run on an ordinary laptop are meaningfully weaker
than the hosted ones, and they are slower unless you have a capable GPU. That trade — worse answers,
infinite availability — is exactly the right shape for a **fallback**.

Why a fallback matters more here than in most projects: this plan's budget is **$0** (Principle 5),
so the currency is *requests per day*, not dollars. A free tier that is exhausted at 11pm cannot be
topped up at any price. There is no upgrade button, no emergency card. The only thing that turns a
hard stop into a soft degradation is a provider that has no quota at all — and that is the last link
in the chain you build on **Day 6**: Gemini → Groq → OpenRouter → Ollama.

**Neither tool is needed today.** That is the point of meeting them today. Both are large downloads,
Docker on Windows requires a restart, and both have first-run setup steps that are tedious rather
than difficult. Doing that now costs you nothing you were going to spend on learning. Doing it on
Day 67 costs you the lesson.

## Why Mandala needs it

**Docker:**

- **Day 19** — the Agents SDK's native harness and sandbox are a paid-tier feature, so this plan
  teaches the concept and then has you build the free replacement: a local Docker sandbox that a
  long-horizon, file-touching agent runs inside.
- **Day 67 (AG-18)** — sandboxing for real. Agent-written code executes in a disposable container
  with no credentials and minimal network. `rm -rf /` inside a box that dies anyway is a
  demonstration, not an incident.
- **Days 85–88** — deployment is local-first and free: Docker Compose, and the `ticket-db` MCP
  server replicated three times behind a local load balancer to prove the 2026-07-28 spec's
  stateless story actually holds.

**Ollama:**

- **Day 6 (AG-08)** — the shared provider-fallback router with 429-aware backoff. Ollama is its last
  branch, and you cannot write a test for the "everything hosted is exhausted" path against a
  provider that does not exist on your machine.
- **Any evening a free tier runs out.** Which will happen, because the rosters rotate and the limits
  change without notice (`docs/RATE_BUDGET.md` tracks them). A local model means the day continues
  at reduced quality instead of stopping.
- **Day 72 (AG-23) — LLM-as-judge.** The standing rule is *judge ≠ judged*: an evaluation is
  worthless if the model grading the answer is the model that wrote it. A local model is one more
  genuinely independent judge, and one that costs nothing to run over a large eval set.

## The mechanism

**Install Docker Desktop.** Download it from
[docker.com/products/docker-desktop](https://www.docker.com/products/docker-desktop/) and run the
installer. On Windows it will enable WSL 2 (a Linux kernel running alongside Windows) and ask for a
restart. Let it restart now rather than deferring it.

After the restart, launch Docker Desktop once and wait for it to report that the engine is running.
Then, in Git Bash:

```bash
docker --version
docker run --rm hello-world
```

**Line by line:**

- `docker --version` — proves the client is installed and on `PATH`. It can succeed while the engine
  is *not* running, so it is necessary but not sufficient — which is why the second command exists.
- `docker run` — create a container from an image and start it.
- `--rm` — delete the container when it exits. Without this, every run leaves a stopped container
  behind, and a machine accumulates hundreds of them. **Get into the habit now**; it is the flag
  that makes "disposable" true in practice rather than in principle.
- `hello-world` — a tiny official image whose only job is to print a paragraph confirming the whole
  chain worked: the client talked to the engine, the engine pulled an image, created a container,
  and ran it. If this prints, Docker is genuinely working, not merely installed.

Now the command that matters for Day 67 — a container with no network:

```bash
docker run --rm --network none python:3.12-slim python -c "print('isolated')"
```

**Line by line:**

- `--network none` — give this container no network interfaces at all. Not a firewall rule, not a
  blocked port: no route to anywhere. **This one flag is most of what "sandbox" means** on Day 67,
  and it is worth running once today so the idea is concrete rather than theoretical.
- `python:3.12-slim` — the official Python image, `slim` variant (a smaller base with fewer system
  packages). Note the version tag matching
  [1.4](1.4-python-3-12-and-why-nothing-floats.md) — the same interpreter your project pins, because
  developing against one and shipping another is how import errors are discovered in the most
  expensive possible place.
- `python -c "print('isolated')"` — the command to run *inside* the container. Everything before the
  image name configures Docker; everything after it is the container's own command line.
- This pull is a few hundred megabytes. Doing it today is the entire point of this part.

**Install Ollama.** Download it from [ollama.com/download](https://ollama.com/download), install,
and then:

```bash
ollama --version
ollama pull llama3.2:3b
ollama list
```

**Line by line:**

- `ollama --version` — client installed and reachable. Like Docker, Ollama runs a background service
  the client talks to.
- `ollama pull llama3.2:3b` — download a model once, to your disk. The `:3b` is the **parameter
  count** — roughly three billion — which is the main lever on quality, speed and memory. A 3B model
  runs comfortably on an ordinary laptop and is deliberately modest: this is the fallback, not the
  workhorse. If your machine has more memory to spare, an 8B model is a reasonable upgrade; the
  fallback logic on Day 6 does not care which you chose.
- `ollama list` — what you have locally, with sizes on disk. Useful later when you are deciding
  whether to keep a model or reclaim the space.

And prove it answers, because an installed model that has never been asked a question is not yet
evidence of anything:

```bash
ollama run llama3.2:3b "Reply with exactly one word: ready"
```

**Line by line:**

- `ollama run <model> "<prompt>"` — send one prompt, print the answer, exit. With no prompt argument
  it opens an interactive chat instead, which is not what you want in a check.
- The response may not be exactly one word, and that is informative rather than a failure: a small
  local model follows instructions less reliably than a hosted one. **Noticing that gap today is
  useful** — it is the reason Ollama is the *last* branch of the fallback chain and not the first.

## When it breaks

**Docker installed, engine not running:**

```text
$ docker run --rm hello-world
docker: error during connect: Get "http://%2F%2F.%2Fpipe%2FdockerDesktopLinuxEngine/v1.51/...":
open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified.
```

**What it means.** The client is fine; it could not reach the engine. The named pipe in that message
is how the client talks to the Docker daemon on Windows, and it does not exist because the daemon is
not up. Start Docker Desktop and wait for its status to go green. This is the single most common
Docker error on Windows and it says nothing helpful about its own cause.

**Virtualisation disabled in firmware:**

```text
Docker Desktop - Unexpected WSL error
wsl update failed: update failed: updating wsl: exit code: 4294967295
```

**What it means.** WSL 2 needs hardware virtualisation, and on many machines it ships disabled in
the BIOS/UEFI. Check Task Manager → Performance → CPU for "Virtualization: Enabled". If it says
disabled, it is a firmware setting (usually named Intel VT-x, AMD-V, or SVM Mode), not something
Windows can fix. This is worth discovering today rather than on Day 19.

**Ollama out of memory:**

```text
$ ollama run llama3.1:70b "hello"
Error: model requires more system memory (37.0 GiB) than is available (15.4 GiB)
```

**What it means.** Exactly what it says, and it is an honest, useful error — the model's weights must
fit in memory to run. Use a smaller parameter count. This is the concrete form of the trade-off from
*The idea in plain language*: local models are free of quota but bounded by your hardware, and the
bound is not negotiable.

**Ollama service not running:**

```text
$ ollama list
Error: could not connect to ollama app, is it running?
```

**What it means.** Same shape as the Docker error: client present, service absent. Launch the Ollama
application (on Windows it lives in the system tray). On Day 6 your fallback router must treat this
as *just another provider being unavailable* — the local branch failing is a normal condition to
handle, not an exceptional one, and a router that crashes when its last fallback is down has missed
the point of having one.

## In production

**The sandbox is not a nicety; it is the control that makes agent-written code acceptable at all.**
The moment a system executes code a model produced, "review every line before it runs" stops being
possible — that is the whole reason the model is writing it. What replaces review is *containment*:
no credentials in the environment, no network unless explicitly granted, a read-only mount for
inputs, a hard resource limit, and a lifetime measured in the length of one task. Production systems
add layers you will not build here — gVisor or Firecracker microVMs for kernel-level isolation, a
separate account or project so a compromise cannot reach your other infrastructure — but the
*reasoning* is identical to `--network none`, and you will meet it as **the lethal trifecta on
Day 65**: private data, untrusted input, and the ability to act externally must never meet in one
agent.

**A local model is a real architectural component, not a toy.** Teams run local or self-hosted
models for reasons that have nothing to do with cost: data that legally cannot leave the building,
latency budgets a network round trip cannot meet, or an availability requirement no third-party API
will underwrite. In this project the reason is quota, but the *pattern* — a tiered chain from best
to always-available, chosen per request — is the same one production systems use, and it is what you
build on Day 6.

**Free tiers change the shape of the failure.** A paid API degrades gracefully under load; a free
tier stops dead. That difference is why the router on Day 6 must distinguish a **429** (rate
limited — back off and retry, this provider will return) from a **quota exhausted for the day**
(do not retry, move down the chain) from a **model id that no longer exists** (a plan amendment,
because the roster rotated). Treating all three as "an error" produces a system that hammers a
provider that will not answer until tomorrow.

**What degrades at scale.** Container startup, which is negligible for one demo, becomes the
dominant cost when every tool call runs in a fresh sandbox. Real systems respond with pooled warm
containers, a per-image cache, and hard caps on concurrent sandboxes — and each of those
optimisations weakens isolation slightly, which is a trade you must be able to state out loud rather
than stumble into. Similarly, one local model on a laptop is free; a fleet serving many users is a
GPU capacity problem with a real budget attached.

**The review comment a senior engineer leaves.** On a pull request that runs generated code with
`subprocess.run(...)`: *"This executes model output on the host with our credentials in the
environment. It needs to go in a container with `--network none` and no secrets mounted — and the
PR should say what the blast radius is if the model is prompt-injected."* And on a `docker run`
without `--rm` in a loop: *"This leaks a container per iteration; add `--rm` or we will fill the
disk."*

**The interview question.** *"An agent in your system writes and executes Python. How do you make
that safe?"* The answer they want is not "we prompt it not to do bad things". It is: the code runs
in a disposable container with no credentials, no network unless a specific host is required,
read-only inputs, a resource cap, a lifetime bounded by the task — and, crucially, that the design
assumes the model *will* eventually be induced to write something hostile, because the input it
reads is untrusted. Saying "we assume it will be prompt-injected and design for containment rather
than prevention" is the sentence that ends this question well.
