# 1.3 — `uv`, the one binary that owns the environment

## One-line answer

`uv` is a single program that does the four jobs Python normally splits across four tools —
installing interpreters, creating the environment, resolving and locking dependencies, and running
your code inside that environment — which is what makes "which environment am I in?" stop being a
question you can get wrong.

---

## The story

A team keeps a `requirements.txt`. It is honest work: someone wrote down the packages the project
needs, one per line, with versions.

A new hire clones the repository on a Tuesday and runs the install. It succeeds. The tests fail.

Not dramatically — one test, comparing two floating-point numbers, off in the sixth decimal place.
Everyone else's machine passes. The new hire's does not.

Two days later somebody finally diffs the *installed* packages rather than the requested ones. The
requirements file listed twelve packages. The environment contained sixty-one. The other forty-nine
arrived as dependencies-of-dependencies, and the file said nothing about them — so each machine got
whatever was newest on the day it installed. One of those forty-nine had shipped a new release three
weeks earlier that changed a default rounding mode.

Nobody had done anything wrong. The requirements file recorded *intent*. It did not record
*outcome*. The environment that produced the passing tests had never been written down anywhere, so
it could not be reproduced — only re-approximated, differently, on every machine.

That gap between "what I asked for" and "what I got" is the thing a lockfile closes, and it is the
main reason this project uses `uv` rather than the tools most tutorials reach for.

---

## The idea in plain language

Traditionally, four different programs handle four jobs:

| Job | Traditional tool |
|---|---|
| Get a Python interpreter onto the machine | the python.org installer, `pyenv`, a distribution |
| Create an isolated environment | `python -m venv`, `virtualenv`, `conda` |
| Install and resolve packages | `pip`, plus `pip-tools` or `poetry` for locking |
| Run your code in that environment | "activate" the venv, then type `python` |

Four tools means four places for the answer to "which environment is this?" to diverge — which is
exactly the failure from [1.1](1.1-why-one-tool-must-own-the-environment.md).

`uv` does all four. It is one executable file, written in Rust, with no Python of its own to
bootstrap. That last detail is not trivia: `pip` is a Python program, so it needs a Python to run,
which means the tool that manages your interpreters depends on having an interpreter — a circularity
that produces some of the strangest errors in the ecosystem. `uv` has no such loop.

Three ideas are worth naming properly before you type anything.

**A dependency resolver.** When you ask for two packages, each of which wants a third at different
version ranges, something must find a set of versions that satisfies everyone simultaneously. That
search is genuinely hard, and doing it *fast* is most of why `uv` feels different from what you may
have used before.

**A lockfile.** Your `pyproject.toml` records what you *asked for* — "crewai, exactly 1.15.6". The
lockfile (`uv.lock`) records what you *got* — every package in the resolved tree, transitive
dependencies included, at exact versions, with cryptographic hashes of the files. It is the answer
to the story: intent in one file, outcome in another, both committed. You meet it properly in
[2.4](../02/2.4-uv-init-pyproject-and-the-lockfile.md).

**A run command that guarantees the environment.** `uv run python foo.py` does something subtly
different from typing `python foo.py`: before running anything, it checks that the environment
matches the lockfile, fixes it if not, and *then* executes — inside that environment, without
"activating" anything. There is no `PATH` lottery because `PATH` is not consulted. This is why every
command in these ninety days starts with `uv run`.

There is a fourth idea that only matters because of where this particular project lives.

**Hardlinks, and why yours are disabled.** To avoid storing the same package a hundred times, `uv`
keeps one global cache and creates **hardlinks** from it into each project's environment. A hardlink
is a second name for the same bytes on disk — nearly free, instant, no copying. It only works
*within* one filesystem, and some filesystems refuse it entirely. Cloud-synced folders are the
common case: OneDrive, Dropbox and iCloud Drive keep files as placeholders that may not be fully on
your disk, and a hardlink to a file that is not really there is not a thing they can make. When that
happens `uv` fails loudly rather than silently doing something wrong, and the fix is to tell it to
copy instead. **This repository lives in a OneDrive folder, so it is configured to copy** — see
*When it breaks*.

## Why Mandala needs it

- **Principle 4 — pin everything — is unenforceable without a lockfile.** "Pinned" means the
  transitive tree is pinned too. `uv add crewai==1.15.6` writes the pin *and* regenerates the lock
  in one command, so the two cannot drift apart.
- **Four frameworks, one environment.** By Day 62 this repository has the Agents SDK, CrewAI,
  LangChain and LangGraph installed together, and they share dependencies with overlapping version
  requirements. That is a genuinely hard resolution problem, and it is the reason the bake-off in
  Phase 9 is possible at all: all four run against one locked environment, so a difference between
  them is a real difference and not an artifact of four separate installs.
- **`./m check` runs everything through `uv run`.** Lint, format, tests and the depth check all
  execute in the locked environment, so a green check means green *in the environment the lockfile
  describes* — not in whatever your `PATH` happened to point at.
- **Day 19 and Day 85 build container images.** A Dockerfile that installs from a lockfile produces
  the same image every time; one that installs from a loose requirements file produces a new lottery
  ticket on every build. The sandbox on Day 67 is only meaningful if you can say exactly what is
  inside it.

## The mechanism

**Install `uv`.** In Git Bash:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

**Line by line:**

- `curl` — fetch something over HTTP and, by default, print it to the screen.
- `-L` — follow redirects. The short URL redirects to the real script; without this you download the
  redirect notice instead of the script.
- `-s` — silent: no progress meter, so only the script itself reaches the pipe.
- `-S` — show errors anyway. `-s` alone would also hide the failure message, which is how people end
  up piping an error page into a shell. `-sS` together means "quiet on success, loud on failure".
- `-f` — fail on an HTTP error status instead of cheerfully saving the error page as if it were the
  file. **This is the flag that makes the pipe safe.**
- `| sh` — run what was downloaded. Piping a URL into a shell deserves the suspicion it usually
  gets; it is acceptable here because the host is the tool's official domain over HTTPS, and it is
  the installation method the tool documents. If you would rather read before running, drop the
  `| sh`, read the script, then run it.

Windows users who prefer PowerShell can instead run
`powershell -c "irm https://astral.sh/uv/install.ps1 | iex"`, and macOS users with Homebrew can run
`brew install uv`. All three end in the same place.

**Close Git Bash and open it again**, then:

```bash
uv --version
which uv
```

**Line by line:**

- `uv --version` — proves the binary is installed *and* on this shell's `PATH`. The reopen matters:
  the installer appends to your shell's startup file, and a shell that is already running does not
  re-read it. "Command not found immediately after installing" is nearly always this, not a failed
  install.
- `which uv` — from [1.1](1.1-why-one-tool-must-own-the-environment.md): shows *which* file you
  would get. Expect something under your home directory — `uv` installs per-user and needs no
  administrator rights, which is why it works on locked-down work laptops.

**Install a Python interpreter with it.** This is the job that used to need a separate installer:

```bash
uv python install 3.12
uv python list
```

**Line by line:**

- `uv python install 3.12` — downloads a standalone build of CPython 3.12 into `uv`'s own directory.
  It does not touch your system Python, does not modify `PATH`, and does not need administrator
  rights. If you already have a 3.12, `uv` will find and reuse it rather than duplicating.
- `uv python list` — every interpreter `uv` knows about, downloaded or discovered on your system.
  Compare it against the `which -a python` output from
  [1.1](1.1-why-one-tool-must-own-the-environment.md): `uv`'s list is the *managed* set, and the
  point is that from here on you only care about that one.
- `3.12` and not `3.12.7` — a request for "the latest 3.12.x". The exact patch version is pinned in
  the lockfile, not in this command. Why 3.12 rather than 3.13 is [1.4](1.4-python-3-12-and-why-nothing-floats.md).

**The four commands you will actually type for ninety days:**

```bash
uv sync
uv add "package==1.2.3"
uv run python script.py
uv run pytest
```

**Line by line:**

- `uv sync` — read `pyproject.toml` and `uv.lock`, and make `.venv/` match them exactly. It installs
  what is missing **and removes what should not be there** — that second half is what makes it a
  *sync* rather than an install, and it is what stops an environment drifting as a project changes.
- `uv add "package==1.2.3"` — resolve, install, write the pin into `pyproject.toml`, and update
  `uv.lock`, as one atomic step. The quotes protect `==` from the shell. **This is the only way
  packages enter this project** (Principle 4); a bare `pip install` would install a package that no
  file records, which is precisely the story.
- `uv run python script.py` — verify the environment against the lockfile, then run. No activation,
  no `PATH` question, no possibility of running against a stale environment.
- `uv run pytest` — the same guarantee for tests. This is the difference between "the tests passed"
  and "the tests passed against the code I actually have".

## When it breaks

**The one you will hit in this repository, because it lives in OneDrive:**

```text
$ uv run python -c "print('hi')"
  × Failed to build `mandala @ file:///C:/Users/me/OneDrive/Desktop/Projects/mandala`
  ├─▶ Failed to install: pluggy-1.6.0-py3-none-any.whl (pluggy==1.6.0)
  ╰─▶ failed to hardlink file from
      C:\Users\me\AppData\Local\uv\cache\builds-v0\.tmpUMLAEU\Lib\site-packages\pluggy\_warnings.py
      to
      C:\Users\me\AppData\Local\uv\cache\archive-v0\Eyka5mLP_I_HmcqB\pluggy\_warnings.py:
      The cloud operation cannot be performed on a file with incompatible
      hardlinks. (os error 396)
```

**What it means.** Read the last line, not the first. "The cloud operation cannot be performed"
is OneDrive speaking, not Python and not `uv`. `uv` tried to hardlink from its cache into the
project, and the cloud-synced filesystem refused. Nothing is corrupt and nothing is misconfigured
about Python — the filesystem simply does not support the operation `uv` prefers.

**The smallest fix** is to tell `uv` to copy for this one command:

```text
$ UV_LINK_MODE=copy uv run python -c "print('hi')"
```

**The durable fix** — and the one this repository ships — is in `pyproject.toml`, so it applies to
every command and to anyone who clones:

```toml
[tool.uv]
link-mode = "copy"
```

Copying is slower than hardlinking and completely correct. If you would rather have the speed, the
real answer is to move the project out of the synced folder entirely, which is what most people do
once they have hit this twice.

**The one that looks like a `uv` bug and is not:**

```text
$ uv add "crewai==1.15.6"
  × No solution found when resolving dependencies:
  ╰─▶ Because langchain-core==1.6.0 depends on pydantic>=2.14 and crewai==1.15.6 depends on
      pydantic<2.13, we can conclude that crewai==1.15.6 and langchain-core==1.6.0 are
      incompatible.
```

**What it means.** This is the resolver reporting, correctly, that **no set of versions satisfies
everyone at once**. Read it as a proof, because that is what it is: it names both constraints and
the package they collide on. The instinct to loosen a pin and move on is exactly wrong here — under
Principle 14, a genuine version conflict between two pinned frameworks is *ecosystem reality
disagreeing with the plan*, and it goes into `docs/CHANGELOG_PLAN.md` as an amendment before any
version changes. Silently unpinning to make an error disappear is how a project ends up back in the
story at the top of this page.

**The one that follows an install:**

```text
$ uv --version
bash: uv: command not found
```

**What it means.** Almost always that this shell was open before the installer ran, so its `PATH`
does not include the new directory yet. Close it, open a new one, try again. If it persists, the
installer told you which line to add to your shell startup file — read its output rather than
guessing.

## In production

**The lockfile is the deployable artifact, not the `pyproject.toml`.** A production Dockerfile does
not run `uv add`; it copies `pyproject.toml` and `uv.lock` in, runs `uv sync --frozen`, and stops.
`--frozen` means "install exactly the lockfile, and **fail** if it does not match `pyproject.toml`"
— turning a silent re-resolution into a loud build failure. That distinction is the whole point: a
build that quietly re-resolves is a build that can differ from the one you tested, with no commit in
between. You write this Dockerfile on **Day 19**.

**Hashes in the lockfile are a supply-chain control.** `uv.lock` records a cryptographic hash of
every file it installs, so a package that is republished under the same version number — whether by
accident or by an attacker who has compromised a maintainer account — produces a hash mismatch and a
failed install rather than a silent substitution. This is not hypothetical; typosquatted and
hijacked packages are a routine attack on Python projects. **On Day 66 you will apply exactly this
thinking to third-party MCP servers**, and it is the same question in a different costume: what
exactly am I running, and how do I know it has not changed?

**`uv run` in CI is what makes a green build mean something.** Every step in
`.github/workflows/check.yml` goes through `uv run`, so CI executes against the locked environment
rather than whatever the runner image happens to ship. A CI job that installs loosely is a job that
can pass on Monday and fail on Tuesday with no commit in between — and when that happens, people
stop trusting the build, which costs far more than the failure did.

**What degrades at scale.** With one project, install speed is a convenience. With a monorepo of
forty services and a CI matrix across three Python versions, dependency resolution is a measurable
share of engineering time and cloud spend, and cache behaviour becomes an operational concern:
where the cache lives, whether runners share it, whether it is warm. Teams do migrate package
managers over exactly this, and the honest framing is that the resolver's *speed* is what makes the
resolver's *strictness* affordable — nobody keeps a discipline that makes every build slow.

**The review comment a senior engineer leaves.** On a pull request that changes `pyproject.toml`
without `uv.lock`: *"Lockfile not updated — this PR changes what we ask for but not what we get,
so CI is testing a different environment than production will run."* And on a Dockerfile with
`uv sync` where `uv sync --frozen` belongs: *"Use `--frozen` here; otherwise a stale lockfile
silently re-resolves at build time and the image stops matching the commit."*

**The interview question.** *"What is the difference between a `requirements.txt` and a lockfile,
and why do you need both?"* The answer they are listening for is **intent versus outcome**: the
manifest records the versions a human chose and the constraints they care about, the lockfile
records the complete resolved tree including transitive dependencies, at exact versions, with
hashes. The follow-up is usually *"so why commit both?"* — because the manifest is what you edit and
review, and the lockfile is what you reproduce and audit. Anyone who has debugged the story at the
top of this page answers this immediately.
