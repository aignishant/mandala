# 1.4 — Python 3.12, and why nothing in this project floats

## One-line answer

This project runs on Python **3.12** and says so in a file, because 3.12 is the version every one of
the four agent frameworks supports simultaneously — and a project that does not *state* its
interpreter version has not chosen one, it has merely not noticed yet.

---

## The story

An engineer picks up a project that has been quiet for eight months. The README says "Python 3".
They have 3.13 installed, so they use it. The install runs for a while and then stops:

```text
ERROR: Could not find a version that satisfies the requirement tensorflow
```

They search the error. Nothing helpful. The package exists — they can see it on the index, they can
open its page, it has recent releases. The error says no version satisfies the requirement, and they
have specified no requirement at all.

What they eventually learn is that Python packages containing compiled code are published as
pre-built files, one per platform *and per Python version*. The package had not yet published a
build for 3.13. So from the installer's point of view there genuinely was no candidate: it looked
for "a version of this package compatible with the interpreter you are using", found none, and said
so — accurately, and in the least helpful phrasing available.

The fix was to use 3.12. The cost was the afternoon, and a lingering sense that the ecosystem is
capricious.

It is not capricious. It is *specific*, and this project's answer is to be specific back: name the
version, write it down, let the tooling refuse anything else.

---

## The idea in plain language

**A Python version is not cosmetic.** Each minor release — 3.11, 3.12, 3.13 — changes the internal
interfaces that compiled extension modules build against. Any package with C, C++ or Rust inside it
(and in this project that includes PyTorch, the vector store, and much of what CrewAI pulls in) must
be compiled separately for each one. Those pre-built files are called **wheels**, and a wheel names
the Python versions it fits. No matching wheel means either building from source — slow, and it
needs a compiler — or the flat refusal from the story.

So a new Python release is *ahead* of the ecosystem, not behind it. The newest version is the one
with the fewest wheels available, which reverses the usual instinct that newer is safer.

**Version numbers carry meaning.** Most Python packages follow **semantic versioning**:
`MAJOR.MINOR.PATCH`, where a patch bump promises bug fixes only, a minor bump promises new features
that do not break existing code, and a major bump is permitted to break things. It is a promise, not
a guarantee — plenty of "minor" releases have broken plenty of code — but it tells you how much to
worry about a given change, and it is why the freshness check on Friday (Principle 13) treats a
patch drift and a major drift completely differently.

**Constraint operators say how much you will accept.** The ones you will meet:

| Operator | Means | Example |
|---|---|---|
| `==1.2.3` | exactly this | `crewai==1.15.6` |
| `>=1.2` | this or anything newer | `pydantic>=2.0` |
| `~=1.2.3` | "compatible release": ≥1.2.3, <1.3.0 | `httpx~=0.28.1` |
| `==3.12.*` | any patch of this minor | `requires-python = "==3.12.*"` |

**This project uses `==` everywhere** (Principle 4). Not because the others are wrong in general —
a *library* published for others to use should accept ranges, or it becomes impossible to install
alongside anything else — but because an *application* that pins loosely has volunteered to be
broken by someone else's release schedule, on a day it did not choose.

The interpreter itself gets `==3.12.*`, one step looser than the packages, and deliberately so: a
patch release of Python contains security fixes and no ABI changes, so accepting 3.12.7 through
3.12.11 costs nothing and gains the fixes. The *minor* version is what is nailed down, because the
minor version is what the wheels care about.

**And why 3.12 specifically for this project?** It is the intersection. The four frameworks have
overlapping but not identical support windows: the OpenAI Agents SDK has dropped older versions from
below, while parts of the wider stack cap out from above. 3.12 sits inside every window at once,
which is what makes a single environment running all four possible — and Phase 9's bake-off, where
the same slice is built four ways and compared, depends entirely on that being true.

---

## Why Mandala needs it

- **Phase 9 (Days 59–64) is only meaningful in one environment.** You build the same triage slice on
  all four frameworks and score them side by side. If each framework needed its own interpreter, a
  difference between them could be an artifact of four different installs rather than a real
  difference in the framework. One version, one environment, one comparison.
- **Day 46 installs `sentence-transformers`, which brings PyTorch.** That is the single most
  version-sensitive install in the ninety days, and it is the one most likely to have no wheel for a
  too-new interpreter. Choosing 3.12 today is what makes that day boring.
- **Day 19 and Day 85 build container images.** A Dockerfile starts `FROM python:3.12-slim`. That
  tag must match `requires-python`, or you will develop against one interpreter and ship another —
  and the difference will surface as an import error in a container, which is the most expensive
  place to find it.
- **Principle 4 has no exceptions.** A project that pins sixty packages exactly and leaves the
  interpreter unstated has left the largest variable of all floating.

## The mechanism

You installed 3.12 in [1.3](1.3-uv-the-one-binary-that-owns-the-environment.md). Now confirm what
`uv` will actually give this project:

```bash
uv python list --only-installed
```

**Line by line:**

- `uv python list` — every interpreter `uv` knows about, whether it downloaded them or found them
  already on your system.
- `--only-installed` — hide the ones it *could* download and show only what is present. Without it
  the list is long and mixes "have" with "could have", which is the wrong question when you are
  checking your own machine.
- You want at least one `cpython-3.12.x` row. `cpython` is the standard implementation — the one
  everything in this project is built against, as opposed to alternatives like PyPy.

Now state the requirement in the project file. This line already exists in this repository's
`pyproject.toml`; open it and read it rather than typing it again:

```toml
[project]
requires-python = "==3.12.*"
```

**Line by line:**

- `[project]` — the standard section of `pyproject.toml` describing the project itself. Standard
  matters here: this is not `uv`-specific, so any conforming tool reads it the same way.
- `requires-python` — the interpreter versions this project declares itself compatible with. `uv`
  reads it when choosing which Python to build the environment on, and refuses if it cannot satisfy
  it.
- `"==3.12.*"` — any patch release of 3.12, and nothing else. Not `>=3.12`, which would silently
  accept 3.13 the moment it is present and reintroduce the story. Not `==3.12.7`, which would refuse
  a security patch for no benefit. The `*` is doing exactly one job: allowing the digits that cannot
  hurt you.

Prove it end to end, from inside the environment:

```bash
uv run python -c "import sys; print(sys.version); print(sys.version_info[:2])"
```

**Line by line:**

- `uv run` — from [1.3](1.3-uv-the-one-binary-that-owns-the-environment.md): sync the environment
  against the lockfile, then execute inside it. This is the version your *code* sees, which is the
  only version that matters.
- `sys.version` — the full string, including the build date and compiler. Long, and useful when you
  are comparing two machines that "both have 3.12".
- `sys.version_info[:2]` — the version as a tuple, sliced to major and minor: `(3, 12)`. This is the
  form you compare in code, because comparing version *strings* sorts `"3.9"` after `"3.12"` and
  produces a bug that only appears once a year.

And see what a wheel actually declares, since that is the thing the story turned on:

```bash
uv run python -c "import sysconfig; print(sysconfig.get_platform()); import sys; print(f'cp{sys.version_info.major}{sys.version_info.minor}')"
```

**Line by line:**

- `sysconfig.get_platform()` — the platform tag, something like `win-amd64`. Half of what a wheel
  filename encodes.
- `f'cp{major}{minor}'` — the interpreter tag, `cp312`. The other half.
- Together these two strings are why a file named
  `torch-2.13.0-cp312-cp312-win_amd64.whl` will install for you and
  `torch-2.13.0-cp313-cp313-win_amd64.whl` will not. **The story's `Could not find a version that
  satisfies the requirement` was this comparison failing**, expressed in the least informative way
  the tool had available.

## When it breaks

**The version mismatch, as `uv` reports it:**

```text
$ uv sync
  × No interpreter found for Python ==3.12.* in managed installations or search path
```

**What it means.** `pyproject.toml` demands 3.12 and no 3.12 is available. This is the *good*
failure — loud, immediate, and naming the constraint it could not satisfy, rather than quietly
building on 3.13 and failing later inside a package you have never heard of. Fix it with
`uv python install 3.12`.

**The one from the story, on a fresh machine:**

```text
$ pip install torch
ERROR: Could not find a version that satisfies the requirement torch (from versions: none)
ERROR: No matching distribution found for torch
```

**What it means.** `(from versions: none)` is the tell, and it is easy to misread as "this package
does not exist". It means "no *candidate* matched your interpreter and platform". The package is
fine. Your interpreter is too new, or your platform has no wheel. Check
`python -c "import sys; print(sys.version_info)"` first, every time — it is a five-second question
that answers most of these.

**The one that wastes the most time, because it looks like success:**

```text
$ python --version
Python 3.12.7

$ uv run python --version
Python 3.12.7
```

Both say 3.12.7 — and they can still be different interpreters with different `site-packages`, which
is the entire lesson of [1.1](1.1-why-one-tool-must-own-the-environment.md). The version number is
not an identity. If you need to know *which* Python, ask for the path:

```text
$ uv run python -c "import sys; print(sys.executable)"
C:\Users\me\OneDrive\Desktop\Projects\mandala\.venv\Scripts\python.exe
```

That path — inside this project's `.venv` — is the correct answer. Anything else means `uv run` is
not doing what you think, and you should stop and find out why before installing anything.

## In production

**The interpreter version is part of your deployable, and it is pinned in three places.** In a real
service you will find `requires-python` in `pyproject.toml`, a base image tag in the Dockerfile
(`FROM python:3.12-slim`), and a version matrix in CI. Those three drifting apart is a common and
genuinely nasty bug class: tests pass on 3.12 in CI, the image is built on 3.11 because someone
updated one file and not the others, and the difference surfaces in production as an import error or
— worse — as behaviour that differs subtly rather than failing.

**Upgrading Python is a project, not a chore.** Teams typically run one minor version behind the
newest on purpose, and the upgrade is planned: check every dependency for wheels, run the suite on
the new version in CI *alongside* the old one, then cut over. "We are on 3.12 because 3.13 does not
have wheels for two of our dependencies yet" is a completely respectable answer in a design review,
and being able to give a *reason* rather than a shrug is the point.

**Why applications pin and libraries do not.** If this project were a library that others installed,
`crewai==1.15.6` would make it uninstallable alongside anything else wanting a different CrewAI. The
distinction professionals hold is: **libraries declare ranges, applications pin exactly, and the
lockfile is what makes exact pinning survivable.** This project is an application, so it pins.

**Free-tier reality adds one more edge.** Where the lockfile pins every package, the *models* this
project calls are not in any lockfile — a provider can retire a model id or rotate a free roster
without notice, and no amount of package pinning helps. That is why Principle 4 says *every agent
sets `model=` explicitly*: it makes the model an auditable value in your code rather than a
framework default that can move under you, so when a provider changes something you get a clear
failure naming the model, not a silent change in behaviour. **Day 6 builds the fallback router that
turns that failure into a degraded-but-working system.**

**The review comment a senior engineer leaves.** On a `pyproject.toml` with `requires-python =
">=3.9"`: *"Do we actually test on 3.9? If not, this is a claim we cannot back — narrow it to what
CI runs."* And on a Dockerfile using `FROM python:latest`: *"Pin the tag. `latest` means the image
changes under us with no commit, and the first time it moves a minor version we will find out in
production."*

**The interview question.** *"How do you decide which Python version a new project targets?"* A
junior answer is "the newest". The answer that lands names the constraint: the intersection of what
your dependencies actually ship wheels for, biased one version behind the newest release, then
written down in `requires-python`, the base image tag, and the CI matrix so the three cannot drift.
Mentioning that a new release is *ahead* of the ecosystem rather than behind it — that newest means
fewest wheels — is the sentence that shows you have lived through it.
