# 1.5 — The editor, and the interpreter it silently picks

## One-line answer

Your editor runs a Python interpreter of its own choosing to power autocomplete, error squiggles and
the Run button — and unless you point it at this project's `.venv`, it will be analysing a different
environment than the one your code actually runs in, and lying to you in both directions.

---

## The story

A developer is halfway through a feature. The editor is showing a red squiggle under a line that
imports a package. The message says the module cannot be resolved. They have installed it — they
watched it install.

They ignore the squiggle, because the code runs fine from the terminal. Sensible. Annoying, but
sensible.

Two hours later they add a call to a function that does not exist. No squiggle. Autocomplete even
offered the name. They run it and it fails.

Now they are in the worst possible position: the editor's opinion is uncorrelated with reality, so
they have learned to ignore it — which means the editor has stopped being able to help them at all.
Every genuine error it catches from now on will also be ignored, because they have trained
themselves to treat its output as noise.

The cause was one setting. The editor had picked a Python from the system when the folder was first
opened and never revisited the choice. It was analysing that interpreter's packages: it could not
see the package they had installed into the project, and it *could* see an older version of another
package with a function signature that had since changed.

The editor was not broken. It was answering a different question, accurately, all afternoon.

---

## The idea in plain language

An editor with Python support is running a **language server** — a separate program that reads your
code and answers questions about it: what does this name refer to, what attributes does this object
have, is this call's argument list valid. This is what produces autocomplete, go-to-definition,
inline type errors and refactoring.

To answer any of those questions the language server needs to know *which packages exist*, which
means it needs an interpreter — specifically, it needs the `site-packages` folder belonging to one
([1.1](1.1-why-one-tool-must-own-the-environment.md)). Editors therefore keep a per-folder setting
usually called the **interpreter path** or **Python interpreter**, and they guess it when you first
open a folder.

The guess is usually right and occasionally catastrophic, and the failure is asymmetric in a way
worth naming:

- **Analysing an environment with too few packages** produces false alarms — squiggles under working
  code. Irritating, but honest: you notice immediately.
- **Analysing an environment with different versions** produces false *silence* — no warning on code
  that will fail. This is the dangerous one, because the absence of a warning is indistinguishable
  from correctness.

Both come from the same cause, and both are fixed by one act: **point the editor at
`.venv`** — the environment `uv` built for this project
([2.5](../02/2.5-the-venv-you-never-activate.md) explains what that folder is).

Two more pieces are worth having in place before Day 1, because they change what the editor is *for*:

**A linter** reads your code without running it and reports likely mistakes — an unused import, a
name that does not exist, a mutable default argument. This project uses `ruff`, which does this
plus formatting, and `./m check` runs it. Having the same linter live in your editor means you see a
violation as you type rather than at commit time. **Same tool, same config, two moments** — that is
the whole idea. An editor running a *different* linter than CI is a machine for generating arguments
you cannot win.

**A formatter** rewrites your code into a canonical shape — where the line breaks go, how many
spaces, whether that dictionary is one line or five. The value is not beauty; it is that formatting
stops being a thing anyone thinks about or comments on in review, and diffs stop containing changes
nobody made. `ruff format` does it, `./m check` verifies it, and setting your editor to format on
save means you never see the check fail for it.

There is one more caution specific to this repository. `ruff` can also format Python **inside
Markdown code blocks**. These lessons are full of Python inside Markdown, written deliberately —
aligned comments, `TODO(me)` markers, code that is *supposed* to be wrong so you can watch it fail.
Left alone, `ruff format` would rewrite all of it. So `pyproject.toml` excludes `*.md` from
formatting, and if you enable format-on-save for Markdown in your editor you will undo that
protection file by file.

---

## Why Mandala needs it

- **Day 3 writes a raw agent loop against a provider SDK.** Autocomplete over that SDK is the
  difference between reading the source and guessing at parameter names — but only if the language
  server can see the installed package.
- **Day 11 and Day 26 use structured output with typed models.** The entire benefit of a typed
  contract is that mistakes are visible *before* you spend a model call finding them. That benefit
  is delivered by the language server, and it is zero if the server is analysing the wrong
  environment.
- **Rate limits are the budget (Principle 5).** Every avoidable runtime failure — a typo'd
  parameter, a wrong attribute name — costs a request against a free tier you cannot top up. An
  editor wired to the right environment converts a class of quota-burning failures into red
  squiggles that cost nothing.
- **`./m check` must stay green.** It runs `ruff check` and `ruff format --check`. If your editor
  runs the same tool with the same configuration, the check never surprises you.

## The mechanism

Any editor works; the instructions below are for VS Code because it is the most common. The
*principle* — point the tooling at `.venv` — is identical everywhere.

**Install the two extensions.** In VS Code, open the Extensions panel and install:

- **Python** (publisher: Microsoft) — brings the language server, the interpreter picker, and test
  discovery.
- **Ruff** (publisher: Astral) — the linter and formatter this project uses, so the editor and
  `./m check` agree.

**Then point it at this project's interpreter.** Open the project folder, press `Ctrl+Shift+P`, run
**Python: Select Interpreter**, and choose the entry whose path ends in
`.venv\Scripts\python.exe` (on macOS or Linux, `.venv/bin/python`). VS Code usually offers it with a
`('.venv')` label.

Rather than trusting the picker, write the setting down where you can read it. This project already
contains the file below; open it and check it matches:

```json
{
  "python.defaultInterpreterPath": "${workspaceFolder}/.venv/Scripts/python.exe",
  "python.terminal.activateEnvironment": false,
  "editor.formatOnSave": true,
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff",
    "editor.codeActionsOnSave": { "source.organizeImports.ruff": "explicit" }
  },
  "[markdown]": {
    "editor.formatOnSave": false
  },
  "files.eol": "\n"
}
```

**Line by line:**

- `python.defaultInterpreterPath` — the interpreter the language server analyses. `${workspaceFolder}`
  expands to this project's folder, so the setting is portable: it works for anyone who clones the
  repository, on any machine, without editing an absolute path. On macOS or Linux the tail is
  `.venv/bin/python`.
- `python.terminal.activateEnvironment: false` — stops the editor auto-activating the venv in every
  terminal it opens. This project never activates ([2.5](../02/2.5-the-venv-you-never-activate.md));
  every command goes through `uv run`, which is explicit. Letting the editor activate silently means
  a command sometimes works because of a hidden `PATH` change, which is exactly the ambiguity Day 0
  exists to remove.
- `editor.formatOnSave: true` — format when you save, so `ruff format --check` in `./m check` never
  fails for a reason you could not see.
- `"[python]"` — a **language-scoped block**: everything inside applies only to Python files. This
  is what lets Markdown keep different rules two lines further down.
- `editor.defaultFormatter: charliermarsh.ruff` — name the formatter explicitly. With more than one
  formatter installed, an unspecified default is chosen for you, and it may not be the one CI runs.
- `source.organizeImports.ruff: explicit` — sort and de-duplicate imports on save. `ruff check`'s
  `I` rule set (enabled in `pyproject.toml`) enforces import order, so doing it on save means you
  never see that error.
- `"[markdown]": { "editor.formatOnSave": false }` — **the important one for this repository.** It
  stops the editor reformatting the Python inside these lessons, which is written to be read, not to
  satisfy a formatter.
- `files.eol: "\n"` — save with LF line endings, matching
  [1.2](1.2-git-bash-and-the-carriage-return.md) and `.gitattributes`. Without it, an editor on
  Windows will happily write CRLF into `m` and break it.

**Now verify the editor and the terminal agree**, which is the only check that matters. In the
editor's integrated terminal:

```bash
uv run python -c "import sys; print(sys.executable)"
```

**Line by line:**

- This is the same command from [1.3](1.3-uv-the-one-binary-that-owns-the-environment.md), run from
  inside the editor rather than a standalone shell.
- Compare its output against the interpreter shown in VS Code's status bar. **They must be the same
  path.** If they differ, the language server is analysing one environment while your code runs in
  another — the story, in progress.

## When it breaks

**The false alarm — a squiggle under working code:**

```text
Import "openai" could not be resolved from source  [Pylance reportMissingModuleSource]
```

**What it means.** The language server looked in the `site-packages` of *its* interpreter and did
not find the package. Your terminal disagrees, because `uv run` uses the project's `.venv`. Run
**Python: Select Interpreter** and pick `.venv`. If the picker does not offer it, the environment
does not exist yet — run `uv sync` and reopen the folder.

**The false silence, which has no error text at all.** This is the one to actively look for, because
nothing announces it. If your editor offers autocomplete for a function whose arguments you know
changed, or accepts a call that fails at runtime, stop and check the interpreter path before
debugging the code. **An editor analysing a stale environment produces confident, wrong answers**,
and no amount of reading your own code will reveal that the problem is a setting.

**The reformatted lesson, which you will notice as a giant diff:**

```text
$ git status --porcelain
 M days/day-00-setup/parts/01/1.3-uv-the-one-binary-that-owns-the-environment.md
 M days/day-00-setup/parts/02/2.4-uv-init-pyproject-and-the-lockfile.md
```

**What it means.** You saved a lesson with Markdown format-on-save enabled, and the formatter
rewrote the Python inside the fenced blocks. Restore with `git checkout -- <file>` and set
`"[markdown]": { "editor.formatOnSave": false }`. The `[tool.ruff.format] exclude = ["**/*.md"]`
line in `pyproject.toml` protects the *command line*; only the editor setting protects the *editor*.

**The disagreement that wastes an afternoon:**

```text
$ ./m check
Would reformat: src/mandala/router.py
1 file would be reformatted
```

...while the editor shows the file as perfectly formatted. **What it means.** Two different
formatters, or two different versions of one. Almost always a second formatter extension is
installed and winning the default. Check that `editor.defaultFormatter` for Python is
`charliermarsh.ruff`, and that the extension's bundled `ruff` is not older than the pinned one in
`pyproject.toml`. The durable fix is to have the editor use the project's own `ruff` rather than a
bundled copy — the extension has a setting for this — so there is exactly one version in play.

## In production

**The editor is a fast, unreliable copy of CI, and that framing keeps you honest.** It runs the same
tools with a shorter feedback loop and no guarantees; CI runs them in a clean environment and is the
answer of record. Professionals wire them to the same configuration precisely so the fast one is
*predictive* of the slow one. When they diverge, the fix is always to reconcile the configuration —
never to add an editor-only exception, because an editor-only exception is invisible to everyone
else on the team.

**This is why linter configuration lives in `pyproject.toml` and not in editor settings.** The rules
in `[tool.ruff.lint]` are committed, versioned and reviewed, so every developer and every CI run
applies the same set. Rules configured in a personal editor profile are invisible to code review and
produce the "it passed for me" arguments that formatting tools exist to eliminate.

**Pre-commit hooks are the third rung of the same ladder.** This repository has a
`.pre-commit-config.yaml`: a hook that runs the linter on staged files before the commit is created,
so a violation cannot reach the branch even if you ignored the editor. Editor → hook → CI, each one
slower, each one harder to bypass. **Day 2 wires the CI rung**, and by then you will already have
the first two.

**What degrades at scale.** On a large codebase the language server's index becomes a performance
problem, and teams start excluding directories, splitting workspaces, or paying attention to which
type-checking mode they run. More importantly, *type coverage* becomes a real engineering decision:
a codebase with type annotations gets meaningful editor answers, and one without gets guesses. That
matters more than usual in this project, because typed structured output — a contract the model must
fill — is the pattern that recurs from Day 4 to the capstone.

**The review comment a senior engineer leaves.** On a pull request adding `.vscode/settings.json`
with an absolute interpreter path: *"Use `${workspaceFolder}` — this path only exists on your
machine, and committing it breaks the setting for everyone else."* And on a `# noqa` added to
silence a linter: *"What is the rule, and why is this an exception? Either fix it or document the
exception with the rule code — a bare `noqa` disables everything on that line, including rules we
have not written yet."*

**The interview question.** *"Your editor shows no errors and the build fails. What do you check?"*
The answer is: whether they are looking at the same thing. Same interpreter, same tool versions,
same configuration file. It sounds trivial and it is the correct first move roughly every time —
and the follow-up question, *"how do you stop it recurring?"*, is answered by "configuration in the
repository, not in a personal profile", which is the point of this whole part.

## Check yourself

```bash
uv run python -c "import sys; print(sys.executable)" && ls .vscode/settings.json 2>/dev/null || echo "no committed editor settings"
```

The first path must be inside this project's `.venv`. Then look at your editor's status bar: it must
show the same interpreter. Two places, one answer.

**Answer out loud, without scrolling up:**

> Your editor underlines an import as unresolvable, but the code runs fine from the terminal. What
> are the two programs disagreeing, what exactly are they disagreeing *about*, and which of the two
> possible failures — a false alarm or a false silence — would you rather have? Justify it.
