# 1.1 — Why one tool must own the environment

## One-line answer

A "Python environment" is nothing more than **one interpreter plus one folder of installed
packages**, and almost every baffling `ModuleNotFoundError` happens because the interpreter that ran
your code and the folder that received the package belonged to two different environments.

---

## The story

A developer joins a team on a Monday. Their first task is deliberately small: run a script the team
has used for a year, `report.py`, and confirm it prints the same numbers it printed last week.

They open a terminal and type `python report.py`.

```text
ModuleNotFoundError: No module named 'httpx'
```

Reasonable enough. They install it: `pip install httpx`. A progress bar fills the terminal and ends
with `Successfully installed httpx-0.28.1`. They run the script again.

```text
ModuleNotFoundError: No module named 'httpx'
```

They stare at it. They run `pip install httpx` again — `Requirement already satisfied`. They can see
the package. They open a file explorer and *find the folder it went into*. It is there. It is
unambiguously there. The script still cannot see it.

They lose the afternoon. Eventually a colleague leans over, types one command, and reads the output
aloud: there are four Pythons on this laptop. One came from the python.org installer. One came
bundled with an editor. One came from a data-science distribution installed two years ago and never
removed. One is the Windows Store shim. `pip` belonged to the third. `python` was the fourth.

Nothing was broken. Two words on the same keyboard were pointing at two different machines that
happened to share a disk.

That afternoon is the most common way a first month gets lost. Today exists so it never happens to
you — not on Day 3 when you are writing your first agent loop, and certainly not on Day 67 when the
thing that fails is a Docker sandbox and you have real work to lose.

---

## The idea in plain language

Let us build the vocabulary from nothing. Three words: **interpreter**, **site-packages**, and
**PATH**.

**An interpreter is a program.** `python.exe` (or `python` on macOS and Linux) is an executable file
sitting somewhere on your disk, exactly like a game or a text editor. It reads a `.py` file and
carries out the instructions in it. You can have as many of these programs on one machine as you
like, in as many folders as you like, and they neither know nor care about each other. This is the
first fact people get wrong: **"Python" is not a thing installed on your computer. It is a *file*,
and you can have twelve.**

**Every interpreter owns one folder of packages, called `site-packages`.** When you install a
library — `httpx`, `crewai`, anything — the files land in a folder that sits next to a *specific*
interpreter. There is no global, shared, machine-wide library shelf. Interpreter A cannot see
interpreter B's `site-packages`, in the same way your documents folder cannot see mine.

```mermaid
flowchart TB
    subgraph A["Interpreter A  (C:\\Python312\\python.exe)"]
        SPA["site-packages/<br/>httpx · openai"]
    end
    subgraph B["Interpreter B  (AppData\\...\\python.exe)"]
        SPB["site-packages/<br/>requests"]
    end
    A -. "cannot see" .-> SPB
    B -. "cannot see" .-> SPA
```

**`PATH` decides which one you get when you type a word.** When you type `python` and press Enter,
your shell does not search your whole disk. It walks a list of folders — that list is the
environment variable named `PATH` — in order, top to bottom, and runs **the first file it finds with
that name**. Then it stops looking. (An *environment variable* is simply a named piece of text that
your shell holds in memory and hands to every program it starts. `PATH` is one of them, and it holds
a list of folder names.)

Now the whole trap fits in one sentence:

> `pip` is itself a program on `PATH`, and it installs into the `site-packages` of **whichever
> interpreter that particular `pip` belongs to** — which is not necessarily the interpreter that the
> word `python` resolves to.

The developer in the story had a `pip` from the third Python earlier on `PATH` than the `pip` from
the fourth. Both commands succeeded perfectly. They simply spoke to different machines.

**A virtual environment** — the phrase you will meet everywhere — is the fix the Python world
settled on. It is not magic and not a container: it is a *folder* holding a link to one interpreter
plus its own private `site-packages`. "Activating" it means temporarily putting that folder at the
front of `PATH`, so that `python` and `pip` resolve to the pair inside it. One project, one folder,
one interpreter, one set of packages, no crosstalk.

And **that** is the idea this whole day is built on: *something must own the environment.* If
nothing owns it, `PATH` does — and `PATH` is a list of accidents accumulated by every installer you
have ever run. In this project the owner is a single program called `uv`, which you meet in
[1.3](1.3-uv-the-one-binary-that-owns-the-environment.md). It creates the environment, installs into
it, records exactly what it installed, and runs your code inside it. One owner, four jobs, no
ambiguity.

## Why Mandala needs it

This is not a Day 0 nicety. Four specific places it decides whether you have a good evening:

- **Day 23 (CrewAI).** CrewAI pulls a large dependency tree, including its own vector store. If a
  second interpreter is reachable on your machine, "did `crewai` install?" and "can my code import
  `crewai`?" become different questions, and you will answer the first while debugging the second.
- **Day 46 (the one honest RAG day).** Embeddings on this project are computed locally with
  `sentence-transformers`, which drags in PyTorch — a large, version-sensitive install. Putting that
  into the wrong interpreter is not a five-second mistake to undo.
- **Day 67 (sandboxing).** That day's entire point is that code runs in an environment you defined
  and can throw away. You cannot reason about a *deliberately* isolated environment if you are fuzzy
  about the accidental one you are typing in.
- **Every day with a test.** `./m check` runs `pytest`. If `pytest` and your code resolve to
  different environments, your tests import a *different copy* of your own package than the one you
  just edited — and you get a green suite for code you did not write. That failure is far worse than
  a red one, because you believe it.

There is a larger reason. Principle 4 of this plan is *pin everything*: exact versions, a committed
lockfile, `model=` typed out on every agent, nothing floating. **A pin is meaningless if you cannot
say which environment it applies to.** Reproducibility starts here or it does not start.

## The mechanism

You are going to look at your own machine and count. Open **Git Bash** — you install it in
[1.2](1.2-git-bash-and-the-carriage-return.md) if you do not have it yet; on macOS or Linux your
normal terminal is fine.

```bash
which -a python python3 pip pip3
```

**Line by line:**

- `which` — asks the shell "if I typed this word, which file would actually run?" It answers by
  walking `PATH` exactly as the shell would.
- `-a` — **all** matches, not just the winner. This is the flag that makes the command useful:
  without it you see the one that wins and stay unaware of the three queued behind it. The winner is
  printed **first**.
- `python python3 pip pip3` — four separate words, because on a real machine they routinely resolve
  to different places. `python3` existing while `python` does not is normal on macOS and Linux;
  `pip` pointing somewhere `python` does not is the bug from the story.

On Windows there is a second, sharper tool:

```bash
py -0p
```

**Line by line:**

- `py` — the **Python launcher for Windows**, a small dispatcher installed by the python.org
  installer. Its job is to find Pythons for you.
- `-0` — "list the interpreters you know about" (that is a zero, not a capital O).
- `p` — appended to `-0`, adds the full **p**ath of each one. `py -0` alone gives you names;
  `py -0p` gives you the addresses, which is what you actually need.
- If this prints `bash: py: command not found`, you have no python.org install — which is a
  *cleaner* starting point, not a problem.

Now the decisive question — not "is `httpx` installed?" but "installed *where*?":

```bash
python -c "import sys; print(sys.executable); print(sys.prefix)"
```

**Line by line:**

- `python -c "<code>"` — run the string as a program and exit. No file needed. `-c` for
  **c**ommand.
- `import sys` — `sys` is the standard-library module that describes the running interpreter itself.
  Nothing to install; it is part of Python.
- `sys.executable` — the **full path of the interpreter currently running this line**. This is
  ground truth. Not what you typed, not what you assume: the actual file.
- `sys.prefix` — the root of the environment this interpreter belongs to. Its `site-packages` lives
  underneath. Inside a virtual environment, `sys.prefix` points at that environment's folder;
  outside one, it points at the base installation. Comparing the two is how you tell where you are.
- The two `print` calls are separated by `;` so a single `-c` string runs both statements.

And the same question asked of `pip`:

```bash
pip -V
```

**Line by line:**

- `-V` — print pip's version **and**, crucially, the path it operates from. The output ends with
  something like `from C:\...\site-packages\pip (python 3.11)`. That parenthesised version and that
  path tell you which interpreter this `pip` installs *for*.
- Compare it against `sys.executable` above. **If those two disagree, you have just reproduced the
  story's bug on your own machine** — and you now know how to detect it in ten seconds instead of an
  afternoon.

## When it breaks

Here is the failure in full, as it actually appears:

```text
$ pip install httpx
Requirement already satisfied: httpx in c:\users\me\appdata\roaming\python\python311\site-packages (0.28.1)

$ python report.py
Traceback (most recent call last):
  File "report.py", line 1, in <module>
    import httpx
ModuleNotFoundError: No module named 'httpx'
```

**What the traceback is telling you.** Read the two paths, not the words. `pip` reported success
into a `python311` folder. Now ask `python` who it is:

```text
$ python -c "import sys; print(sys.executable)"
C:\Users\me\AppData\Local\Programs\Python\Python312\python.exe
```

`311` versus `312`. Two interpreters. `pip` did its job perfectly and `python` did its job
perfectly; they were simply not the same environment. **`ModuleNotFoundError` almost never means
"the package is missing from your computer". It means "the package is missing from *this*
interpreter."**

**The smallest fix**, and the one to reach for whenever you are unsure:

```text
$ python -m pip install httpx
```

`python -m pip` means "ask *this specific interpreter* to run its own `pip` module". It removes the
`PATH` lottery entirely, because the interpreter is named explicitly and pip is found *through* it
rather than *beside* it. If you take exactly one habit from this part: **never type bare `pip`
again.**

In this project you will type neither, because `uv` handles installation itself
([1.3](1.3-uv-the-one-binary-that-owns-the-environment.md)) — but you will meet machines that are
not this project, and this is the twenty-second diagnosis for all of them.

## In production

This stops being a laptop annoyance and becomes an outage the moment code leaves your machine.

**The same bug, wearing a suit.** A service works locally and crashes on deploy with
`ModuleNotFoundError`. The Dockerfile ran `pip install -r requirements.txt` as `root`, and the
container starts the app as an unprivileged user with a different `PATH` — or the base image ships
its own system Python and the app runs under a second one. Identical mechanism, different building.
The production version of `which -a python` is
`docker run --rm <image> python -c "import sys; print(sys.executable)"`, and it is the first thing
to run when a container claims a module is missing. You will build exactly this kind of image on
**Day 19** for the sandbox, and again on **Day 85** for deployment.

**Why professionals never install into the system Python.** On Linux distributions the operating
system is itself written partly in Python, and `apt`/`yum` depend on specific versions of specific
libraries in the system interpreter's `site-packages`. `sudo pip install` into it can upgrade a
dependency out from under the package manager and leave a machine that can no longer install
software. This is why modern Python refuses by default and prints
`error: externally-managed-environment` (PEP 668) — a guard rail added precisely because so many
people broke their machines this way. **Rule: the system Python belongs to the operating system.
Your project gets its own.**

**What the professional's version looks like.** In a serious codebase the environment is never
described in prose ("install crewai and langgraph") — it is *declared in a file and locked*: a
manifest listing direct dependencies at exact versions, and a lockfile pinning the full transitive
tree with hashes. Anyone, anywhere, on any machine materialises an identical environment from those
two files. That is what you build in
[2.4](../02/2.4-uv-init-pyproject-and-the-lockfile.md), and it is why Principle 4 exists.

**What degrades at scale.** With one project, ambiguity costs an afternoon. With forty services, an
unowned environment costs you the ability to answer "what is actually running in production right
now?" — and that question turns up during incidents, during security audits (which version has the
CVE?), and during compliance reviews. The entire supply-chain-security discipline rests on a
machine-readable, exact answer, which a `PATH` accident cannot give.

**The agent-specific sharpening.** Agent frameworks make this worse than ordinary libraries do,
because they resolve things *at runtime from strings*. A framework that takes `model="gemini/..."`
and looks up a provider adapter by name will fail with `ImportError` deep inside its own call stack
if the adapter package landed in a different environment — and the traceback will point at the
framework, not at your `PATH`. You will see exactly this shape on **Day 9**, the first day a
framework touches this repo. Knowing today that "the framework cannot find its adapter" and "I have
two environments" are the same sentence will save you that evening.

**The review comment a senior engineer leaves.** On a pull request containing `pip install foo` in a
CI script or a Dockerfile: *"Pin this and install it through the project's lockfile — an unpinned
install means CI can pass today and fail tomorrow with no commit in between."* The unstated point is
that an unpinned build is not reproducible, and a build you cannot reproduce is one you cannot roll
back to.

**The interview question.** *"A developer tells you `pip install requests` succeeded but their
script still raises `ModuleNotFoundError`. Walk me through your diagnosis."* They are not testing
whether you know the word "virtualenv". They want to hear you (1) ask what `sys.executable` prints,
(2) ask what path `pip -V` reports, (3) name the mismatch, and (4) reach for `python -m pip` — and
ideally (5) say that the real fix is for the project to own its environment rather than relying on
`PATH`. Answering with the mechanism instead of the incantation is the whole difference between
sounding junior and sounding senior.

## Check yourself

Run this now, before installing anything:

```bash
which -a python python3 pip pip3 2>/dev/null; echo "---"; py -0p 2>/dev/null || echo "no py launcher"
```

Write the answer down somewhere. You want to know what your machine looked like *before* today, so
that if something is strange on Day 40 you can tell what changed.

**Answer out loud, without scrolling up:**

> I type `pip install httpx` and it succeeds. I type `python` and `import httpx` fails. Explain
> exactly what happened, using the words *interpreter*, *site-packages* and *PATH* — and then give
> the one command that would have avoided it.
