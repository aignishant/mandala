# 1.2 — Git, Git Bash, and the carriage return that breaks your scripts

## One-line answer

Git installs two things on Windows — a version-control program **and** a full Unix shell called Git
Bash — and the single setting you must get right on install is how Git rewrites line endings,
because getting it wrong produces an error message that names a file which visibly exists.

---

## The story

Two people share a repository. One works on Windows, one on Linux. Everything is fine for months.

Then the Windows developer adds a small deployment script — twenty lines of shell — and pushes it.
The Linux developer pulls, runs it, and gets:

```text
bash: ./deploy.sh: /usr/bin/env^M: bad interpreter: No such file or directory
```

They look at the first line of the file. It says `#!/usr/bin/env bash`. They check that
`/usr/bin/env` exists. It does. They run `ls -l` — the file is there, it is executable, the spelling
is right. The error names a program that is present on the machine and refuses to run it anyway.

They spend an hour convinced the file is corrupt. It is not corrupt. It has one invisible character
on the end of every line.

The Windows machine wrote the file with Windows line endings — every line terminated by *two*
characters instead of one. So the first line of the file does not say "run this with
`/usr/bin/env`". It says "run this with `/usr/bin/env\r`" — a program whose name ends in a carriage
return, which does not exist and never will.

The fix took four seconds. Finding it took an hour, because nothing in the error message suggests
looking for a character you cannot see.

---

## The idea in plain language

**A line ending is a character.** Text files do not have invisible structure; a "new line" is stored
as an actual byte in the file, and two conventions exist for which byte(s) to use.

- **Unix, Linux, macOS** end a line with one character: **line feed**, written `\n`, sometimes
  abbreviated **LF**.
- **Windows** ends a line with two: **carriage return** then line feed, `\r\n`, abbreviated
  **CRLF**.

The names come from typewriters. "Carriage return" was the lever that slid the paper carriage back
to the left margin; "line feed" was the roller advancing the paper by one line. Windows kept both
instructions; Unix decided one was enough. Neither is wrong. They are simply different, and text
written under one convention and read under the other has an extra character on the end of every
line.

Most of the time nothing notices. Editors hide it. Python's file reading normalises it. But two
things care enormously:

1. **The shebang line of a script.** The `#!` on the first line of a shell script tells the system
   which program to run the file with. If the line ends `\r\n`, the carriage return is part of the
   program's *name*. Hence `/usr/bin/env^M: bad interpreter` — `^M` is how a terminal displays a
   carriage return when it is not acting as a line ending.
2. **Git's idea of "changed".** Git compares files byte by byte. Flip every line ending in a file
   and Git sees every line as modified, even though nothing meaningful changed. Two developers on
   two platforms can end up in a loop, each "reverting" the other.

**Git's answer is a setting called `core.autocrlf`**, which controls whether Git rewrites line
endings as files move between your disk and the repository. It takes three values:

| Value | On checkout (repo → disk) | On commit (disk → repo) |
|---|---|---|
| `true` | LF becomes CRLF | CRLF becomes LF |
| `input` | unchanged | CRLF becomes LF |
| `false` | unchanged | unchanged |

`true` is what the Windows installer offers by default, and it means your working files are CRLF
while the repository stores LF. That is fine for prose and Python — and it is exactly what breaks
`./m`, because `./m` is a shell script that is *executed from your disk*, where it is CRLF.

**So this project uses `input`**: files land on disk exactly as stored, and anything you commit is
normalised to LF. The repository and your disk agree, `./m` runs, and a Linux collaborator sees no
spurious changes.

There is a second, stronger mechanism: a file called **`.gitattributes`**, committed to the
repository, which states per-file-pattern what the line endings must be. Because it lives *in* the
repo, it applies to everyone who clones it, regardless of their personal `core.autocrlf`. A setting
protects you; a committed `.gitattributes` protects the project. This repository has one, and it
names `m` explicitly.

**And Git Bash.** On Windows, installing Git also installs a genuine Unix shell environment —
`bash`, plus the small programs the shell world assumes exist: `ls`, `grep`, `find`, `sed`, `curl`,
`which`. Every command in these ninety days is written in that dialect. You are not required to use
it (there is a translation table in [`days/README.md`](../../../README.md)), but every command in
every lesson is written to be pasted into Git Bash and work.

## Why Mandala needs it

- **`./m` is a bash script** with a `#!/usr/bin/env bash` shebang, and you will run it on almost
  every day of this project ([3.2](../03/3.2-the-case-dispatcher.md)). A CRLF `./m` is a `./m` that
  does not run, with an error message that sends you looking in the wrong place.
- **Every lesson's Setup block is bash.** `mkdir -p`, `cat > file <<'EOF'`, `uv add`. Written for
  Git Bash and given in full, so you never have to translate.
- **Git is how a day is *finished*.** Principle 1 says no commit, no day. `./m done N` runs
  `git commit`, and `docs/TRACKER.md` reads what is on disk. Git is not an optional extra here; it
  is the mechanism by which progress exists at all.
- **Day 74 puts all of this into CI.** GitHub Actions runs your checks on Linux. A script that only
  works because your machine is forgiving will fail there, in front of a red build.

## The mechanism

**Install Git.** Download it from [git-scm.com](https://git-scm.com/download/win) and run the
installer. Almost every screen can keep its default, but two matter:

- **"Configuring the line ending conversions"** — choose **"Checkout as-is, commit Unix-style line
  endings"**. That is `core.autocrlf=input`. If you already installed Git and chose the first
  option, you fix it with a command below rather than reinstalling.
- **"Adjusting your PATH environment"** — choose the recommended middle option, which puts Git's
  tools on `PATH` for other programs (your editor's terminal, for one) without replacing Windows'
  own utilities.

Now open Git Bash: press Start, type `Git Bash`, press Enter. Then:

```bash
git --version
uname -s
```

**Line by line:**

- `git --version` — proves Git installed and is reachable from *this* shell, which is a different
  question from "is it installed" (see [1.1](1.1-why-one-tool-must-own-the-environment.md) — the
  `PATH` lesson applies to every program, not just Python).
- `uname -s` — prints the kernel name. In Git Bash it prints something starting with `MINGW64`,
  which is your proof that you are in the Unix-shell environment and not in `cmd.exe` wearing a
  different font. On macOS it prints `Darwin`; on Linux, `Linux`.

**Tell Git who you are.** Git stamps every commit with a name and an email, and refuses to commit
without them:

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.autocrlf input
```

**Line by line:**

- `git config` — read and write Git's configuration.
- `--global` — write to your user-level config file (`~/.gitconfig`) rather than to one repository.
  Without it, the setting applies only to the repository you are standing in — and you are not
  standing in one yet, so Git would error.
- `user.name` / `user.email` — stamped into every commit you make, permanently and publicly. Use an
  email you are willing to have in a public history.
- `init.defaultBranch main` — names the first branch `main` instead of `master`. Without it, newer
  Git versions print a paragraph of advice every single time you run `git init`.
- `core.autocrlf input` — the setting from above: leave files alone on checkout, normalise to LF on
  commit. **This is the line that prevents the story.**

**Verify what you just set**, rather than assuming it took:

```bash
git config --global --list | grep -E "user\.|autocrlf|defaultBranch"
```

**Line by line:**

- `--list` — print every setting Git currently has at this level, as `key=value` lines.
- `|` — a **pipe**: send the output of the command on the left to the input of the command on the
  right, instead of to the screen.
- `grep -E "user\.|autocrlf|defaultBranch"` — print only lines matching this pattern. `-E` enables
  extended regular expressions, where `|` means "or". The `\.` is an escaped dot, matching a literal
  `.` rather than "any character" — without the backslash, `user.` would also match `username`.
- You should see four lines. If `core.autocrlf` is missing or says `true`, run the `git config` line
  above again and re-check. Do not move on assuming it worked.

**See the bytes for yourself.** This is the part that turns an abstract rule into something you can
recognise:

```bash
printf 'line one\r\nline two\r\n' > /tmp/crlf.txt
printf 'line one\nline two\n' > /tmp/lf.txt
cat -A /tmp/crlf.txt
cat -A /tmp/lf.txt
```

**Line by line:**

- `printf` — writes exactly the string you give it, interpreting escapes like `\r` and `\n`, and —
  unlike `echo` — adding nothing of its own. That precision is why it is used here instead of
  `echo`.
- `'...\r\n...'` — single quotes stop the shell touching the backslashes, so `printf` receives them
  and does the interpreting.
- `>` — **redirect**: send this command's output into a file, replacing what was there.
- `cat -A` — print the file with every invisible character made visible: `-A` shows line ends as `$`
  and control characters in caret notation. The CRLF file shows `line one^M$`; the LF file shows
  `line one$`. **That `^M` is the whole bug from the story, now visible on your own screen.**

## When it breaks

**The bad interpreter, in full:**

```text
$ ./m check
bash: ./m: /usr/bin/env^M: bad interpreter: No such file or directory
```

**What it means.** Not "env is missing". The shell read the shebang line, took everything after
`#!` as the program to run, and that string ends in a carriage return. It is looking for a file
literally named `env\r`. The file `./m` is fine; its line endings are not.

**The smallest fix**, when you just want the script to run:

```text
$ sed -i 's/\r$//' m
```

`sed -i 's/\r$//' m` edits the file in place, replacing a carriage return at the end of each line
(`\r$`) with nothing. Then fix the *cause* — check `core.autocrlf` and confirm `.gitattributes`
covers the file — or the next checkout will undo you.

**The whole-file phantom diff:**

```text
$ git diff m
diff --git a/m b/m
index 8a1f2c3..b7e91d4 100644
--- a/m
+++ b/m
@@ -1,80 +1,80 @@
-#!/usr/bin/env bash
+#!/usr/bin/env bash
-set -euo pipefail
+set -euo pipefail
```

**What it means.** Every line shows as both removed and added, and the two versions look identical
because the difference is invisible. You changed the line endings, not the content. The cause is
almost always an editor configured to "save as CRLF", or a `core.autocrlf` change made after the
file already existed on disk. Confirm with:

```text
$ git ls-files --eol m
i/lf    w/crlf  attr/text=auto eol=lf   m
```

`i/` is what is stored **i**n the repository, `w/` is what is in your **w**orking tree. `i/lf`
with `w/crlf` is the mismatch, and `attr/` shows which `.gitattributes` rule applies.

**The one people meet on a fresh Windows machine:**

```text
$ ./m status
bash: ./m: Permission denied
```

**What it means.** Not line endings this time — the file is not marked executable. Unix files carry
permission bits, one of which means "may be run as a program"; Windows has no direct equivalent, so
a file created on Windows often arrives without it. Fix with `chmod +x m` (`chmod` = **ch**ange
**mod**e; `+x` = add the e**x**ecutable bit). Git stores this bit, so committing after `chmod +x`
fixes it for everyone who clones. Alternatively `bash ./m status` sidesteps the bit entirely by
naming the interpreter yourself — useful for a one-off, wrong as a habit.

## In production

**`.gitattributes` is the professional's answer, not `core.autocrlf`.** A setting lives on one
developer's machine and silently differs on the next one. A committed `.gitattributes` travels with
the repository and applies to everyone. This project ships one:

```text
*.sh   text eol=lf
m      text eol=lf
*.py   text eol=lf
*.md   text eol=lf
```

`text` tells Git the file is text and may be normalised; `eol=lf` forces LF in the working tree
regardless of platform or personal config. On any repository containing shell scripts, a
`.gitattributes` with `eol=lf` on them is not optional — it is the difference between "works on my
machine" being a joke and being an incident.

**Where this bites hardest is Docker.** You will build container images on **Day 19** for the
sandbox and **Day 85** for deployment. A `COPY entrypoint.sh` of a CRLF file into a Linux image
produces a container that exits immediately with `exec /entrypoint.sh: no such file or directory` —
the same bug, with an even less helpful message, discovered in a build pipeline rather than on your
screen. Teams lose whole afternoons to this precise failure, and the fix is always the
`.gitattributes` line they did not write.

**Line endings are a data-integrity problem, not just a script problem.** Checksums, signatures and
content-addressed storage are all byte-exact. A file that "did not change" but was rewritten CRLF
has a different SHA-256 and will fail an integrity check. When you sign an Agent Card on **Day 87**,
this stops being about scripts and becomes about whether a signature verifies: a signature is over
bytes, and a helpful editor that normalises line endings on save has changed those bytes.

**The Git identity you set is a security surface.** `user.email` is not authenticated by Git — it is
a string you typed, and anyone can commit as anyone. Platforms fix this with commit signing (GPG or
SSH keys) and "verified" badges, and serious repositories enforce signed commits on protected
branches. Worth knowing now: the name on a commit is a claim, not proof.

**The review comment a senior engineer leaves.** On a pull request adding a shell script to a repo
with no `.gitattributes`: *"Add `*.sh text eol=lf` to `.gitattributes` — otherwise this breaks the
first time a Windows contributor touches it, and it breaks in CI rather than locally."* And on a
diff that shows every line changed: *"This is a line-ending change, not a content change. Please
rebase it out — it makes `git blame` useless for this file forever."* That last consequence is the
one people underestimate: a whole-file rewrite reassigns authorship of every line to whoever changed
the endings.

**The interview question.** *"A colleague says a shell script that works on their Windows machine
fails on the Linux server with `bad interpreter`. What is your first hypothesis?"* The answer they
want is line endings, in one sentence, followed by *how you would confirm it* (`cat -A`, `file`, or
`git ls-files --eol`) and *where the durable fix lives* (`.gitattributes`, committed, not a local
setting). Being able to name `^M` on sight is a small thing that reliably marks someone who has
shipped across platforms.
