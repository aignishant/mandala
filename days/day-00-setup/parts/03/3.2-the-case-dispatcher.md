# 3.2 — The `case` dispatcher, and why `./m` has one

## One-line answer

`./m` is a single script whose whole body is one `case` statement matching its first argument
against a list of subcommands — which is how a project gets *one* command to remember instead of
fifteen, and how the correct incantation for each task stops living in someone's shell history.

---

## The story

A new joiner asks how to run the tests.

The answer arrives in three messages. The first says `pytest`. The second corrects it: actually you
need to exclude the integration tests, so `pytest -m "not integration"`. The third adds that you
also want `--no-header` because the CI output parser chokes otherwise, and that if you are on
Windows you need to prefix the whole thing differently.

The new joiner writes it down. Two weeks later the marker is renamed from `integration` to `live`,
and their note is wrong. They do not find out for a while, because `pytest -m "not integration"`
does not fail when no test carries that marker — it silently runs everything, including the tests
that call a real API.

By the end of the quarter there are four subtly different versions of the test command circulating
in the team, each correct at the moment it was written down. Nobody is wrong. The knowledge simply
had nowhere to live except in people, and people copy each other imperfectly.

The fix is not a wiki page. A wiki page is another copy that goes stale. The fix is a *script in the
repository* — because a script is versioned with the code it operates on, so renaming the marker and
updating the command are the same commit.

---

## The idea in plain language

**A dispatcher is a script that reads its first argument and decides what to do.** You type
`./m check`, the script sees `check`, and it runs the commands that constitute checking. `./m done 4`
sees `done` and `4`. One entry point, several verbs.

The bash construct for this is `case`:

```text
case "$WORD" in
  pattern1)  commands ;;
  pattern2)  commands ;;
  *)         fallback ;;
esac
```

It compares `$WORD` against each pattern in order, runs the first branch that matches, and stops.
`;;` ends a branch, `*` matches anything (the catch-all), and `esac` is `case` backwards — an old
shell joke that is now just how you close the block.

`case` rather than a chain of `if`/`elif` because the patterns are **glob patterns**, not string
equality: `st|status)` matches either spelling, `day-*)` matches a prefix. That expressiveness is
free, and it reads as a table rather than as a ladder.

**Why a project wants one at all.** Three things, and each is worth stating separately:

1. **The correct command is written down where it cannot go stale.** It lives in the repository next
   to the code it runs, so a change to the code and a change to the command are one commit. That is
   the story's fix.
2. **The command is the same for everyone.** You, a collaborator, and CI all invoke `./m check`. When
   CI is red and your machine is green, the difference is not the command — which eliminates the
   most common false lead.
3. **The verbs become the project's vocabulary.** `./m start 7`, `./m depth 7`, `./m done 7`. New
   contributors learn the workflow by reading the usage text, and the usage text cannot drift from
   the implementation because both are in the same file.

**Why not `make`?** `make` is the traditional answer and it is a good tool, but it is not installed
on Windows by default, and its actual job — rebuilding files whose dependencies changed — is not what
this project needs. Using `make` as a "list of commands" means fighting its tab-sensitive syntax and
its assumption that every target is a file. **`./m` is forty lines of bash that does exactly one
job.** Choosing the smaller tool that fits, rather than the famous one that nearly fits, is itself
the lesson.

**And why the file is called `m`.** Because you will type it hundreds of times. One character, no
extension, executable. `./m` rather than `m` because the current directory is deliberately not on
`PATH` — a security default worth keeping, since it means a stray file named `ls` in a folder you
`cd` into cannot hijack a command.

---

## Why Mandala needs it

- **Ninety days is long enough to forget.** By Day 62 you will not remember which flags `ruff` needs
  or that pytest must exclude the `live` marker. `./m check` does not require you to.
- **`./m done N` is where Principle 1 is enforced.** It refuses to commit while the checklist has
  unticked boxes ([3.3](3.3-the-done-gate.md)). That refusal is only possible because there is a
  single place through which a day is finished.
- **The `live` marker is a money question here.** `pyproject.toml` defines `live` as "hits a real
  provider; costs free-tier quota". `./m check` runs `pytest -m "not live"`, so the routine check
  never spends a request (Principle 5). If that flag lived in your memory instead of in the script,
  you would eventually forget it — on the evening your quota was already low.
- **Day 2 makes CI run the same verbs.** `.github/workflows/check.yml` calls the same commands, so a
  green local check genuinely predicts a green build.

## The mechanism

Here is the whole dispatcher, with the branches you have already met and the ones coming in
section 4. Read it top to bottom:

```bash
#!/usr/bin/env bash
# Project Mandala daily driver. Replaces `make` (not installed on Windows).
set -euo pipefail

DAY="${2:-}"
pad() { printf "%02d" "$1"; }

daydir() {
  local n="$1"
  if [ -d "days/day-$(pad "$n")" ]; then echo "days/day-$(pad "$n")"
  elif [ -d "days/day-$n" ]; then echo "days/day-$n"
  elif [ "$n" = "0" ] && [ -d "days/day-00-setup" ]; then echo "days/day-00-setup"
  else echo ""; fi
}
```

**Line by line:**

- `#!/usr/bin/env bash` — the shebang from [3.1](3.1-set-euo-pipefail.md).
- `set -euo pipefail` — line 3, exactly as argued in [3.1](3.1-set-euo-pipefail.md). Everything
  below depends on a failing step actually stopping the script.
- `DAY="${2:-}"` — the second argument, or empty. The `:-` is **required** here: with `set -u`, a
  bare `$2` would abort the script whenever you type `./m status` with no day number.
- `pad() { ...; }` — defines a function. `printf "%02d"` formats a number to two digits with a
  leading zero, so `7` becomes `07` and the folder name `days/day-07` matches. Without this, `./m
  start 7` would look for `days/day-7` and fail on a folder that plainly exists.
- `daydir()` — resolves a day number to its folder, trying the padded name, then the unpadded one,
  then the special `day-00-setup`. It exists because Day 0 has a different folder name from every
  other day, and one function is a better place for that irregularity than five branches.
- `local n="$1"` — `local` scopes the variable to the function. Without it, bash variables are
  global, and a function that quietly overwrites a caller's variable is a bug that takes an evening.
- `[ -d "path" ]` — the **test** command: true if the path exists and is a directory. `[` is
  genuinely a program (with a matching `]` argument), which is why the spaces around it are
  mandatory rather than stylistic.
- `echo ""` in the fallback — return an empty string for "no such day", so callers can test for it
  rather than parsing an error.

Now the dispatcher itself:

```bash
case "${1:-help}" in
  status)
    uv run python scripts/tracker.py --summary
    ;;

  start)
    [ -z "$DAY" ] && { echo "usage: ./m start <day>"; exit 1; }
    D="$(daydir "$DAY")"
    [ -n "$D" ] || { echo "no day folder for day $DAY - see docs/TRACKER.md"; exit 1; }
    echo "-> open $D/LESSON.md   (the hub - read its §2 map, then work through parts/ in order)"
    find "$D/parts" -name '*.md' | sort | sed "s|^$D/|     |"
    ;;

  check)
    uv run ruff check .
    uv run ruff format --check .
    rc=0
    uv run python -m pytest -q -m "not live" || rc=$?
    if [ "$rc" -eq 5 ]; then
      echo "   (pytest collected no tests yet - expected until the first lab writes one)"
    elif [ "$rc" -ne 0 ]; then
      echo "FAIL pytest exited $rc"; exit "$rc"
    fi
    uv run python scripts/depth_check.py
    echo "OK all green"
    ;;

  *)
    cat <<'USAGE'
usage: ./m <command> [day]

  status         how many days are written / complete
  start N        point at day N's hub and list its parts/
  depth [N]      check day N against the plan's Part 11 depth contract
  check          ruff + ruff format + offline pytest + the depth contract
  done N         refuse unless the checklist is ticked and checks are green, then commit
USAGE
    ;;
esac
```

**Line by line:**

- `case "${1:-help}" in` — dispatch on the first argument, defaulting to `help` when there is none.
  So bare `./m` prints usage instead of erroring, which is what a person typing it for the first
  time expects.
- `status)` — a branch. Everything until `;;` runs when the argument is exactly `status`.
- `[ -z "$DAY" ] && { ...; exit 1; }` — `-z` is true when the string is empty. `&&` runs the block
  only if so. The braces group the two commands, and the `;` before `}` is required by bash's
  grammar. This is the argument-validation idiom: check, complain, exit non-zero.
- `D="$(daydir "$DAY")"` — command substitution, calling the function and capturing what it echoed.
- `[ -n "$D" ] || { ...; exit 1; }` — `-n` is true when non-empty; `||` runs the block when it is
  not. The mirror image of the line above, and the reason `daydir` returns an empty string rather
  than printing an error itself.
- `find "$D/parts" -name '*.md' | sort` — list every part document, sorted so the reading order is
  the numeric order.
- `sed "s|^$D/|     |"` — substitute the day-folder prefix with five spaces, so the output is a
  short indented list rather than a column of long paths. `s|a|b|` uses `|` as the delimiter instead
  of the usual `/` — necessary here because the text being matched *contains* slashes.
- `uv run ruff check .` — lint the whole project. Every command in `check` goes through `uv run`
  ([2.5](../02/2.5-the-venv-you-never-activate.md)), so the check runs in the locked environment
  whether you invoke it from a terminal, an editor, or CI.
- `ruff format --check .` — verify formatting **without changing anything**. `--check` makes it a
  test rather than an edit, which is what belongs in a gate.
- `rc=0` then `... || rc=$?` — capture pytest's exit status without letting `set -e` abort the
  script. `||` is one of `-e`'s exemptions ([3.1](3.1-set-euo-pipefail.md)), and here that exemption
  is being used deliberately rather than tripped over.
- `if [ "$rc" -eq 5 ]` — pytest exits **5** when it collected no tests at all. Early in the project
  that is the honest state, not a failure, so it is reported and tolerated. Every other non-zero
  status is a real failure and exits with it. **Distinguishing "nothing to run" from "something
  failed" is the kind of detail that decides whether a gate gets trusted or routed around.**
- `uv run python scripts/depth_check.py` — the last gate: no day may violate the plan's Part 11
  contract ([4.1](../04/4.1-the-depth-check.md)).
- `*)` — the catch-all branch, matching anything the earlier patterns did not.
- `cat <<'USAGE' ... USAGE` — a heredoc printing the usage text. Quoting the delimiter stops the
  shell expanding `$` or backticks inside it, exactly as in
  [2.2](../02/2.2-gitignore-before-the-secret-exists.md).

Make it executable and run it:

```bash
chmod +x m
./m
./m status
```

**Line by line:**

- `chmod +x m` — **ch**ange **mod**e, add the e**x**ecutable bit. Git records this bit, so committing
  after `chmod` fixes it for anyone who clones.
- `./m` — the `./` names the file in the current directory. Required because `.` is deliberately not
  on `PATH`.
- `./m status` — the first real verb. It prints how many days are written, which will read `0 of 91`
  until this day is committed.

## When it breaks

**The bit that Windows does not set:**

```text
$ ./m status
bash: ./m: Permission denied
```

**What it means.** The executable bit is missing. `chmod +x m` fixes it, and committing afterwards
fixes it for everyone. `bash ./m status` works around it by naming the interpreter yourself —
acceptable once, wrong as a habit, because it hides the actual problem from the next person.

**The one where the file is right and the path is wrong:**

```text
$ m status
bash: m: command not found
```

**What it means.** You omitted `./`. The shell searched `PATH`, and the current directory is not on
it. This is a *security* default, not an oversight: if `.` were on `PATH`, cloning a repository
containing a file named `ls` and typing `ls` would run someone else's code. Type `./m`.

**The silent misdispatch, which is the failure mode `case` invites:**

```text
$ ./m chekc
usage: ./m <command> [day]
  status         how many days are written / complete
  ...
```

**What it means.** No branch matched `chekc`, so the catch-all printed usage. That is the correct
behaviour and it is worth noticing *why* it is correct: the alternative — a dispatcher that ignores
unknown verbs silently — would let `./m chekc` exit 0 and look like a passing check. **A dispatcher
whose fallback is "print usage" is safe; one whose fallback is "do nothing quietly" is a trap.** If
you extend `./m`, keep the catch-all last, because `case` takes the *first* match and a `*` branch
placed earlier would swallow everything below it.

**The failure that only shows up once you add a branch:**

```text
$ ./m parts 7
./m: line 41: syntax error near unexpected token `)'
```

**What it means.** A missing `;;` on the branch above. Without it, bash reads the next pattern as
part of the previous branch's command list and fails on the `)`. The line number points at the
*symptom*, not the cause — the missing terminator is usually several lines earlier, which is the
single most common way to lose ten minutes editing a `case` statement.

## In production

**Every mature repository has one of these, whatever it is called.** `make`, `just`, `task`, a
`scripts/` directory, or a bare `./m`. The name does not matter; the property does — **there is one
documented way to build, test and ship, and it is executable rather than described.** The test for
whether yours is working: can a new contributor run the test suite correctly without asking anyone?
If the answer requires a conversation, the knowledge is still living in people.

**The dispatcher is the contract between local development and CI.** The strongest version of this
is a CI workflow whose steps are nothing but `./m check` — because then a green local run and a
green build are the *same command*, not two commands that resemble each other. Day 2 wires exactly
this. When they diverge, "works locally, fails in CI" becomes a genuine mystery instead of a
five-minute diff, and teams start re-running builds hoping for a different answer.

**Task runners grow, and knowing when to stop is a real skill.** `./m` is under a hundred lines and
delegates anything substantial to Python ([4.1](../04/4.1-the-depth-check.md),
[4.2](../04/4.2-the-tracker-you-never-hand-edit.md)). The failure mode is a dispatcher that
accumulates logic until it is a program written in the worst available language — no data
structures, no tests, no types, and error handling by convention. **The rule from
[3.1](3.1-set-euo-pipefail.md) applies: past roughly a hundred lines, or as soon as you need real
control flow, the branch should call a program rather than be one.**

**Discoverability is a feature, not documentation.** `./m` with no arguments printing its own usage
means the tool teaches itself, and the usage text cannot go stale because it sits three lines from
the implementation. This is why the catch-all branch is a usage message rather than an error: the
most common way to discover a CLI is to type its name and see what happens.

**What degrades at scale.** In a monorepo, one root dispatcher becomes a bottleneck — every team
wants a verb, and the file becomes a merge-conflict magnet. The usual evolution is a thin root
dispatcher that delegates to per-package runners, or a real build tool with a dependency graph and
caching. The transition point is usually when someone asks "can it skip work that has not changed?",
which is precisely the question `make` was invented for and `case` cannot answer.

**The review comment a senior engineer leaves.** On a pull request adding a README section
describing a five-flag command: *"Put this in `./m` instead — a documented command drifts from the
code, an executed one cannot."* And on a new branch added above the catch-all with no `;;`: *"Missing
terminator; this will fall through into the next branch."*

**The interview question.** *"How does a new engineer on your team run the tests?"* The answer that
lands is one command, and the reason it is one command: because the flags, the markers and the
environment are encoded in a script that is versioned with the code, so renaming a test marker and
updating the command are the same commit. If the honest answer is "they ask someone", the follow-up
writes itself.

## Check yourself

```bash
./m && ./m status && ./m chekc
```

The first prints usage. The second prints the progress summary. The third prints usage again — an
unknown verb falls to the catch-all rather than silently doing nothing.
