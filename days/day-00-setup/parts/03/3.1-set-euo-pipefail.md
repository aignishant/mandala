# 3.1 — `set -euo pipefail`, the four options that make bash safe

## One-line answer

By default a shell script **keeps going after an error**, treats a misspelled variable as an empty
string, and reports success whenever the *last* command in a pipeline succeeds — and
`set -euo pipefail` turns off all three of those behaviours.

---

## The story

A nightly job runs on a server. Three steps: rebuild a dataset, retrain a model on it, copy the
result to where the application reads from. It is a short script and it has worked for months.

One night the first step fails — a source file is briefly unavailable. The script prints an error
and **carries on**, because that is what shell scripts do by default. Step two trains on the
half-written dataset. Step three copies it into place. The script finishes and exits with status
zero, which the scheduler records as success. No alert fires. Nothing turns red anywhere.

For eleven days the application serves predictions from a model trained on truncated data. Quality
degrades slowly enough that nobody attributes it to a single event. By the time someone goes
looking, the logs from that night have rotated away.

The error *was* printed. It simply was not *acted on*, because nothing in the script said an error
should stop anything. The failure was not in the code that broke. It was in the eight characters
missing from line two.

---

## The idea in plain language

A **shell script** is a text file of commands run one after another. Every command, on finishing,
produces an **exit status**: a number where **zero means success** and anything else means failure.
(Backwards from what you might expect, and worth remembering by its reason: there is one way to
succeed and many ways to fail, so the failures get the non-zero numbers.) The `&&` and `||`
operators are simply reading that number — `a && b` runs `b` only if `a` exited zero.

Bash's defaults were designed for an *interactive* session, where a human sees each result and
decides what to do next. In a script — run by a scheduler, by CI, or by `./m done` at the end of a
long evening — nobody is watching. Three of those defaults are actively dangerous.

**1. An error does not stop the script.** Each command runs regardless of what the previous one did.
That is the story exactly.

**2. An unset variable becomes an empty string.** Misspell a variable name and bash substitutes
nothing, silently. The canonical illustration:

```text
rm -rf "$BUILDDIR/"      # you meant BUILD_DIR
```

`BUILDDIR` is unset, so it expands to nothing, so the command becomes `rm -rf "/"`. No error, no
warning — just a different command than the one you wrote.

**3. A pipeline reports only its last command's status.** In `a | b | c`, if `a` fails and `c`
succeeds, bash considers the pipeline successful. So `run_tests | tee results.log` reports success
whenever `tee` manages to write the file, regardless of whether the tests passed.

`set` changes shell options, and `-` turns them on:

| Option | Turns on | Effect |
|---|---|---|
| `-e` | `errexit` | exit immediately if any command fails |
| `-u` | `nounset` | error on an unset variable instead of substituting empty |
| `-o pipefail` | `pipefail` | a pipeline fails if **any** stage failed, not just the last |

The `o` in `-o pipefail` is there because `pipefail` has a name rather than a single letter; `-o`
means "set the option named next". `set -euo pipefail` combines all three, and it is the first line
of essentially every professionally written bash script.

The mental shift is worth naming: these options convert **silent wrongness into loud failure**. That
is almost always the trade you want, because a script that stops at step one is an inconvenience,
while a script that continues to step three is an incident.

---

## Why Mandala needs it

- **`./m` is the daily driver** and you will run it on nearly every one of the ninety days
  ([3.2](3.2-the-case-dispatcher.md)). A gate that can silently half-fail is not a gate.
- **`./m done N` commits your work** ([3.3](3.3-the-done-gate.md)). If its lint or test step failed
  quietly, it would commit broken code and mark the day complete — defeating Principle 1 and
  Principle 7 together, with a single missing line.
- **Day 2 puts these same commands into GitHub Actions**, where nobody is watching the output at
  all. Everything here applies more strongly there, not less.
- **Principle 7 says a test must be able to go red.** A red test that does not stop the script is a
  test that cannot fail in any way that matters — the check goes green, the day gets committed, and
  the eval you wrote to catch a regression catches nothing.

## The mechanism

Before writing the line into `./m`, watch each option fail on purpose. Create a scratch script:

```bash
cat > /tmp/demo.sh <<'EOF'
#!/usr/bin/env bash
echo "step 1"
false
echo "step 2 - should this run?"
EOF
bash /tmp/demo.sh; echo "exit status: $?"
```

**Line by line:**

- `#!/usr/bin/env bash` — the **shebang**: the first line of an executable script, naming the
  interpreter to run it with. `/usr/bin/env bash` finds bash on `PATH` rather than assuming a fixed
  location, which is what makes the script portable between Linux and macOS (where bash lives in
  different places). This is the line that breaks on a CRLF file
  ([1.2](../01/1.2-git-bash-and-the-carriage-return.md)).
- `false` — a real program whose only job is to exit with status 1. Its counterpart `true` exits 0.
  They exist precisely for testing logic like this.
- `bash /tmp/demo.sh` — run it.
- `$?` — the exit status of the previous command. **The output is the lesson:** `step 2` prints, and
  the script exits **0**. A command failed, and the script both continued and reported success.

Now add `-e`:

```bash
cat > /tmp/demo.sh <<'EOF'
#!/usr/bin/env bash
set -e
echo "step 1"
false
echo "step 2 - should this run?"
EOF
bash /tmp/demo.sh; echo "exit status: $?"
```

**Line by line:**

- `set -e` — exit on the first failure. Now `step 2` does not print and the status is **1**. One
  line is the entire difference between the story's silent outage and an obvious failure.
- Everything else is byte-identical on purpose: this is a controlled experiment with one variable.

Now `-u`, the one that prevents the destructive typo:

```bash
cat > /tmp/demo.sh <<'EOF'
#!/usr/bin/env bash
set -eu
TARGET="/tmp/safe-to-delete"
echo "would remove: '${TARGE}/'"
EOF
bash /tmp/demo.sh; echo "exit status: $?"
```

**Line by line:**

- `TARGE` — a deliberate typo for `TARGET`. Without `-u` this prints `would remove: '/'` and carries
  on cheerfully. With `-u`, bash refuses: `TARGE: unbound variable`, status 1.
- `echo` is used rather than `rm` for obvious reasons — the point is the substitution, and there is
  no reason to demonstrate it destructively.
- `'${TARGE}/'` — the braces delimit the variable name so bash cannot mistake where it ends. Always
  brace a variable adjacent to other characters: `"$TARGET/file"` is fine, but `"${TARGET}_bak"` is
  *required*, because `$TARGET_bak` would be read as a variable named `TARGET_bak`.

And `pipefail`, the subtlest of the three:

```bash
cat > /tmp/demo.sh <<'EOF'
#!/usr/bin/env bash
set -e
false | echo "the pipeline says it worked"
echo "status without pipefail: $?"
set -o pipefail
false | echo "and now?"
echo "status with pipefail: $?"
EOF
bash /tmp/demo.sh
```

**Line by line:**

- `false | echo "..."` — the first stage fails; the second succeeds. Without `pipefail` bash reports
  **0**, and `set -e` sees nothing wrong — which is why the two options are needed *together*.
- `set -o pipefail` mid-script — shell options can be changed at any point, used here so both
  behaviours appear in one run.
- The second status is **1**. This is why `uv run pytest | tee test.log` is dangerous without
  `pipefail`: `tee` almost always succeeds, so the pipeline hides every test failure behind it.

Now read the line that actually opens this project's driver:

```bash
head -3 m
```

**Line by line:**

- `head -3` — the first three lines of the script you meet in [3.2](3.2-the-case-dispatcher.md): the
  shebang, a comment saying what the script is for, and `set -euo pipefail`. Reading the top of an
  unfamiliar shell script and checking for this line is a fast, reliable signal about whether it was
  written carefully.

## When it breaks

**`-u` firing on an argument that simply was not passed:**

```text
$ ./m start
./m: line 5: $2: unbound variable
```

**What it means.** The script referenced `$2` — the second argument — and you supplied one. With
`-u` that is an error rather than an empty string. The fix is **not** to abandon `-u`; it is to say
what the default should be:

```text
DAY="${2:-}"
```

`${2:-}` means "the second argument, or empty if it is unset" — the same `${VAR:-default}` form you
used in [2.5](../02/2.5-the-venv-you-never-activate.md). You have now *chosen* the empty case
explicitly, and the next line can check for it and print usage. `-u` did its job: it forced the
missing case to be handled rather than assumed. This is exactly why `./m` line 5 reads `DAY="${2:-}"`.

**`-e` not firing where you expected — the classic surprise:**

```text
$ cat check.sh
#!/usr/bin/env bash
set -euo pipefail
grep -q "TODO" src/*.py
echo "no TODOs left"

$ ./check.sh
$ echo $?
1
```

Now change one line and watch it get worse:

```text
if grep -q "TODO" src/*.py; then echo "found"; fi
echo "this still runs even though grep failed"
```

**What it means.** `set -e` deliberately does **not** trigger when a command's status is being
*tested* — in an `if` condition, in a `while`, on the left of `&&` or `||`, or when negated with `!`.
That exemption is necessary (otherwise `if` would be unusable) but it surprises people. Two further
exemptions worth knowing: a failing command inside a function called in a condition does not exit,
and `set -e` is not inherited by subshells in every way you might assume. The professional takeaway
is not to distrust `-e` but to know its shape: **`-e` protects unchecked commands; commands you check
are your responsibility.**

**The one that catches everyone writing their first script on Windows:**

```text
$ ./m check
bash: ./m: /usr/bin/env^M: bad interpreter: No such file or directory
```

**What it means.** The `^M` from [1.2](../01/1.2-git-bash-and-the-carriage-return.md) — a Windows
carriage return on the end of the shebang line, so the system looks for an interpreter literally
named `env\r`. Fix with the `.gitattributes` rule and `core.autocrlf input`, or convert the file in
place with `sed -i 's/\r$//' m`. Worth recognising instantly, because the error names a file that
obviously exists and sends people looking in entirely the wrong direction.

## In production

**This line is the difference between a pipeline that fails and one that lies.** Every CI system
decides a step's outcome from its exit status. A script without `-e` can print a page of errors and
still exit 0, so the pipeline goes green and the artifact ships. Reviewing a `.sh` file in a
deployment pipeline, the first thing to check is line two — and its absence is a legitimate blocking
comment on a pull request.

**`set -x` is the debugging companion.** It prints each command with its variables expanded before
running it, turning "the script did something strange" into a transcript. In CI it is common to
enable it conditionally — `[[ -n "${DEBUG:-}" ]] && set -x` — so a failing job can be re-run with
tracing. Note it is conditional rather than permanent because **it prints secrets**: an
`export GEMINI_API_KEY=...` becomes a line in your build log otherwise, which is
[2.2](../02/2.2-gitignore-before-the-secret-exists.md)'s problem arriving through a different door.

**`IFS` is the fourth member of the family.** The strict-mode line many teams use is
`set -euo pipefail; IFS=$'\n\t'`. `IFS` — the internal field separator — controls how bash splits
unquoted expansions into words; by default it includes a space, so a filename containing a space
becomes two arguments. Narrowing it to newline and tab removes an entire class of bug. It is not in
this project's `./m` because that script handles no filenames, and adding machinery you do not need
is its own kind of mistake — but you should recognise it in the wild.

**Static analysis exists for shell.** `shellcheck` reads a script and reports quoting bugs,
unhandled statuses, and misuse of `[` versus `[[`. Serious repositories run it in CI on every `.sh`
file. Shell is a language whose failure modes are unusually well catalogued, which makes it
unusually amenable to a linter — and unusually dangerous without one.

**Where teams outgrow bash.** These options make short scripts safe; they do not make bash a good
language for long ones. The rule of thumb most teams converge on: past roughly a hundred lines, or
as soon as you need data structures, error recovery, or tests, move to Python. This project's `./m`
sits under that line and delegates anything substantial —
[the depth check](../04/4.1-the-depth-check.md) and
[the tracker](../04/4.2-the-tracker-you-never-hand-edit.md) — to Python scripts, deliberately.

**The review comment a senior engineer leaves.** On any new shell script without the strict-mode
line: *"Add `set -euo pipefail` — without it a failing step here goes unnoticed and the job still
reports success."* And on `results=$(generate | tee out.log)`: *"This masks failures in `generate`.
Either add `pipefail` or check `PIPESTATUS`."*

**The interview question.** *"What does `set -euo pipefail` do, and when does `-e` **not** save
you?"* The first half is memorisable; the second half distinguishes someone who has written
production scripts. The answer: `-e` is suppressed wherever a command's status is being tested —
`if` conditions, `while`, `&&`/`||` chains, `!` negation — so a command whose failure you intended to
handle will not exit the script, which is correct but surprising. Mentioning that `pipefail` and
`-e` must be used *together* to catch a failing pipeline stage is the detail that lands it.

## Check yourself

```bash
printf '#!/usr/bin/env bash\nset -euo pipefail\nfalse | echo piped\necho "unreachable"\n' > /tmp/t.sh && bash /tmp/t.sh; echo "exit status: $?"
```

`unreachable` must **not** print, and the status must be **1**. If it prints, one of the three
options is missing from the line you wrote.

**Answer out loud, without scrolling up:**

> Name each of the three options and the specific silent failure it prevents. Then: your script has
> `set -euo pipefail`, a command inside an `if` condition fails, and the script keeps going. Is that
> a bug in bash, a bug in your script, or a bug in your expectation? Justify it.
