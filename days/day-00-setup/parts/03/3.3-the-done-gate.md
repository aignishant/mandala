# 3.3 — The `done` gate that refuses to commit

## One-line answer

`./m done N` reads the day's checklist, and if a single box is still `- [ ]` it prints the unticked
lines and exits without committing — which turns Principle 1 from an intention you hold into a
condition a program enforces on an evening when you are tired.

---

## The story

Someone is on day forty of a long self-study plan. It is late. The lab works — they ran it, they saw
the output, the agent did the thing.

There are three boxes left on the checklist. One asks them to break a test deliberately and watch it
go red. One asks them to answer a question out loud. One asks them to read the failure mode section
they skipped.

They tick all three. Not dishonestly, exactly — more like *rounding up*. They know the material. It
is late. The code works.

On day sixty-one, a test that should have caught a regression does not catch it, because it asserts
something that is true whether or not the code works. They never verified it could fail. It has been
green and meaningless for three weeks.

The interesting part is not that they cut a corner. Everyone does, eventually, at the end of a long
evening. The interesting part is that **the checklist offered no resistance.** It was a list of
sentences in a Markdown file, and ticking a box cost exactly one keystroke whether the work was done
or not.

A gate that cannot say no is not a gate. It is a wish.

---

## The idea in plain language

**A gate is a check that can refuse.** The distinguishing property is not that it *reports*
something — it is that it *stops* something you wanted to happen. A test suite that prints failures
but lets the deploy continue is a report. One that fails the pipeline is a gate.

`./m done N` is a gate on the act of finishing a day. It refuses when:

1. **the checklist has unticked boxes**, or
2. **`./m check` is not green** — lint, formatting, offline tests, and the depth contract.

Only when both pass does it commit and regenerate the tracker.

**Why refusing at the *commit* is the right place.** Principle 1 says: *every day produces runnable,
committed code; no commit = day not done.* That makes the commit the completion record — there is no
separate progress database (see [4.2](../04/4.2-the-tracker-you-never-hand-edit.md)). So the commit
is precisely the moment where a check has leverage: it is the thing you want, so it is the thing
worth withholding.

**What the gate can and cannot enforce, stated honestly.** A checklist box is a claim by you. The
script cannot verify that you answered a question out loud or understood a part document. What it
*can* do is make the claim explicit and deliberate: you must open the file, find the line, and
change `[ ]` to `[x]`. That is a small friction, applied at the moment of the decision, and small
frictions at decision points are most of what process design is. It is the difference between
skipping something and *deciding* to skip it — and you can only be honest with yourself about the
second kind.

**And what it enforces absolutely.** The half it does not have to trust you about: `ruff` either
passes or it does not, `pytest` either goes green or it does not, and the depth check either
satisfies the contract or it does not. That half cannot be rounded up at 11pm.

**The `--force` question.** This gate has no escape hatch, deliberately. An escape hatch used once
becomes the way the command is used. If you genuinely need to defer a box, the honest move is to
edit the checklist and write down *why* — which leaves a trace in the commit — rather than to pass a
flag that leaves none.

---

## Why Mandala needs it

- **Principle 1 is the plan's first rule**, and rules without enforcement decay in exactly the way
  the story describes. This is the enforcement.
- **Principle 7 — evals before features — is the box most worth protecting.** Every day's checklist
  carries a *"break it, watch it go red, fix it"* box, because a test that has never failed is
  unproven. That box is the one the story's engineer ticked without doing, and it is the one that
  cost them three weeks later.
- **Ninety days is long enough for standards to drift.** Day 3 you are careful because it is new.
  Day 55 you are fast because it is familiar. The gate does not get tired, and it applies the same
  standard on both days.
- **Day 89 is README-as-portfolio.** Ninety commits, each one gated, is the artifact. A hiring
  manager reading the history sees a consistent record — which is only worth something if the
  consistency was real.

## The mechanism

Here is the `done` branch of the dispatcher from [3.2](3.2-the-case-dispatcher.md):

```bash
done)
  [ -z "$DAY" ] && { echo "usage: ./m done <day>"; exit 1; }
  D="$(daydir "$DAY")"
  [ -n "$D" ] || { echo "no day folder for $DAY"; exit 1; }
  C="$D/CHECKLIST.md"
  [ -f "$C" ] || { echo "FAIL no $C"; exit 1; }
  if grep -q '^- \[ \]' "$C"; then
    echo "FAIL unticked boxes remain in $C"; grep -n '^- \[ \]' "$C"; exit 1
  fi
  "$0" check
  uv run python scripts/tracker.py
  git add -A && git commit -m "day-$(pad "$DAY"): complete"
  echo "OK day $DAY committed"
  ;;
```

**Line by line:**

- `[ -z "$DAY" ] && { ...; exit 1; }` — the argument check from
  [3.2](3.2-the-case-dispatcher.md). `./m done` with no number is a mistake, not a request.
- `C="$D/CHECKLIST.md"` — the file this gate reads. Naming it in a variable keeps the three later
  references honest; a typo in one of three literal paths would produce a gate that checks a file
  that does not exist and passes.
- `[ -f "$C" ] || { echo "FAIL no $C"; exit 1; }` — **fail closed.** A missing checklist is a
  refusal, never a pass. This is the most important line in the block: a gate whose absence of input
  means "allow" is not a gate. Every security control ever bypassed was bypassed here.
- `grep -q '^- \[ \]' "$C"` — search for unticked boxes. `-q` is **q**uiet: print nothing, just
  exit 0 if there was a match. `^- \[ \]` anchors to the start of a line (`^`), then a literal
  `- `, then `[`, a space, `]` — the brackets escaped with backslashes because `[...]` is a
  character class in a regular expression and would otherwise mean "one of these characters".
- `if grep -q ...; then` — `if` tests the exit status, which is one of `set -e`'s exemptions
  ([3.1](3.1-set-euo-pipefail.md)). Here the exemption is *needed*: a `grep` that finds nothing exits
  1, and without the `if` that would abort the script on the success path.
- `grep -n '^- \[ \]' "$C"` — the same search with `-n` for line **n**umbers, run only on the
  failure path. **The gate does not merely refuse; it prints exactly which boxes are open**, so the
  refusal is actionable rather than annoying. A gate that says "no" without saying "which" is a gate
  people learn to route around.
- `exit 1` — non-zero, so anything wrapping this script sees a failure too.
- `"$0" check` — re-invoke *this same script* with the `check` verb. `$0` is the path the script was
  invoked as, so it works regardless of the current directory. Reusing the verb rather than
  duplicating its commands means `check` and `done` can never drift apart — the same reasoning that
  made `./m` exist at all.
- `uv run python scripts/tracker.py` — regenerate `docs/TRACKER.md` **before** the commit, so the
  progress file and the commit are the same snapshot ([4.2](../04/4.2-the-tracker-you-never-hand-edit.md)).
- `git add -A && git commit -m "..."` — stage everything and commit. `-A` stages deletions as well
  as additions, so a file you removed during the day is actually recorded as removed. `.gitignore`
  is what makes `-A` safe ([2.2](../02/2.2-gitignore-before-the-secret-exists.md)) — without it,
  `-A` is how `.env` gets committed.
- `$(pad "$DAY")` — the zero-padding function, so the commit message reads `day-07: complete` and
  sorts correctly in a log.
- Note there is **no `|| true` anywhere**. Every command in this branch can stop the script, which
  is the entire point of `set -euo pipefail` on line 3.

Watch it refuse, which is the only way to know a gate works:

```bash
printf '# Day 99 - CHECKLIST\n\n- [x] done thing\n- [ ] undone thing\n' > /tmp/CHECKLIST.md
grep -n '^- \[ \]' /tmp/CHECKLIST.md; echo "grep exit status: $?"
```

**Line by line:**

- `printf` writes a two-box checklist, one ticked and one not — the state the gate exists to catch.
- `grep -n` prints `4:- [ ] undone thing`: the line number and the text, which is exactly what the
  gate shows you.
- `$?` is `0`, meaning **grep found something**, which in this gate's logic means *refuse*. Note the
  inversion worth holding onto: a successful search is a failed check. Reading it wrong is an easy
  way to write a gate that passes precisely when it should not.

## When it breaks

**The refusal, working as designed:**

```text
$ ./m done 0
FAIL unticked boxes remain in days/day-00-setup/CHECKLIST.md
47:- [ ] `./m check` prints `OK all green`
52:- [ ] Read 3.3 and can say out loud what makes `./m done` refuse
```

**What it means.** Two boxes are open, at lines 47 and 52. Nothing was committed. This is not an
error to work around — it is the gate doing its job, and the two line numbers are the to-do list.

**The one that means the previous branch left work behind:**

```text
$ ./m done 0
FAIL pytest exited 1
FAILED tests/test_repo_shape.py::test_env_is_not_tracked - AssertionError
```

**What it means.** The checklist passed, so `"$0" check` ran, and a test failed. Nothing was
committed. Notice the ordering: the cheap check (a `grep` over one file) runs before the expensive
one (lint plus the full suite), so the common failure gives you an answer immediately. **Cheap
checks first is a small design decision that decides whether people run the gate at all.**

**The one that looks like the gate is broken:**

```text
$ ./m done 0
OK all green
[main 4f2a1c8] day-00: complete
 21 files changed, 4213 insertions(+)
OK day 0 committed

$ git log --oneline -1
4f2a1c8 day-00: complete
```

...but you had not finished. **What it means.** The gate did exactly what you told it: every box in
the file was `- [x]`. The gate cannot detect a box ticked without the work behind it, and pretending
otherwise would be worse than admitting it. This is the honest boundary from *The idea in plain
language*: the machine enforces the mechanical half absolutely, and the human half is made explicit
and deliberate rather than verified. Knowing precisely which half you are trusting is the whole
skill.

**The one that catches a stale checklist format:**

```text
$ ./m done 4
OK all green
[main 9c3e5a1] day-04: complete
```

...on a day whose checklist you know had open boxes. **What it means.** The boxes are not written in
the form the `grep` matches — indented, or `-[ ]` without the space, or `* [ ]` with an asterisk.
The pattern `^- \[ \]` is anchored and literal, so a variation slips past silently. This is the
classic weakness of a regex-based gate: **it fails open on input it does not recognise.** The
defence is that the checklist format is fixed by the plan's Part 11 and generated by the `/day`
skill, so the shape is not a matter of taste — and if you hand-write a checklist, match the format
exactly.

## In production

**"Fail closed" is the principle this gate is built on, and it generalises far past shell scripts.**
A missing checklist refuses. A missing test result refuses. When a control cannot determine the
answer, the safe default is *deny*, not *allow*. Every serious deployment gate works this way: if
the security scan did not report, the deploy does not proceed. The failure mode that gets people is
always a check that silently passes when its input is absent — an empty test report read as zero
failures, a linter that exits 0 when it cannot find its config.

**This is a local gate, and local gates are bypassable — by design.** `git commit` directly, and
nothing stops you. That is not a flaw, because the *purpose* of a local gate is to be fast and to
catch honest mistakes, not to constrain a determined person. Real enforcement lives where you cannot
reach it: branch protection on the remote, a required CI check, a review. **Day 2 builds the CI
rung** and **Day 74 makes the eval suite a required check**. The professional model is three rungs —
editor, local gate, CI — each slower, each harder to bypass, and each catching what the one before
it missed.

**Human approval gates are the same mechanism applied to agents, and they are this plan's spine.**
By **Day 50** you build LangGraph's `interrupt()`: the graph *stops*, durably, and waits for a human
before an external write. By **Day 82** that gate stands between your capstone and its first real
side effect, and Principle 12 says no agent performs an external side effect without it until the
graduated-autonomy review on Day 84. **`./m done` is the toy version of the most important pattern
in the whole curriculum**: something valuable is withheld until a condition is met, the refusal is
explicit and legible, and there is no quiet path around it.

**What the checklist really is, in production terms.** It is a **definition of done**, checked at the
moment work is claimed complete — the same artifact as a release checklist, a change-management
approval, or the pre-merge criteria on a pull request. The reason these are written down rather than
remembered is precisely the story: standards under time pressure drift downward, and a written list
applied by a machine does not have a bad evening.

**What degrades at scale.** Gates that are slow get bypassed, and gates that are noisy get ignored —
both failures are social, not technical. Teams respond by making gates fast (cheap checks first,
incremental runs, caching) and specific (name the failing line, never "check failed"). Notice that
this forty-line branch already does both: `grep` before `pytest`, and `grep -n` so the refusal names
its lines.

**The review comment a senior engineer leaves.** On a CI step ending in `|| true`: *"This makes the
step advisory — it will never fail the build. Was that intentional? If the check is not worth
failing on, delete it; a check that cannot fail is worse than none because it looks like coverage."*
And on a gate that skips when its config is missing: *"Fail closed here. Right now, deleting the
config file is enough to disable the check, and nobody will notice."*

**The interview question.** *"What is the difference between a check and a gate?"* The answer: a
check reports, a gate refuses — and the design questions that follow are *what does it do when it
cannot determine the answer* (fail closed), *can it be bypassed and by whom* (locally yes,
deliberately; on the protected branch no), and *does its refusal tell you what to fix* (name the
line, not the category). A candidate who volunteers "and I would make the cheap check run first so
the common failure is fast" has clearly built one.
