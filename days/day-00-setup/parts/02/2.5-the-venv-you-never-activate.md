# 2.5 — The `.venv` you never activate

## One-line answer

`uv sync` creates a `.venv/` folder holding this project's interpreter and packages, and this
project **never activates it** — because activation is an invisible change to your shell that you
can forget, while `uv run` states the environment explicitly on every single command.

---

## The story

Someone is debugging a failing test at the end of a long day. They have four terminal tabs open —
one running a server, one tailing logs, one for git, one for running the test.

In the test tab they fix the bug and the test passes. They switch to the git tab, commit, push.

CI fails. Same test.

They re-run it locally. It passes. They re-run CI. It fails. They read the CI logs line by line
looking for an environment difference, find nothing meaningful, and start to suspect the CI runner.

Twenty minutes later they notice something in the *git* tab's prompt that is not in the *test*
tab's: the test tab's prompt begins `(.venv)`. The git tab's does not.

The tab where the test passed had the project environment active. The tab where they ran everything
else did not. When they had earlier run an install command from the git tab, it went somewhere else
entirely. Their passing test and their commit came from two different environments, and CI —
correctly — used the one described by the committed files.

Nothing here was incompetence. Activation is a state you cannot see unless you look for a
parenthesis in a prompt, and it is per-terminal, so having four terminals means having four
independent chances to be wrong.

---

## The idea in plain language

**What `.venv/` actually is.** A folder created by `uv sync`, containing three things:

- a link (or a small copy) of the Python interpreter this project uses,
- a `site-packages/` folder holding exactly the packages in `uv.lock`,
- a `Scripts/` folder on Windows (`bin/` on macOS and Linux) with executables like `pytest` and
  `ruff`.

That is the whole "virtual environment" concept from
[1.1](../01/1.1-why-one-tool-must-own-the-environment.md), made concrete. It is not a container, not
a sandbox, and not isolated from your filesystem. It is one interpreter plus one package folder,
sitting in your project.

**What "activating" does.** The `activate` script modifies your *current shell*: it puts
`.venv/Scripts` at the front of `PATH` and sets a variable named `VIRTUAL_ENV`. After that, typing
`python` finds the one in `.venv` first, because `PATH` is searched in order. It is a `PATH` edit
and nothing more — there is no magic and no isolation being switched on.

Three properties follow, and together they are the argument of this part:

1. **It is per-shell.** A new terminal starts fresh. Four tabs, four independent states.
2. **It is invisible except by convention.** The `(.venv)` prefix is a courtesy the script adds to
   your prompt. Some shells and setups do not show it. Nothing enforces it.
3. **It is stateful.** Whether a command works depends on something you did earlier, in this
   terminal, possibly hours ago.

**Why this project refuses it.** Every command in these ninety days begins with `uv run`, which:

- verifies `.venv/` matches `uv.lock`, syncing if not,
- then executes the command inside that environment,
- without touching your shell's `PATH` at all.

The environment is therefore named on **every** command, not established once and remembered. It is
the difference between a stateful ritual and a stateless statement — and stateless is what you want
from anything that can be silently wrong. It also means a command pasted from a lesson works
regardless of which terminal you paste it into, which matters when the lessons are the primary
interface.

**A useful comparison, because you will meet both:**

| | activate + `python` | `uv run python` |
|---|---|---|
| Environment chosen by | shell state set earlier | the command itself |
| Works in a fresh terminal | no | yes |
| Works in a script or CI | only if you re-activate | yes |
| Stale environment possible | yes, silently | no, it syncs first |
| Visible in the command | no | yes |

The last row is the one that matters most in a project taught through documents: a lesson containing
`uv run pytest` is complete, while a lesson containing `pytest` is complete only if you also
remember a step from an earlier page.

## Why Mandala needs it

- **`./m` runs non-interactively.** It executes `uv run ruff`, `uv run pytest` and
  `uv run python scripts/...` ([3.2](../03/3.2-the-case-dispatcher.md)). A script cannot rely on
  whether the human who invoked it happened to activate something first.
- **Day 74 puts the same commands in CI**, where there is no interactive shell and nobody to
  activate anything. Commands that work identically in both places mean CI failures are real
  failures rather than environment differences — the whole value of the regression gate.
- **Every lesson's Setup block must be copy-pasteable into a fresh terminal**, because that is how
  you will actually use them. An instruction that only works after an earlier, invisible step is a
  documentation bug.
- **The story is expensive here specifically.** Every model call costs a free-tier request
  (Principle 5). Debugging a failure that is actually an environment mismatch burns quota you cannot
  buy back, and burns it on a question that has nothing to do with agents.

## The mechanism

Create the environment from the committed files:

```bash
uv sync
```

**Line by line:**

- Reads `pyproject.toml` and `uv.lock` ([2.4](2.4-uv-init-pyproject-and-the-lockfile.md)) and makes
  `.venv/` match them exactly — installing what is missing and **removing what should not be
  there**. That removal is what makes it a *sync*: an environment cannot drift as the project
  changes.
- It creates `.venv/` if it does not exist. You never run a separate "create the environment"
  command.
- It is idempotent. Run it twice and the second run does nothing, quickly.

Look inside, because seeing the folder removes the mystery permanently:

```bash
ls .venv && ls .venv/Scripts | head -12
```

**Line by line:**

- `ls .venv` — you will see `Scripts/` (or `bin/`), `Lib/` (or `lib/`), and `pyvenv.cfg`. That last
  file is a three-line text file naming the base interpreter this environment was built from — the
  entire "which Python is this?" question, answered in plain text.
- `ls .venv/Scripts` — the executables the environment provides: `python`, `pytest`, `ruff`, and
  `activate`. **`activate` is right there and this project simply never runs it.**
- `head -12` — first twelve lines only; the full list is long and the shape is the point.

Now prove the two paths are the same environment, which is the claim that lets you stop worrying:

```bash
uv run python -c "import sys; print(sys.executable)"
uv run python -c "import sys; print(sys.prefix); print(sys.base_prefix)"
```

**Line by line:**

- `sys.executable` — the interpreter actually running. It must be a path inside this project's
  `.venv`.
- `sys.prefix` — the root of the environment in use: your `.venv`.
- `sys.base_prefix` — the root of the interpreter the environment was *built from*: the `uv`-managed
  3.12 from [1.3](../01/1.3-uv-the-one-binary-that-owns-the-environment.md). **When these two differ
  you are inside a virtual environment; when they are equal you are not.** That is the precise,
  programmatic test, and it beats looking at your prompt.

And confirm your shell is *not* activated, which is the state this project wants:

```bash
echo "VIRTUAL_ENV=${VIRTUAL_ENV:-<not set>}"
```

**Line by line:**

- `${VIRTUAL_ENV}` — the variable the `activate` script sets. Reading it is how tools detect
  activation.
- `${VIRTUAL_ENV:-<not set>}` — the `:-` form means "use this default if the variable is unset or
  empty". Without it, `set -u` (which you meet in
  [3.1](../03/3.1-set-euo-pipefail.md)) would abort on an undefined variable.
- **`<not set>` is the correct answer here.** If it prints a path, some tool activated the
  environment for you — commonly an editor's integrated terminal, which is why
  [1.5](../01/1.5-the-editor-and-the-interpreter-it-picks.md) sets
  `python.terminal.activateEnvironment: false`. Nothing will break, but you have gained an invisible
  state you did not choose.

## When it breaks

**The classic, and the reason people reach for activation in the first place:**

```text
$ pytest
bash: pytest: command not found
```

**What it means.** `pytest` lives in `.venv/Scripts/`, which is not on your `PATH` because you never
activated. This is not a problem to solve — it is the design working. The command is
`uv run pytest`. If you find yourself wanting to activate so that bare `pytest` works, remember the
story: the convenience is exactly the invisibility.

**The stale environment, which activation permits and `uv run` does not:**

```text
$ source .venv/Scripts/activate
(.venv) $ python -c "import crewai"
ModuleNotFoundError: No module named 'crewai'
```

...even though `pyproject.toml` lists it. **What it means.** Someone added the dependency (or you
pulled a commit that did) and `.venv/` has not been synced since. Activation gives you whatever the
folder contains right now, however old that is. `uv run` would have re-synced before running,
because checking the lockfile is part of what it does. Fix with `uv sync` — and note that you had to
*know* to do that, which is the cost of activation.

**The one from the story, reproduced deliberately so you recognise the shape:**

```text
$ echo "VIRTUAL_ENV=${VIRTUAL_ENV:-<not set>}"
VIRTUAL_ENV=/c/Users/me/OneDrive/Desktop/Projects/other-project/.venv
```

**What it means.** This terminal has *another* project's environment active — you activated it
earlier, in this tab, and then changed directory. Every bare `python` and `pip` in this tab now
talks to the wrong project. `deactivate` restores the shell. `uv run` was never affected, because it
does not consult `PATH`.

**The one that is not about activation at all, and is worth telling apart:**

```text
$ uv run pytest
error: Failed to spawn: `pytest`
  Caused by: program not found
```

**What it means.** `uv run` looked inside `.venv/` and `pytest` genuinely is not installed. Not a
`PATH` problem — a *dependency* problem. `pytest` is in the `dev` group
([2.4](2.4-uv-init-pyproject-and-the-lockfile.md)), so this appears if the environment was built
with `--no-dev`. `uv sync` restores it. Distinguishing "not on PATH" from "not installed" quickly is
worth the ten seconds it takes to read which tool produced the error.

## In production

**Nobody activates anything in production, and the reasons generalise.** A container image has one
Python and one set of packages, so there is nothing to switch between — activation is a solution to a
problem containers remove by construction. A systemd unit or a Kubernetes manifest names an absolute
interpreter path. CI runners invoke tools explicitly. **The interactive convenience does not survive
contact with automation**, which is a good reason to not build habits on it.

**`.venv/` is never committed, and never copied between machines.** It contains absolute paths
baked in at creation time, platform-specific compiled files, and is often hundreds of megabytes.
That is why it is in `.gitignore` ([2.2](2.2-gitignore-before-the-secret-exists.md)). The
reproducible artifacts are `pyproject.toml` and `uv.lock`; `.venv/` is derived and disposable.
Deleting it and running `uv sync` is a completely routine repair, and it is worth doing once
deliberately so that it stops feeling drastic.

**"Works on my machine" is usually this.** A developer's shell has accumulated state — an activated
environment, an exported variable, a tool installed globally months ago — that is not described
anywhere. The professional response is to make the environment *declarative*: everything the code
needs is in files, and running it states its own context. `uv run` is a small instance of that
principle, and containers are the large one. **Day 19's sandbox and Day 85's deployment are the same
idea at a bigger scale**: nothing implicit, nothing remembered.

**Where activation still earns its place.** Interactive exploration — a REPL session, a notebook
kernel, a long debugging sitting where you will type `python` fifty times — is a genuinely
reasonable use. The discipline is knowing you have done it, and never letting a *documented* or
*automated* step depend on it. If a README says `pytest`, it is relying on the reader's shell state;
if it says `uv run pytest`, it is not.

**What degrades at scale.** With many services on one machine — or one CI runner building several
projects — implicit environment state becomes a genuine class of bug: a job that passes only because
a previous job on the same runner left something behind. This is why CI runners are ephemeral by
default, and why "it only fails on the second run" is a smell worth chasing rather than retrying.

**The review comment a senior engineer leaves.** On a README that begins "activate the venv, then
run the tests": *"Can we make these commands work from a fresh shell? Right now step 2 silently
depends on step 1 having happened in the same terminal, and that is the first thing a new joiner
gets wrong."* And on a CI script that sources `activate`: *"Invoke the tools by path or through the
runner instead — activation in a non-interactive shell is a stateful step we cannot verify from the
logs."*

**The interview question.** *"What does activating a virtual environment actually do?"* The answer
that lands is mechanical, not conceptual: it prepends the environment's `bin`/`Scripts` directory to
`PATH` and sets `VIRTUAL_ENV`; it is a per-shell mutation with no isolation properties whatsoever.
The follow-up worth volunteering: *"which is why I prefer a runner that names the environment on
each command — the state cannot be forgotten, and the same command works in a terminal, a script and
CI."*

## Check yourself

```bash
uv run python -c "import sys; print(sys.prefix != sys.base_prefix, sys.executable)" && echo "VIRTUAL_ENV=${VIRTUAL_ENV:-<not set>}"
```

The first must print `True` and a path inside this project's `.venv`. The second should print
`<not set>` — your shell is clean, and `uv run` did the work.
