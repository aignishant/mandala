# 2.4 — `uv init`, `pyproject.toml`, and the lockfile

## One-line answer

`pyproject.toml` records what you **asked for** and `uv.lock` records what you **got** — and
committing both is the only way a project can be rebuilt identically on another machine, which is
what Principle 4 means when it says *pin everything*.

---

## The story

A team ships a service. It has been stable for months. Nobody has touched it.

On a Wednesday, the deploy pipeline runs — triggered by an unrelated change to a README — and the
new container starts crashing on boot with a validation error deep inside a library nobody on the
team wrote.

There is no code change. `git log` shows a one-line documentation edit. The service that worked on
Tuesday and the service that fails on Wednesday come from commits that differ by one sentence of
prose.

What differed was not the code. It was the build. The Dockerfile installed dependencies with a
loose constraint, so every build resolved fresh against the package index. Overnight, a
sub-dependency four levels down had published a new minor version that tightened a validation rule.
Tuesday's build got the old one. Wednesday's got the new one. Both builds were "correct"; they were
simply builds of different software.

The team spent the morning discovering that "we did not change anything" and "the software did not
change" are different statements — and that only one of them was true.

---

## The idea in plain language

**`pyproject.toml` is the manifest.** It is the standard file that describes a Python project: its
name, the Python it needs, the packages it *directly* depends on, and configuration for the tools
that operate on it. It is written by humans, reviewed by humans, and it records **intent**.

**`uv.lock` is the lockfile.** It records the **outcome** of resolving that intent: every package in
the final tree — direct dependencies, their dependencies, and so on all the way down — at one exact
version each, with a cryptographic hash of every file. It is written by machines, read by machines,
and committed so that the machine on the other side gets the same answer.

The distinction is the whole part, so state it plainly: **you declare four packages and get sixty.**
The manifest names the four. The lockfile names all sixty. The story happened to a team that
committed only the first file.

**Why hashes are in there.** A version number is a label the publisher controls. A hash is derived
from the bytes. If a package is republished under the same version — through a maintainer mistake,
an account compromise, or a deliberate attack — the version matches and the hash does not, so the
install fails loudly instead of silently substituting different code. That is the difference between
pinning a *name* and pinning *content*.

**What TOML is.** `pyproject.toml` is written in TOML — a configuration format built for exactly
this: sections in square brackets, `key = value` inside them, strings in quotes, lists in square
brackets. It was chosen over JSON because it allows comments, and over YAML because its
indentation-free syntax has fewer ways to be subtly wrong.

**The three groups of packages**, which matter because they end up in different places:

| Group | Declared in | Installed in production? |
|---|---|---|
| runtime dependencies | `[project] dependencies` | yes — the code needs them to run |
| development dependencies | `[dependency-groups] dev` | no — linters, test runners, notebook kernels |
| build dependencies | `[build-system] requires` | only during the build |

Keeping them separate is not tidiness. A production container that ships a test framework and a
linter is larger, slower to pull, and has a wider attack surface than one that does not.

**And the rule this project runs on:** packages are added **on the day they are first used**, with
`uv add "name==exact"`, never up front and never with a loose constraint. The manifest is then a
readable record of when each capability entered the project, and the lockfile is regenerated in the
same command so the two cannot drift apart.

---

## Why Mandala needs it

- **Principle 4 has no exceptions**, and it names the reason: a silent default-model change broke
  someone's evals overnight. That is the story at the top of this page in a different costume —
  something moved that nobody chose to move. A lockfile removes the package half of that risk
  entirely.
- **Four frameworks in one environment (Phase 9).** By Day 62, the Agents SDK, CrewAI, LangChain
  and LangGraph are installed together and share dependencies with overlapping requirements. The
  bake-off compares them fairly *only* because all four resolve against one locked environment. Four
  separate loose installs would make every difference ambiguous.
- **Day 19 and Day 85 build container images**, and both install with `uv sync --frozen`. That flag
  says "install exactly the lockfile and fail if it disagrees with the manifest" — which is
  precisely the guard the story's team did not have.
- **Day 74's CI regression gate has to be trustworthy.** A red build must mean "you broke
  something", never "the index moved". Without a lockfile, CI is a random variable, and a flaky
  gate gets ignored — at which point you have the maintenance cost of a gate with none of the
  benefit.

## The mechanism

If the project has no `pyproject.toml` yet, create one:

```bash
uv init --python 3.12 --no-readme
```

**Line by line:**

- `uv init` — write a minimal `pyproject.toml` for the current directory, using the folder name as
  the project name.
- `--python 3.12` — set `requires-python` to this version
  ([1.4](../01/1.4-python-3-12-and-why-nothing-floats.md)) instead of whatever happens to be
  installed.
- `--no-readme` — skip generating a placeholder README, because this project has a real one that
  says something.
- If `pyproject.toml` already exists, `uv init` refuses rather than overwriting. That refusal is
  correct: this file is hand-maintained, and a tool that clobbered it would be losing decisions.

Open the file and read it. This repository's version, with the parts that matter:

```toml
[project]
name = "mandala"
version = "0.1.0"
requires-python = "==3.12.*"
dependencies = [
    "openai==3.3.1",
    "python-dotenv==1.2.3",
]

[dependency-groups]
dev = [
    "pytest==9.1.1",
    "ruff==0.16.3",
    "pre-commit==4.6.2",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/mandala"]

[tool.uv]
link-mode = "copy"
```

**Line by line:**

- `[project]` — the standardised section. Any conforming tool reads it identically, which is why it
  is not `[tool.uv.project]`.
- `name = "mandala"` — must match the package directory `src/mandala/`
  ([2.1](2.1-the-folder-skeleton.md)), or `import mandala` will not resolve to what you expect.
- `version = "0.1.0"` — required by the standard. This project is not published, so the number is
  ceremonial; a library would bump it on every release.
- `requires-python = "==3.12.*"` — from
  [1.4](../01/1.4-python-3-12-and-why-nothing-floats.md): any 3.12 patch, nothing else.
- `dependencies = [...]` — the runtime list, every entry with `==`. `openai` is here because Day 3
  calls it directly, pointed at a free provider's OpenAI-compatible endpoint; `python-dotenv` reads
  `.env` from Day 1.
- `[dependency-groups] dev` — tools you need to *develop* and never to *run*. `uv sync` installs
  them locally; `uv sync --no-dev` in a container leaves them out.
- `[build-system]` — how the project is turned into an installable package. `hatchling` is the build
  backend; you will never invoke it directly, but it is what makes `import mandala` work after
  `uv sync`.
- `[tool.hatch.build.targets.wheel] packages = ["src/mandala"]` — tells the backend that the package
  lives under `src/`. **This is the line that makes the `src` layout work**; without it the backend
  looks for `mandala/` at the root and finds nothing.
- `[tool.uv] link-mode = "copy"` — from
  [1.3](../01/1.3-uv-the-one-binary-that-owns-the-environment.md): this repository sits in a
  OneDrive folder, which refuses hardlinks, so `uv` copies from its cache instead. Slower and
  correct. **Note that the reason is written in a comment in the real file** — a setting whose
  rationale is not recorded is a setting someone will delete.

Now add a package the way this project always adds packages:

```bash
uv add "python-dotenv==1.2.3"
```

**Line by line:**

- `uv add` — resolve, install, write the pin into `pyproject.toml`, **and** update `uv.lock`, as one
  step. That atomicity is the point: there is no window in which the two files disagree.
- `"python-dotenv==1.2.3"` — quoted so the shell does not try to interpret `==`. Exact version, per
  Principle 4.
- To add a development tool instead, the flag is `--dev`: `uv add --dev "ruff==0.16.3"`.

Look at what the lockfile actually records:

```bash
grep -c "^\[\[package\]\]" uv.lock && grep -A3 'name = "python-dotenv"' uv.lock | head -8
```

**Line by line:**

- `grep -c "^\[\[package\]\]"` — count the lines starting a package entry. `[[package]]` is TOML's
  syntax for an array of tables — one entry per package. **The number will be far larger than the
  list in `pyproject.toml`**, and that gap is the entire reason the lockfile exists.
- `-A3` — print three lines **a**fter each match, so you see the version and source alongside the
  name.
- `head -8` — stop after eight lines, because you want the shape rather than the whole file.
- What you are looking at is the record of *outcome*: the exact version resolved, where it came
  from, and (further down each entry) the hashes.

Finally, prove reproducibility — the claim the whole part rests on:

```bash
uv sync --frozen
```

**Line by line:**

- `uv sync` — make `.venv/` match the lockfile exactly: install what is missing, remove what should
  not be there.
- `--frozen` — **do not re-resolve.** Install precisely what `uv.lock` says, and fail if it is out
  of date with respect to `pyproject.toml`. Locally this is a consistency check; in a Dockerfile it
  is the difference between a reproducible image and a lottery ticket. **This is the flag the story's
  team was missing.**

## When it breaks

**The lockfile that has drifted from the manifest:**

```text
$ uv sync --frozen
error: The lockfile at `uv.lock` needs to be updated, but `--frozen` was provided.
To update the lockfile, run `uv lock`.
```

**What it means.** Someone edited `pyproject.toml` by hand — added a package, changed a pin — and did
not regenerate the lock. `--frozen` refuses to paper over it. This is the failure working exactly as
designed, and it is why `uv add` (which updates both) is preferred over hand-editing.

**The resolution that cannot be satisfied:**

```text
$ uv add "crewai==1.15.6"
  × No solution found when resolving dependencies:
  ╰─▶ Because langchain-core==1.6.0 depends on pydantic>=2.14 and crewai==1.15.6 depends on
      pydantic<2.13, we can conclude that crewai==1.15.6 and langchain-core==1.6.0 are
      incompatible.
```

**What it means.** Read it as a proof, because that is its form: it names both constraints and the
package they collide on, and asserts that no assignment satisfies both. The tempting fix — loosen a
pin until the error goes away — is exactly wrong. Under Principle 14, a real conflict between two
pinned frameworks is **ecosystem reality disagreeing with the plan**, and it is logged in
`docs/CHANGELOG_PLAN.md` as an amendment *before* any version moves. Silently unpinning to make a
message disappear is how a project ends up in the story at the top of this page.

**The one that means the `src` layout is not wired up:**

```text
$ uv run python -c "import mandala"
ModuleNotFoundError: No module named 'mandala'
```

...even though `src/mandala/__init__.py` exists. **What it means.** The build backend does not know
where to look. Check for `[tool.hatch.build.targets.wheel] packages = ["src/mandala"]`. Without it,
hatchling searches for a top-level `mandala/`, finds nothing, and builds an empty package — which
installs successfully and imports as nothing. A successful install of an empty package is a
particularly annoying failure, because every step reported success.

**The one that appears in someone else's clone and never in yours:**

```text
$ uv sync
error: Distribution `some-package==2.1.0` has no matching hash in the lockfile
```

**What it means.** The file downloaded from the index does not match the hash recorded when the lock
was generated. Occasionally this is a mirror or proxy serving a rebuilt file; occasionally it is the
supply-chain attack this mechanism exists to catch. Either way the correct response is to **stop and
investigate**, not to regenerate the lockfile to make the error go away. Regenerating replaces the
hash you can no longer verify with the hash of whatever you just downloaded, which converts a
detection into a silent acceptance.

## In production

**The lockfile is the deployable input.** A production Dockerfile copies `pyproject.toml` and
`uv.lock` first, runs `uv sync --frozen --no-dev`, and only then copies the source. The ordering is
deliberate: dependencies change rarely and source changes constantly, so putting dependencies in an
earlier layer means the expensive install is cached across builds. `--no-dev` leaves the linter and
test framework out of the shipped image. You write this on **Day 19** and again on **Day 85**.

**Reproducibility is a security property, not only a convenience.** If you cannot rebuild the exact
artifact that is running, you cannot answer "does this deployment contain the vulnerable version?"
during an incident — and that question arrives with a deadline attached. Lockfiles are also the
input to SBOM generation (a software bill of materials, the machine-readable inventory increasingly
required in regulated industries) and to automated CVE scanning. All three capabilities rest on
having an exact, committed list.

**Dependency updates become a scheduled, reviewed activity.** With loose constraints, updates happen
to you at random. With a lockfile, `uv lock --upgrade` produces a *diff* — a pull request showing
exactly which versions moved — that CI tests before a human approves it. Teams automate the proposal
and keep the approval, which is the right split. This is the same discipline as Principle 13's
**Friday freshness check**: changes are read and decided on, not absorbed silently.

**What a lockfile still does not pin, and this project cares a lot.** Model identifiers. A provider
can retire a model or rotate a free-tier roster without notice, and no packaging discipline helps.
That is the other half of Principle 4 — *every agent sets `model=` explicitly* — so the model is an
auditable value in your code rather than a framework default, and a retirement produces a clear
error naming the model instead of a silent behaviour change. **Day 6's fallback router** is the
mechanism that turns that error into a degraded-but-working system, and `docs/RATE_BUDGET.md` is
where the live limits are recorded because they are not in any lockfile either.

**What degrades at scale.** In a monorepo of many services, resolution time and lockfile conflicts
become real friction: two pull requests that both add a dependency produce a merge conflict in a
machine-generated file that nobody can usefully review. Teams respond with per-service lockfiles,
merge drivers that regenerate rather than merge, and update automation that batches changes. The
underlying rule does not change — commit the outcome — but the tooling around it has to grow.

**The review comment a senior engineer leaves.** On a pull request touching `pyproject.toml` with no
lockfile change: *"Lockfile not regenerated — this changes what we ask for but not what we get, so
CI is testing a different tree than production will run."* And on a Dockerfile using `uv sync`
without `--frozen`: *"Add `--frozen`, otherwise a stale lockfile re-resolves at build time and the
image silently stops matching the commit."*

**The interview question.** *"Your service worked yesterday and fails today with no code change.
What is your first hypothesis?"* The answer they want is the story: something outside your commits
moved — a dependency resolved differently, a base image tag advanced, a model id was retired.
Follow it with the diagnosis (compare the resolved dependency tree between the two builds) and the
prevention (lockfile committed, `--frozen` in the build, pinned base image tag). Being able to say
*"'we did not change anything' and 'the software did not change' are different statements"* is the
sentence that ends this question.

```bash
uv sync --frozen && grep -c "^\[\[package\]\]" uv.lock && uv run python -c "import mandala; print('package imports')"
```

`--frozen` must succeed (manifest and lock agree), the package count must be larger than the
dependency list in `pyproject.toml`, and the import must work.
