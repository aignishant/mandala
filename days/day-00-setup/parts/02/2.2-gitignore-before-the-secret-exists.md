# 2.2 — `.gitignore` before the secret exists

## One-line answer

`.gitignore` is written **before** the first API key exists, because git's history is append-only:
a secret that is committed once is in the repository forever, even after you delete it, and the only
reliable fix is to treat the key itself as compromised.

---

## The story

A developer is building a side project over a weekend. It talks to three APIs. The keys live in a
file called `config.py` because that was the fastest thing that worked on Friday night.

On Sunday they clean it up properly: keys move into environment variables, `config.py` reads from
the environment, `.gitignore` gets a line for the file that holds them. Textbook. They commit the
improvement with the message "move secrets to env vars" and push.

Nine minutes later, one of the providers emails them. The key has been disabled. Automated scanning
found it in a public repository.

They are baffled, because they *removed* it. The file with the key in it is not in the repository
any more — they can see that it is not there.

What they had not internalised is that git does not store the current state of your files. It stores
**every state they have ever been in**, as a chain of commits, and a public repository publishes the
whole chain. Friday night's commit is still there, exactly as it was, with the key in it, reachable
by anyone who clones. Sunday's commit did not delete Friday's; it added a new one on top.

They were lucky. The provider's scanner found it before anyone else did, and the account had spending
limits. Both of those are luck, not process.

---

## The idea in plain language

**Git's history is append-only.** A commit is a permanent snapshot. Later commits add to the chain;
they do not modify earlier ones. So the correct mental model is not "the repository contains my
files" but "the repository contains every version of my files, forever". Deleting a file is a new
commit that says *from here on, this file is absent* — and says nothing at all about the commits
before it.

**Therefore the only reliable protection is to never commit the secret in the first place.** Which
means the ignore rule has to exist *before* the file does. Written afterwards, it is a rule that
protects you from a future you have already left.

**What `.gitignore` actually does.** It is a plain text file listing patterns. Any *untracked* file
matching a pattern is invisible to git: it will not show in `git status`, and `git add -A` will not
pick it up. The word **untracked** is the load-bearing part — `.gitignore` has no effect on a file
git is already tracking. Add a file, commit it, *then* add it to `.gitignore`, and git keeps
tracking it and keeps committing your changes to it. This surprises people at the worst possible
moment, and it is the reason for the ordering rule at the top of this part.

**Two categories belong in there, and they are opposites in every way but one:**

| Category | Example | Why not committed |
|---|---|---|
| **Secret** | `.env` | Committing it is a security incident |
| **Regenerable** | `.venv/`, `__pycache__/`, `.ruff_cache/` | Committing it is noise: large, machine-specific, and reproducible from files you *did* commit |

Both are excluded, for completely different reasons. Conflating them is how `.env` ends up feeling
like a tidiness issue rather than a security one.

**And the file that *is* committed: `.env.example`.** Real secrets live in `.env`, which is ignored.
Next to it sits `.env.example`, which is committed and contains **the names with no values**:

```text
GEMINI_API_KEY=
GROQ_API_KEY=
```

This solves a real problem. Without it, a person cloning the repository has no way to know which
environment variables the project expects — they discover them one `KeyError` at a time. With it,
the *shape* of the configuration is documented and reviewable while the *values* never leave anyone's
machine. It is the single most useful convention in this part.

**Pattern syntax, briefly, because the details bite:**

| Pattern | Matches |
|---|---|
| `.env` | a file *or folder* named `.env`, at any depth |
| `.env*` | `.env`, `.env.local`, `.env.production` — **and `.env.example`**, which you wanted to keep |
| `!.env.example` | re-include this specific file after a broader rule excluded it |
| `.venv/` | only a *directory* named `.venv` — the trailing slash is what says "directory" |
| `*.db` | any file with that extension, at any depth |
| `/data` | a `data` entry **at the repository root only** — a leading slash anchors the pattern |

The `.env*` row is a live trap: the natural instinct is to write `.env*` for thoroughness, and it
silently excludes the example file you meant to publish.

---

## Why Mandala needs it

- **Day 1 creates three real API keys** — Gemini, Groq and OpenRouter — and puts them in `.env`.
  That is tomorrow. The ignore rule must exist today, before there is anything to protect, because
  after tomorrow it is too late to have been careful.
- **This project runs on free tiers with no card on file (Principle 5).** That changes the *shape*
  of a leak rather than removing it. A leaked key cannot run up a bill, but it can burn your daily
  quota — and there is no way to buy your way out of an exhausted free tier at 11pm. A stolen key
  means your evening is over.
- **`.env` is not the only secret by Day 66.** Least privilege and credential scoping (AG-17) mean
  several narrowly-scoped credentials, each mounted only where it is needed. The permission table
  you publish on Day 70 is a claim about which process holds which secret, and it is worthless if
  the secrets are also in the git history.
- **Day 74's CI regression gate runs on GitHub Actions with no keys present.** Every test in CI is
  offline or replayed from a cassette. That is only possible because secrets were never in the
  repository — CI cannot leak what it does not have.

## The mechanism

Write the file **now**, before `git init` and long before any key exists:

```bash
cat > .gitignore <<'EOF'
# ---- secrets: never, under any circumstances ----
.env
.env.local
!.env.example

# ---- the environment: regenerable from pyproject.toml + uv.lock ----
.venv/

# ---- python bytecode and tool caches ----
__pycache__/
*.py[cod]
.pytest_cache/
.ruff_cache/

# ---- local model / vector / db artifacts (Days 46, 54) ----
.chroma/
*.db
*.sqlite3

# ---- editor and OS noise ----
.DS_Store
.idea/
EOF
```

**Line by line:**

- `cat > .gitignore <<'EOF'` — a **heredoc**: everything up to the line reading `EOF` becomes the
  file's contents. `>` truncates any existing file first.
- `<<'EOF'` with **quoted** `EOF` — the quotes stop the shell expanding anything inside. Without
  them, a `$` or a backtick in the text would be interpreted as a variable or a command. Quote the
  delimiter by default; you almost never want the alternative.
- `.env` — the file Day 1 creates. No slash and no wildcard: matches a `.env` at any depth, which is
  what you want, since a stray `.env` in a subfolder is just as dangerous.
- `.env.local` — the conventional name for personal overrides, listed explicitly rather than reaching
  for `.env*` and destroying the next line.
- `!.env.example` — `!` **re-includes** a path that an earlier pattern excluded. Harmless here since
  nothing above matches it, and it is written down deliberately: it documents the intent, and it
  survives someone later "tidying" the two lines above into `.env*`.
- `.venv/` — the environment. Trailing slash means directory only. It is large, full of absolute
  paths that are wrong on any other machine, and reproducible with `uv sync` — three independent
  reasons.
- `__pycache__/` and `*.py[cod]` — compiled bytecode. `[cod]` is a character class matching one of
  `c`, `o`, or `d`, covering `.pyc`, `.pyo` and `.pyd` in one pattern.
- `.pytest_cache/`, `.ruff_cache/` — tool caches. Regenerable, and they change on every run, so
  committing them means every commit contains noise.
- `.chroma/`, `*.db`, `*.sqlite3` — local data stores. Day 46 writes vectors, Day 54 builds
  `ticket-db`, and Day 47 checkpoints graph state to SQLite. All regenerable; all potentially large.
- `.DS_Store`, `.idea/` — macOS finder metadata and JetBrains project files. Personal to a machine,
  useful to nobody else.

Now the companion file, which **is** committed:

```bash
cat > .env.example <<'EOF'
# Names only. Never values. Copy to .env (which is gitignored) and fill it in.
# Day 1 creates all three. Every one is a free tier; no card on file, ever.
GEMINI_API_KEY=
GROQ_API_KEY=
OPENROUTER_API_KEY=

# Day 73. Free LangSmith developer tier. Optional.
LANGSMITH_API_KEY=
LANGSMITH_TRACING=false
EOF
```

**Line by line:**

- The comment header states the rule *in the file*, so someone who opens it without reading this
  lesson still learns the convention.
- `GEMINI_API_KEY=` — name, equals sign, nothing. The empty value is the point: this file documents
  shape, never content.
- The Day-73 block shows that not every variable is needed on Day 1. Naming the day a variable
  becomes relevant turns the file into a small map of the project's external dependencies.

**Verify the rule works before you trust it.** Do not assume — test it with a decoy:

```bash
echo "GEMINI_API_KEY=not-a-real-key" > .env
git status --porcelain
git check-ignore -v .env
```

**Line by line:**

- `echo ... > .env` — create a fake `.env` with an obviously fake value. This is a rehearsal, so use
  a value that is unmistakably not a secret.
- `git status --porcelain` — status in a stable, script-friendly format, one line per changed file.
  **`.env` must not appear.** If it does, the ignore rule is not doing its job and you must stop
  here.
- `git check-ignore -v .env` — ask git directly: is this path ignored, and by which rule? `-v` makes
  it **v**erbose, printing the file, line number and pattern that matched — for example
  `.gitignore:2:.env	.env`. This is the command that turns "I think it is ignored" into evidence,
  and it is worth memorising: it is how you debug an ignore rule that is not behaving.

## When it breaks

**The one that catches everyone, at least once:**

```text
$ git status --porcelain
 M .env
```

**What it means.** `.env` was committed at some point, so git is *tracking* it — and `.gitignore` is
irrelevant for tracked files. The rule was written after the file was added.

Stop tracking it without deleting it from disk:

```text
$ git rm --cached .env
rm '.env'
$ git commit -m "stop tracking .env"
```

`git rm --cached` removes the file from git's index while leaving your copy alone. From the next
commit onward it is untracked, and `.gitignore` finally applies.

**But be clear about what that did and did not fix.** It stops *future* commits. It does not remove
the key from the commits already made. If the key ever reached a commit that was pushed anywhere —
or even just shared — **rotate it.** Revoke the old one at the provider and issue a new one. History
rewriting (`git filter-repo`, or the BFG tool) exists and works, but it rewrites every commit hash,
breaks every clone and fork, and cannot recall a copy someone already pulled. **Rotation is the fix;
history rewriting is damage control.**

**The trap that removes the file you meant to keep:**

```text
$ git check-ignore -v .env.example
.gitignore:2:.env*	.env.example
```

**What it means.** Somebody replaced the explicit lines with `.env*`, which matches `.env.example`
too — so the file documenting your configuration silently vanished from the repository, and the next
person to clone has no idea what variables to set. The `!.env.example` line above exists precisely
to survive this edit.

**The one that fills a diff with garbage:**

```text
$ git status --porcelain | head -5
?? .venv/Lib/site-packages/certifi/__init__.py
?? .venv/Lib/site-packages/certifi/cacert.pem
?? .venv/Lib/site-packages/charset_normalizer/__init__.py
?? .venv/Lib/site-packages/click/__init__.py
?? .venv/Lib/site-packages/click/_compat.py
```

**What it means.** `.venv/` is not being ignored — usually because `.gitignore` was created *after*
`uv sync` and the pattern was mistyped, or because it says `venv/` without the leading dot. `??`
means untracked. Fix the pattern and confirm with `git check-ignore -v .venv`. If you had committed
these, the repository would be tens of thousands of files heavier and every clone would be slow
forever.

## In production

**Assume every secret that ever touched a commit is compromised.** This is not paranoia; it is the
operating assumption of every security team. Public repository scanning is automated and fast — the
story's nine minutes is typical — and private repositories are not safe either, because they get
cloned to laptops, forked internally, and occasionally made public by accident. **The mature
response to "we committed a key" is always: rotate first, clean up second.**

**Real systems do not use `.env` files in production at all.** `.env` is a development convenience.
Production secrets come from a secret manager — cloud KMS-backed stores, HashiCorp Vault, a
platform's secret facility — which gives you three things a file cannot: access control (who can
read this key), audit logs (who *did* read it), and rotation without a deploy. The mental
progression is `.env` on a laptop, injected environment variables in a container, a secret manager
in production; and the code reads `os.environ` in all three cases, which is why that indirection is
worth having from Day 1.

**Prevention is layered, and each layer is cheap.** Professionals do not rely on `.gitignore` alone:
a **pre-commit hook** scans staged content for high-entropy strings and known key formats and
refuses the commit; the platform runs **push protection** that rejects a push containing a
recognised credential; and **provider-side scanning** catches what escapes both. This repository has
a `.pre-commit-config.yaml` for the first layer. None of these is sufficient alone, which is exactly
why there are three.

**Scope is the control that limits the damage.** Principle 6 — blast radius first — applies to
credentials as much as to tools. A key that can only read, only from one project, and only from one
IP range, is a much smaller incident than an account-wide key. You will build this reasoning
deliberately on **Day 66** (AG-17, least privilege and credential scoping) and publish the resulting
permission table on **Day 70**. The habit to start now: when a provider offers a scoped key, take the
narrowest one that works.

**What degrades at scale.** A `.gitignore` protects one repository. An organisation needs the rule
enforced centrally — org-wide push protection, a shared pre-commit configuration, CI that fails on a
detected secret — because a single repository created by a single person who did not read this page
is enough. The engineering problem stops being "how do I ignore this file" and becomes "how do I
make it impossible for anyone here to commit a secret".

**The review comment a senior engineer leaves.** On a pull request that adds a config file with a
placeholder that looks real: *"Is this a live key? Even a rotated one shouldn't land in history —
use an obviously-fake value and add the real name to `.env.example`."* And on a `.gitignore`
containing `.env*`: *"This also ignores `.env.example`, which we want committed. Please list the
real files explicitly."*

**The interview question.** *"You discover an API key was committed to your repository three months
ago. Walk me through your response."* The answer is ordered, and the order is the answer: **(1)
rotate the key immediately** — before anything else, because every other step takes time and the key
is live during all of it; (2) check provider audit logs for use you did not authorise; (3) stop the
bleeding with `git rm --cached` and a corrected `.gitignore`; (4) decide whether history rewriting
is worth its cost, knowing it cannot recall existing clones; (5) add the layer that would have
prevented it — a pre-commit scan, push protection — so the answer to "how do you stop it recurring"
is not "be more careful". Candidates who start at step 3 have not had a key leaked on them.

## Check yourself

```bash
git check-ignore -v .env && git check-ignore -v .venv && ls -la .env.example && git status --porcelain
```

The first two must each print a matching rule. `.env.example` must exist. And `.env` must **not**
appear anywhere in the status output.

> Why was `.gitignore` written before `.env` rather than after? Then: a key reached a commit that was
