# 2.1 — The folder skeleton, and what earns a folder

## One-line answer

Every folder in this repository exists because something needs to be true about the files inside it —
that they are importable, or tested, or never committed, or generated — and a folder that cannot
name such a rule is a folder that will fill up with things nobody can find.

---

## The story

A project starts with one file. Then a second, because the first got long. Then a folder called
`utils`, because two of the files shared a function.

Eighteen months later, `utils` has forty-one files in it. Nobody can tell you what is in `utils`,
because "utility" is not a category — it is the absence of one. There is a `helpers.py` inside it,
which nobody can distinguish from `utils` itself. There is `utils2.py`. Somebody once created
`common/`, which now also has a `helpers.py`, and there is a running joke about which one is real.

The joke stops being funny during an incident. A configuration value is wrong in production.
Somebody greps for it and finds it defined in three places. Two are dead. Determining which one the
running service actually loads takes forty minutes, during which the service is still wrong.

Nothing in that story required bad engineers. It required exactly one thing: at the moment the first
folder was created, nobody said out loud what rule its contents obeyed. Every folder made after that
inherited the same silence, and silence compounds.

---

## The idea in plain language

A folder is a claim about its contents. Good repositories have a small number of folders, each with
a claim you can state in one sentence, where the sentence is a *rule* and not a *theme*.

"Files about tickets" is a theme, and it decays — because the next file is about tickets *and*
users, and now the theme does not decide anything. "Files that are importable as the `mandala`
package" is a rule: you can look at any file and say yes or no, and so can a tool.

Four rules cover almost every folder in a Python project:

**1. This is the importable package.** In this repository, `src/mandala/`. Code here can be imported
as `import mandala` from anywhere, including from tests. The `src/` wrapper around it is called the
**src layout**, and it exists to close one specific hole: if the package sat at the repository root,
Python would find it simply because you happened to be standing in that directory, and your tests
would pass against your working copy rather than against the *installed* package. With `src/`, the
only way to import `mandala` is for it to be genuinely installed into the environment — which means
a packaging mistake fails in your test run instead of in someone else's install.

**2. This mirrors the package, and proves it works.** `tests/`. Every file here exists to make a
claim about `src/mandala/` that can go red. Principle 7 — *evals before features* — lives in this
folder.

**3. This is written by hand and read by humans.** `docs/` and `days/`. The plan, the index, the
lessons. Prose, versioned like code, reviewed like code.

**4. This is never committed.** `.venv/`, `.env`, caches. Regenerable or secret — and the two are
opposites in every way except this one: neither belongs in git.

There is a fifth rule that only appears in longer projects, and this one has it:

**5. This is generated, and hand-editing it is a bug.** `docs/TRACKER.md`. It is produced from the
curriculum index plus what is on disk. If you edit it by hand, your edit is a lie that survives
until the next regeneration, and then vanishes — the worst of both worlds.

**The rule to hold onto:** a folder is created when a file needs a rule that no existing folder
provides. Not when there are "a lot of files". Not because a similar project had one.

---

## Why Mandala needs it

- **Day 6 builds the provider-fallback router**, and every day from 9 to 90 imports it. It lands in
  `src/mandala/` because it must be importable from a lab on Day 23, a graph node on Day 47, and an
  MCP server on Day 54. Code that only exists inside one day's `lab/` folder cannot be reused, and
  reuse across frameworks is the entire pedagogical engine of this plan (the repetition map, plan
  Part 6).
- **`days/day-NN/lab/` is deliberately *not* importable.** It is where you experiment, break things,
  and leave half-finished ideas. The moment something there is worth keeping, it graduates into
  `src/mandala/` with a test. That graduation is the point — a lab folder is a scratchpad, and a
  scratchpad with a permanent resident is just a badly named module.
- **`tests/fixtures/` holds the golden ticket set** built on Day 2 and used until Day 90. It is the
  reason evals cost `$0`: the same ten invented tickets, replayed offline, so a regression test does
  not spend a free-tier request (Principle 5).
- **`docs/adr/` collects the decision records.** Every phase gate produces one, and Phase 9's
  bake-off produces the big one — ADR-003, the capstone architecture. In an interview, those files
  are the artifact you talk about.

## The mechanism

Create the whole skeleton in one command. Run this from inside the project folder:

```bash
mkdir -p src/mandala tests/fixtures/cassettes days docs/adr scripts .github/workflows
```

**Line by line:**

- `mkdir` — **m**a**k**e **dir**ectory.
- `-p` — create **p**arent directories as needed, and do not error if a directory already exists.
  Both halves matter: without `-p`, `mkdir src/mandala` fails when `src` does not exist yet, and
  re-running the command on an existing tree fails loudly for no reason. `-p` makes this command
  **idempotent** — safe to run twice, which is what you want from any setup step.
- `src/mandala` — the importable package (rule 1). The name matches `[project] name` in
  `pyproject.toml`, which is what lets `import mandala` work.
- `tests/fixtures/cassettes` — fixtures are the invented tickets; **cassettes** are recorded HTTP
  responses. `pytest-recording` (pinned in `pyproject.toml`) can record a real provider call once
  and replay it forever afterwards, which is how a test that exercises a model call can run in CI
  for free.
- `days` — one folder per day, in the hub-plus-`parts/` shape the plan's Part 11 defines.
- `docs/adr` — architecture decision records. One per gate.
- `scripts` — the two programs that keep the ninety days honest, built in section 4.
- `.github/workflows` — where CI lives. Empty today; Day 2 fills it.

Now the two files that turn folders into packages:

```bash
touch src/mandala/__init__.py tests/__init__.py
```

**Line by line:**

- `touch` — create an empty file if it does not exist, and do nothing to it if it does. Another
  idempotent command.
- `src/mandala/__init__.py` — the file whose presence marks a directory as a **package**, the
  importable unit Python understands. **Empty is correct.** People fill these with imports to make
  `from mandala import Router` shorter than `from mandala.router import Router`, and it is a habit
  worth resisting: everything in `__init__.py` runs on *any* import of the package, so a heavy
  import here makes every import slow, and a circular one makes the package unimportable in a way
  that is genuinely hard to diagnose.
- `tests/__init__.py` — makes `tests/` a package too. Its job is different: it lets two test files
  in different subfolders share a name (`test_router.py` in two places) without pytest confusing
  them. Cheap insurance, and the failure it prevents is bewildering when it happens.

Confirm the shape:

```bash
find . -type d -not -path "./.git/*" -not -path "./.venv/*" -not -path "./legacy/*" | sort
```

**Line by line:**

- `find .` — walk everything from here down.
- `-type d` — directories only, so this prints the *shape* rather than the contents.
- `-not -path "./.git/*"` — exclude git's internal storage, which is thousands of folders and none
  of your business.
- `-not -path "./.venv/*"` — exclude the environment, for the same reason: it is machine-generated
  and huge.
- `-not -path "./legacy/*"` — exclude the archived v1.1.0 repository, which is reference material
  and not part of the working shape.
- `| sort` — pipe the results into `sort` so the output is alphabetical and stable, which makes it
  comparable against a previous run.

Finally, prove the package is genuinely importable — which is the claim rule 1 makes:

```bash
uv run python -c "import mandala; print(mandala.__file__)"
```

**Line by line:**

- `import mandala` — succeeds only if the package is installed into the environment. This is the
  `src` layout paying for itself: it fails if packaging is wrong, rather than silently working
  because of your current directory.
- `mandala.__file__` — the path of the `__init__.py` that was actually loaded. Read it. It should be
  inside `src/mandala/`, and if it is anywhere else you have two copies of the package and a
  confusing evening ahead.

## When it breaks

**The import that fails despite the folder being right there:**

```text
$ uv run python -c "import mandala"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'mandala'
```

**What it means.** Usually one of two things, and they are easy to tell apart. Either
`src/mandala/__init__.py` does not exist — so the folder is a folder, not a package — or the project
has not been installed into the environment, which `uv sync` fixes. It is *not* the failure from
[1.1](../01/1.1-why-one-tool-must-own-the-environment.md), because `uv run` has already removed the
`PATH` question. Check the file first; it is the faster test.

**The one that appears once you have two test files with the same name:**

```text
$ uv run pytest
import file mismatch:
imported module 'test_router' has this __file__ attribute:
  /c/.../tests/unit/test_router.py
which is not the same as the test file we want to collect:
  /c/.../tests/integration/test_router.py
HINT: remove __pycache__ / .pyc files and/or use a unique basename for your test modules
```

**What it means.** Two files with the same module name and no package structure to distinguish them,
so pytest imported one and then found another claiming the same identity. The hint suggests unique
filenames; the better fix is the `__init__.py` files you just created, which give each one a
distinct full name (`tests.unit.test_router` versus `tests.integration.test_router`).

**The one that looks like a folder problem and is a naming problem:**

```text
$ uv run python -c "import mandala; print(mandala.__file__)"
C:\Users\me\OneDrive\Desktop\Projects\mandala\mandala\__init__.py
```

**What it means.** You are importing a `mandala` folder at the repository root, not the one in
`src/`. Python found it because the current directory is searched first — which is *exactly* the
hole the `src` layout closes, now demonstrated on your own machine. Two copies of a package is how
you end up editing one and running the other, wondering why your change had no effect.

## In production

**The `src` layout is the default in serious Python repositories for one reason:** it makes "does
the package install correctly?" a question your test run answers, rather than one your users answer.
Without it, tests import the working directory, so a missing `__init__.py`, a file left out of the
package manifest, or a data file that was never included all pass locally and fail on install. With
it, `uv run pytest` is testing the *installed* artifact, which is what will actually ship. That is
the entire argument, and it is why the extra directory earns its keep.

**Folder structure is an access-control surface, not just an organisational one.** By **Day 65** —
the lethal trifecta — this repository's layout is doing security work: which agent can read
`tests/fixtures/` versus reach the network, which credential is mounted into which process, which
tool a given agent is even allowed to import. "Separate contexts, separate permissions, separate
failure domains" (AG-10, Day 8) is a statement about boundaries, and boundaries in a codebase are
mostly module boundaries. A `utils` folder that everything imports is a boundary that does not
exist.

**What degrades at scale.** In a monorepo the same instinct scales up: packages get their own
`pyproject.toml`, dependencies between them become explicit and enforceable, and the build system
can then test only what changed. The failure at scale is always the same as the story's — a shared
"common" package that every service imports, which nobody can change without risking all of them,
and which therefore never gets changed and only grows.

**Generated files need a marker, and this repository uses one.** `docs/TRACKER.md` opens with "Do
not edit this file by hand" and names the command that regenerates it. Without such a header,
someone will eventually improve it by hand — reasonably, since it is a Markdown file — and lose the
edit at the next regeneration. Worse, if the generator is not obvious, they may not lose it: they
may fix the symptom in the generated file and leave the generator wrong.

**The review comment a senior engineer leaves.** On a pull request adding a `utils.py`: *"What is
the rule for what goes in here? If the answer is 'things that did not fit elsewhere', let's name the
actual concept instead — otherwise this file is a year away from being unreadable."* And on a new
top-level directory: *"What does this folder promise about its contents that `src/` does not? Add a
line to the README if the answer is not obvious in six months."*

**The interview question.** *"Why do Python projects put their package under `src/`?"* The weak
answer is "convention". The one that lands: without it, the current working directory shadows the
installed package, so tests pass against your working copy and packaging errors escape to users;
with it, importing the package at all requires it to be installed, so the test run exercises the
real artifact. Anyone who has shipped a library with a missing `__init__.py` gives this answer
instantly.
